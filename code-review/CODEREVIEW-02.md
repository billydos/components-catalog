- **Дата:** 2026-10-08
- **База:** коммит `a5140bb` (+ незакоммиченные правки: нет; рабочий каталог чист — в `qa/tmp/` остался игнорируемый артефакт убитого прогона `load-1693374078`, см. B1)

## Резюме

Кодовая база по-прежнему в хорошем состоянии: слоистость и дисциплина ошибок-значений выдержаны (SQL не поднимается выше `storage`, разбор формата не выходит из `importer`, MsgID-каталог полон и зеркален en/ru), перезапись плейсхолдеров `@имя → $n` в единой точке корректна и покрыта тестами, пакетные чтения карточек и single-flight кэш снимка реализованы аккуратно. Базовые проверки зелёные; последний прогон `qa/runner` на postgres с нагрузкой 10⁴ — 52/52 PASS; `-race` на ядрах чист. Исправления CODEREVIEW-01 проверены и работают (positional-перезапись, ON CONFLICT-подавление гонок писателей, batch-чтения, single-flight, зарезервированные ключи метасхемы).

Главная концентрация проблем этого обзора — **применение каталога и записей в `internal/importer`** (находки A1–A3, B6–B9): контракт «ошибка в любом значении — не применяется вовсе» нарушен в трёх самостоятельных местах, все три воспроизведены: `catalog import` смешанного файла **применяет записи и лишь затем отвергает файл** (A1); строка NDJSON с `catalog` и записью в одной строке **молча отбрасывает запись с exit 0** (A2); ошибки формы в секции каталога не блокируют запись — поле `unit: 5` теряется молча при напечатанной проблеме, `catalog: []` инкрементирует ревизию (A3). Четвёртая находка высокого приоритета — гонка POST в REST (A4, по коду): проигравший параллельный POST **применяет свои секции к чужой записи и отвечает 409** — 409 после мутации нарушает контракт openapi.

Средний приоритет группируется в четыре зоны: (1) CLI-обвязка — молча игнорируемый аргумент `catalog export` (B2, воспроизведено), `help --lang ru` ломается на флагах (B3, воспроизведено), `init` печатает DSN с паролем (B4); (2) i18n — паника в публичном API (B13), некорректный разбор q-значений Accept-Language (B14, `en; q=0.3` игнорирует q) и русский литерал «все классы» в каноническом en-рендере (B15, воспроизведено — тот же класс, что закрытый B3 из CODEREVIEW-01); (3) грамматика series — инвариант «семейства не разбираются строгими системами» проверен тестом не для всех семейств: `КД105` разбирается как диод ГОСТ, `КМ44` даёт ложный вердикт «класс не поддерживается» вместо конденсатора КМ (B16, воспроизведено); (4) обвязка QA — таймауты фаз фактически не гарантируются из-за отсутствия `WaitDelay` (B1, следы в `qa/tmp/`), Ctrl+C даёт шквал ложных FAIL в закоммиченном отчёте (B10). Остальное — B-находки надёжности (компенсация холостых созданий B7, полный отказ экспорта от одной неразбираемой записи B8, ETag поиска, общий для всех комбинаций запроса, B5) и большой пласт C-гигиены.

Переносы из CODEREVIEW-01: **C5 (YAML `.inf`/`.nan` → вводящее в заблуждение «должно быть числом») и C12 (продукты разбора не перезаписываются при обновлении) не исправлены** — перепроверены, C5 воспроизведено. За рамками: нога PostgreSQL локально (нет DSN; сужено по отчётам CI/qa-reports), содержательная корректность предметных данных `data/`, поведение при обрывах сети.

## A. Находки высокого приоритета

### A1. `catalog import` смешанного файла применяет записи, а затем отвергает файл

**Где:** `internal/importer/importer.go:59-68` (`ImportCatalogFile` — проверка `rep.Records > 0` после `Import`), применяющие пути — `importDocument` (`importer.go:103`) и `importNDJSON` (`importer.go:174`); потребитель — `internal/cli/commands.go:187` (`runCatalogImport`, без dry-run); контракт — собственное сообщение `MsgImportCatalogRecordsMixed` («catalog import применяется к файлу только с секцией catalog») и правило AGENTS.md «ошибка в любом значении секции — запись не применяется вовсе».

`ImportCatalogFile` сначала выполняет полный `Import` (секция каталога применяется, записи применяются, `data_revision` инкрементируется), и только потом проверяет, что записи в файле были. Воспроизведение:

```
$ printf '{"catalog": {"kinds": [{"code": "sensor"}]}, "transistors": [{"name": "КТ315Б", "manufacturers": ["Завод"]}]}' > mixed.jsonc
$ catalogctl catalog import mixed.jsonc --db mix.db --lang ru
Ошибка: mixed.jsonc: файл содержит записи классов; catalog import применяется к файлу только с секцией catalog
exit 1
$ catalogctl count --db mix.db
1                                          # запись применена вопреки отказу
$ catalogctl info КТ315Б --db mix.db
КТ315Б — транзисторы; id 1 …               # включая производителей
```

Операция заявляет отказ — и при этом изменила базу (записи, производители, ревизии). Тест `TestCatalogImportFileRejectsRecords` проверяет только текст ошибки, не состояние БД.

**Рекомендация:** проверять отсутствие записей до применения: в `importDocument`/`importNDJSON` вернуть признак «есть записи» из фазы чтения и применять каталог/записи только при её отсутствии (либо полностью перейти на схему «чтение и план → гейт → применение»). Дополнить тест проверкой `count == 0` и неизменности `data_revision` после отказа.

**Решено:** — (обзор без правок).

### A2. NDJSON: строка с `catalog` и записью молча отбрасывает запись

**Где:** `internal/importer/importer.go:146-158` — ветка `if catVal, isCat := v.has("catalog"); isCat { …; continue }` выполняется до правила «ровно один ключ» обёртки (`ReadRecordLine`, `reader.go:588-591`).

Строка NDJSON `{"catalog": {...}, "transistors": [{...}]}` интерпретируется как catalog-строка: каталог сливается, `continue` — второй ключ отбрасывается без проблемы, без счётчика записей, без записи в БД. Воспроизведение:

```
$ printf '{"catalog": {"kinds": [{"code": "sensor"}]}, "transistors": [{"name": "КТ315Б"}]}\n' > drop.ndjson
$ catalogctl import drop.ndjson --db drop.db --lang ru
drop.ndjson: записей: 0, добавлено: 0, …, каталог расширен
exit 0                                     # запись исчезла молча, успех
```

Формат заявляет «одна JSON-строка — одна сущность» (ndjson.go:8-11) и «тихая потеря данных недопустима» (value.go:10-12) — здесь потеря тихая и с нулевым кодом выхода.

**Рекомендация:** в catalog-ветке проверять `len(v.members) == 1` и отвергать строку проблемой формата (по образцу `MsgImportNdjsonWrapperSingle`); то же для записи с лишними ключами рядом с классом уже покрыто `ReadRecordLine`. Тест — строка с двумя ключами, один из которых `catalog`.

**Решено:** —.

### A3. Ошибки формы в секции каталога не блокируют применение: поля теряются молча, ревизия двигается впустую

**Где:** `internal/importer/importer.go:221-242` (`applyCatalog` — гейт только по `probs` от `ApplyCatalog`, `issues` читателя в гейт не входят); источник — `internal/importer/catalog_section.go`: отбрасываемые `ok` у необязательных полей (`:323` unit условий, `:376` unit параметров, `:405` rule параметров, `:446/:453/:467` group/unit/rule атрибутов, `:278` tail_semantic) и «мягкие» `continue` с выпадением строки из входа (`:383-428`); контракт — AGENTS.md «запись не применяется вовсе; частичное применение запрещено» (для каталога — тот же принцип, `CatalogService.Import` заявляет «непустой список проблем — отказ целиком»).

Читатель секции каталога накапливает проблему, но всё равно добавляет изменённые данные во вход; метасхема их уже не отвергает (данные формально валидны), и `Catalog.Import` применяет. Воспроизведения:

```
$ printf '{"catalog": {"conditions": [{"code": "ta", "unit": 5}]}}' > bad.jsonc
$ catalogctl catalog import bad.jsonc --db bc.db --lang ru
… каталог расширен
Проблема: каталог: раздел conditions, «ta»: поле "unit" должно быть строкой
exit 1                                     # и при этом:
$ catalogctl catalog export --db bc.db | … # условие "ta" записано БЕЗ unit — значение потеряно молча

$ printf '{"catalog": []}' > empt.jsonc
$ catalogctl catalog import empt.jsonc --db em.db --lang ru
… каталог расширен
Проблема: каталог: catalog должен быть объектом с подразделами…
exit 1                                     # catalog_revision инкрементирован, кэш сброшен, CatalogApplied=true
```

Симметрично: строка с невалидным обязательным полем выпадает из входа и секция применяется частично (остальные строки применяются). Итог: отчёт говорит «отказ/проблема», а база изменена — состояние расходится с убеждением пользователя, unit/rule/tail_semantic исчезают бесследно.

**Рекомендация:** единый гейт: `applyCatalog` обязан отказывать (без записи) при `len(issues) > 0`, а читатель — не добавлять строку/поле после записанной проблемы (проверять `ok`, как это уже сделано на уровне записей устройств). Тесты: три воспроизведения выше (unit неверного типа — каталожная таблица без изменений и ревизия не двигается; `catalog: []` — отказ без `CatalogApplied`).

**Решено:** —.

### A4. Гонка POST: проигравший запрос мутирует чужую запись и отвечает 409

**Где:** `internal/httpapi/handlers.go:184-221` (`handleCreate`): пред-проверка `Get` (строки 195-202) → `Upsert` (203) → `outcome != OutcomeAdded` → 409 (208-214); мутирующая сторона — `internal/service/devices.go:151-160` (`applyUpsert` для существующей записи выполняет `writeUpsert` с полной секционной семантикой и возвращает `OutcomeUpdatedExisting` уже после коммита); контракт — openapi.yaml (POST «Существующий (kind, designation) — 409») и общее правило HTTP: 409 не должен оставлять мутацию, вызвавшую конфликт.

Между пред-проверкой `Get` и `Upsert` другой клиент успевает создать запись (второй POST того же обозначения, PUT, импорт). Тогда `Upsert` проигравшего **применяет секции своего тела к записи победителя** (merge + writeUpsert + commit + `data_revision++`) и лишь затем транспорт отвечает 409 `already_exists`. Запись победителя теперь содержит данные проигравшего; оба клиента считают себя правыми. Окно узкое (миллисекунды), но систематическое: любой параллельный POST/PUT/импорт одного обозначения. Детерминированное воспроизведение требует гонки, поэтому «По коду»: порядок операторов в `applyUpsert`/`handleCreate` однозначен.

Родственный уже закрытый C14 (CODEREVIEW-01) вводил 409 при `outcome != Added`, но оставил мутацию — исправлена половина проблемы.

**Рекомендация:** атомарный режим «только создание» в сервисном слое: флаг в `Upsert`/отдельный метод `Create`, который внутри транзакции при обнаружении существующей записи откатывается без применения и возвращает исход/ошибку `already_exists` (транспорт лишь маппит её в 409). Тогда 409 перестаёт мутировать по построению. Тест — сервисный: `Create` на существующей записи не меняет её секции.

**Решено:** —.

## B. Находки среднего приоритета

### B1. qa/runner: таймауты фаз не гарантируются — внуки убитой команды держат пайпы

**Где:** `qa/runner/exec.go:44-56` (`runCmdEnv`), `:61-81` (`runCmdOut`), `:194` (`loadPhase`) — `exec.CommandContext` без `cmd.WaitDelay`, `Stdout/Stderr` — `bytes.Buffer`/файл.

При истечении ctx `CommandContext` убивает только прямого потомка (`go`); внуки (тестовый бинарник `qa.test`, порождаемый `go test` в static/load-фазах) наследуют write-концы пайпов, и `cmd.Run()` не возвращается, пока внуки не закроются. С `WaitDelay == 0` (умолчание) заявленные `staticTimeout` 30м / `loadTimeout` 40м не ограничивают прогон — зависший тест тянет джобу до её собственного таймаута. Косвенное подтверждение: `qa/tmp/load-1693374078/{load.db,load.db-wal,load.db-shm}` — остаток убитого прогона, чей `t.Cleanup` не выполнился.

**Рекомендация:** `cmd.WaitDelay = 30 * time.Second` во всех трёх точках создания команд; при необходимости — `Cancel` с групповым убийством дерева (не переносимо на windows, WaitDelay достаточно).

### B2. `catalog export <файл>` молча игнорирует аргумент

**Где:** `internal/cli/commands.go:133-139` — граница `len(rest) > 1` пропускает ровно один лишний позиционный аргумент, а `runCatalogExport` файл не принимает.

Воспроизведение: `catalogctl catalog export backup.jsonc --db db` → exit 0, вывод в stdout, `backup.jsonc` молча не создан. Для сравнения: `import` требует ровно один (`!= 1`), `list` — ноль (`> 0`). Похоже на off-by-one в `> 1` вместо `> 0`. Пользователь теряет выгрузку, не заметив.

**Рекомендация:** `> 0` + локализованная ошибка; осознанно полезнее — поддержать аргумент как файл назначения (парность с `import`).

### B3. `help` не пропускает флаги: `help --lang ru parse` ломается

**Где:** `internal/cli/help.go:19-40` — после сканирования пар `--lang значение` команда берётся как `args[0]` без пропуска флагов; ошибка печатается жёстко на en (строка 34), хотя локаль распарсена двумя строками выше; форма `--lang=` не поддержана (в отличие от `langFromArgs`, run.go:285-299); лишние позиционные после команды молча игнорируются.

Воспроизведение: `catalogctl help --lang ru parse` → `Error: unknown command «--lang»; help: catalogctl help`. В CLI теперь три разборщика `--lang` с разным поведением (run.go, help.go, parseArgs).

**Рекомендация:** пропустить флаги при выборе команды (или переиспользовать `parseArgs`), печатать ошибку на выбранной локали, отвергать лишние аргументы.

### B4. `init` печатает DSN с паролем

**Где:** `internal/cli/commands.go:30` — `MsgCliDbInitialized` получает `dsn` дословно из `--dsn`.

`catalogctl init --dialect postgres --dsn postgres://user:secret@host/db` выводит строку инициализации с паролем в терминал/лог CI. Достаточно замаскировать часть после `@`/`:` при выводе (DSN в ошибке подключения pgx уже редактирован — проверено: выводится `user=u database=db`).

**Рекомендация:** маскировать пароль в отображаемом DSN (одна функция; пригодится и для B12).

### B5. ETag поиска общий для всех запросов, 304 отсекает сервисную валидацию

**Где:** `internal/httpapi/handlers.go:77-105` (`handleSearch`): `etag := "data-<rev>"` без учёта параметров запроса; 304 возвращается до вызова `Search`.

Два следствия: (1) один ETag идентифицирует разные представления (`/components?q=a` и `?par.Pmax=5`) — RFC 9110 требует ETag на представление; клиент/прокси, переиспользующий ETag между URL, получит 304 на невыбранное ими содержимое; (2) транспортные ошибки разбора (limit/sort/числа) дают 400 до проверки ETag, а сервисная семантика (`kind=bogus`, неизвестный `par.<код>`, неприменимый параметр) поднимается из `Search` — уже после отсечения 304: тот же класс невалидного ввода даёт 304 вместо 400 при совпавшем ETag.

**Рекомендация:** включить в ETag хэш канонизированного запроса (`data-<rev>-<hash(query)>`) либо выполнять сервисную валидацию до 304 (дёшево: собрать `SearchRequest` до возврата Not-Modified).

### B6. Элементы набора условий не отвергают неизвестные ключи

**Где:** `internal/importer/catalog_section.go:550-569` — для объекта элемента набора нет `checkKeys` (допустимы `condition`, `mode`, `fixed_value`); все прочие уровни (корень, подразделы, строки, записи, секции, значения, аналоги) неизвестные ключи отвергают.

Воспроизведение: `"fixed_value"` с опечаткой `fxed_value` — импорт проходит (exit 0, «каталог расширен»), экспорт показывает набор **без** `fixed_value`: обязательная константа молча превратилась в свободно задаваемое условие. Изменение семантики валидации без единого сообщения — там, где строгость заявлена максимальной.

**Рекомендация:** `checkKeys` для элемента набора (по образцу соседних уровней) + тест на опечатку.

### B7. Компенсация холостых созданий не структурна

**Где:** `internal/importer/importer.go:315-354` — `recordIssue` выводит запись из очереди, а компенсирующий `Delete` (строки 346-354) выполняется только для оставшихся; `_, _ = … Delete(…)` игнорирует результат.

Если запись, созданная холостым применением (`p.created`), затем проваливает полное применение с ошибкой, отличной от `analog_not_found` (например, сыроя ошибка хранения), она покидает очередь через `recordIssue` — и холостая строка остаётся в БД при отчёте «отвергнуто». Анализ путей показывает, что регулярно достижимые ошибки аналогов (self/duplicate) срабатывают в первом проходе, поэтому окно узкое — но контракт «запись не применяется вовсе» держится не по построению, а совпадением путей. Плюс: компенсирующий Delete глотает ошибку и вместе с холостым созданием дважды инкрементирует `data_revision` для «не применённой» записи.

**Рекомендация:** флаг `created` учитывать в ветке `recordIssue` (удалять и там); ошибку компенсации фиксировать проблемой прогона; при желании — холостое создание и компенсацию выполнять без `BumpDataRevision` (служебная перегрузка Upsert) либо мириться с шумом ревизии, зафиксировав комментарием.

### B8. Экспорт прерывается целиком от одной неразбираемой записи

**Где:** `internal/importer/writer.go:121-125` — `ParseForSystem` по текущему каталогу; ошибка — `return nil, err` для всего экспорта.

Экспорт переразбирает каждое хранимое обозначение. Эволюция каталога (удалённое семейство, изменение грамматики) делает часть хранимых записей неразбираемыми — и `export` падает на первой же, не выдав ни частичного результата, ни пропуска. Разбор используется только для diff-а секции `fields` — могут быть и записи без явных полей, которым разбор не нужен вовсе.

**Рекомендация:** на ошибку разбора — пропускать секцию `fields` записи (или всю запись с проблемой в отчёт экспорта), продолжая выгрузку; жёсткий отказ оставить только для ошибок чтения БД.

### B9. NDJSON: не стриминг и позиционно-зависимая строгость слияния каталога

**Где:** `internal/importer/importer.go:107-176` — комментарий «записи применяются по мере чтения», но записи накапливаются в `var records []Record` (строка 120) и применяются после цикла (174): память растёт с файлом вопреки цели построчности (ndjson.go:8-11); `importer.go:180-209` — `mergeCatalogTrees` даёт жёсткую ошибку (`MsgImportCatalogPlain`/`MsgImportNdjsonSubsection`) там, где первый catalog-экземпляр того же содержимого дал бы мягкую проблему читателя: `{"catalog": 5}` первой строкой — soft issue, второй — abort прогона; `units: null` в документе — пропуск подраздела, при слиянии второй строки — жёсткая ошибка.

**Рекомендация:** либо честно зафиксировать буферизацию комментарием/документацией (всё-или-ничего на синтаксисе), либо применять записи по мере чтения (тогда правило «catalog до записей» уже обеспечивает корректный порядок). Слияние каталога — нормализовать к мягкой проблеме единой точкой (читатель), а не двум режимам по позиции.

### B10. qa/runner: Ctrl+C превращает отменённый прогон в шквал FAIL

**Где:** `qa/runner/main.go:40-41` — `signal.NotifyContext` висит весь прогон.

После первого Ctrl+C каждый шаг падает мгновенно (`exec.CommandContext` на отменённом ctx → code −1) и пишется как FAIL — закоммиченный отчёт неотличим от реальной регрессии. Повторный Ctrl+C поглощается (обработчик стоит до выхода) — вместе с B1 прогон может стать неубиваемым без SIGKILL.

**Рекомендация:** после первого сигнала — помечать оставшиеся шаги пропуском с причиной «отменён» и отдельный вердикт/exit (например, 130); `stop()` после первого сигнала возвращает умолчание — второй Ctrl+C убивает немедленно.

### B11. freePort TOCTOU в REST-носителе сценариев

**Где:** `qa/runner/hostinfo.go:161-171` (`freePort` — listen :0 → close) и `qa/runner/rest_suite.go:25-39` (привязка порта позже запуском restsrv).

Между закрытием listener и `ListenAndServe` порт может занять другой процесс: перемежающийся отказ ноги REST на общих CI-машинах, диагностика — «rest/ready FAIL с хвостом лога», причина неочевидна.

**Рекомендация:** restsrv сам выбирает порт (`--addr=127.0.0.1:0`) и печатает фактический (готовая строка ready), либо повтор с новым портом при отказе готовности.

### B12. Ошибки postgres попадают в закоммичаемый отчёт дословно

**Где:** `qa/runner/dbinfo.go:26-36` — `"ping: "+err.Error()` в детали проверки; отчёты коммитятся (qa/README.md) и выгружаются артефактами.

pgx редактирует пароли в ошибках разбора конфигурации «best effort» (документация драйвера прямо не рекомендует считать их безопасными к показу). Кривой `-postgres-dsn` может оставить след пароля в `qa/reports/*.log` — публичном артефакте.

**Рекомендация:** маскировать DSN перед попаданием в отчёт (общая функция с B4); в детали писать класс ошибки + позицию.

### B13. `i18n.mustKnown` паникует из 15 публичных функций

**Где:** `internal/i18n/language.go:134-138`; вызывается из `KindName`/`SystemName`/`UnitName`/`UnitSymbol`/`FamilyName`/`ConditionName`/`GroupName`/`ParameterName`/`AttributeName`/`RuleDescription`/`DesignationField`/`MaterialName`/`SubclassName`/`AdjustmentName`/`CategoryName` и через `FormatValue`.

Паника русской магической строкой — нарушение заявленных свойств `domain` («без паник», D9-каталог) уже в i18n; встраивающий сервис, передавший локаль из конфигурации без `ParseLanguage`, роняет процесс на первом выводе. Сегодня из CLI/REST путь недостижим (локали валидированы), но API публичное.

**Рекомендация:** заменить панику на молчаливый fallback к `En` (неформатная локаль уже так ведёт себя в `resolve`, language.go:102-105) — `mustKnown` удалить вовсе.

### B14. Accept-Language: q-значения разбираются некорректно

**Где:** `internal/i18n/language.go:71-81` — `params` после `strings.Cut(part, ";")` сохраняет ведущий пробел, `CutPrefix(params, "q=")` не срабатывает для RFC-легальной формы `en; q=0.3` — q молча остаётся 1.

Следствия: заголовок `en; q=0.3, ru` выбирает en вместо ru (порядок приоритетов перевёрнут); `q=0` («неприемлемо» по RFC 9110) не исключает кандидат; `Q=` не распознаётся; `ParseFloat("nan")` даёт NaN-q с нестабильным сравнением. Тест `TestNegotiate` покрывает только плотные хорошо оформленные заголовки.

**Рекомендация:** `strings.TrimSpace` на `params` до `CutPrefix` (и на значении q), кандидатов с q=0 отфильтровывать, сравнение — через корректный компаратор. Таблица к TestNegotiate: `en; q=0.3, ru` → ru; `ru;q=0` → en.

### B15. Русский литерал «все классы» в каноническом en-рендере family_unknown

**Где:** `internal/domain/series.go:326` — `scope := "все классы"` подставляется аргументом `%[3]s` в `family_unknown`.

Воспроизведение:

```
$ catalogctl parse ЪЪЪ-5 --system series --lang en
Error: designation «ЪЪЪ-5»: unknown family «ЪЪЪ»; supported families (все классы): CFR, KNP, …
```

Каноническое en-сообщение содержит русский фрагмент — тот же класс, что B3 из CODEREVIEW-01 (исправлен введением MsgExpectCap*); здесь остался один литерал. Пин-тестом закреплён как есть (designation_test).

**Рекомендация:** `MsgFamiliesAllScopes`-аргумент (`domain.MsgArg`) с форматами en/ru одним изменением по D9; обновить пин.

### B16. Инвариант семейств series проверен не для всех семей; КД/КМ коллидируют с ГОСТ

**Где:** `internal/domain/series.go:110-124` (семьи без `Examples`: КБГИ, КД, КЛС, КПК, КЭГ, МБГО, СГМ, ЭМ) и `series_test.go:20-27` — инвариант «не разбирается строгими системами» тест проверяет только по `family.Examples`; `internal/domain/parse_gost.go` — перехват форм.

Воспроизведения:

```
$ catalogctl parse КД105    # → диоды, система ГОСТ  (КД-конденсатор с 3-значным номером недостижим)
$ catalogctl parse КМ44     # Ошибка: обозначение принадлежит классу, не поддерживаемому модулем
$ catalogctl parse КМ4      # → конденсаторы, серия КМ (однозначные формы работают)
```

Для `КМ`+2 цифры ГОСТ завершается синтаксически и даёт вердикт `KindNotSupported`, который обрывает автодетект — пользователь получает неверный диагноз вместо конденсатора КМ. Семь семей вовсе не покрыты тестом инварианта.

**Рекомендация:** (1) тест инварианта — по всем семьям реестра (сгенерировать формы `<семья><мин.номер>`), а не только по Examples; (2) предметное решение по коллизиям КД/КМ: либо расширить `Examples`/документацию (канонические формы конденсаторов КД/КМ проходят через дефис/однозначные номера), либо в автодетекте пропускать вердикт `KindNotSupported`, когда обозначение является префиксом известного семейства series (обсудить с планом 03 §2.4 — порядок систем зафиксирован).

## Что сделано хорошо

- **Дисциплина контрактов ядра**: перезапись `@имя → $n` в единственной точке `positional` с пропусканием литералов/комментариев и табличными тестами (`db.go:147-213`); все DML-пути идут через общие хелперы; аргументы детерминированы текстом запроса.
- **Гонки писателей закрыты систематически**: `ON CONFLICT DO NOTHING` + перечитывание id по ключу во всех точках вставки (устройства, производители, связи, атрибуты, аналоги, меты) — с тестом детерминированной гонки на postgres; выводы CODEREVIEW-01 B6 подтверждены чтением.
- **Пакетные чтения и кэш**: `buildCards` — восемь SELECT на страницу с группировкой в Go, guard'ы пустых списков; `Cache` — single-flight с ревизией из того же согласованного чтения снимка (пара «снимок ≠ ревизия» невозможна по построению), стресс-тесты гонок зелёные под `-race`.
- **Читатель формата**: дубликаты ключей отвергаются во всех трёх форматах; null/`[]`/`{}` различимы и семантика секций проведена единообразно через reader → merge → engine (пин-тесты); числа хранятся исходным текстом — точность не теряется; `yamlPlain` защищает от интерпретации YAML 1.1 (yes/no/on/off/0x/inf — закавычены).
- **Движок валидации**: все предметные проверки — данными снимка (типы значений, positivity/ceiling, наборы условий с fixed_value, enum, применимость D7); жёсткая проверка ключей на всех уровнях, кроме найденного B6.
- **REST-гигиена**: строгий разбор запросов (неизвестный ключ — 400, отсортированные детерминированные проблемы), корректный 405+Allow, recover с метрикой, `MaxBytesReader` с классификацией `MaxBytesError`, ETag каталога из того же снимка, что и тело; маршруты пин-тестом против openapi.
- **qa/runner**: структурный отчёт точно соответствует грамматике qa-log/1 (проверено сличением с реальным отчётом), честные коды выхода (0/1/2), `-p 1` для postgres-ноги, DSN путешествует одним argv-элементом (пароли с пробелами безопасны), ci.yml соответствует заявкам qa/README.md (три джобы, pg_isready, артефакты при любом исходе).
- **Тестовая культура**: пин-тесты сидов против реестров, двусторонняя сверка таблиц testutil/storage, зеркальность бандлов en/ru, `TestPositional*`, стресс-тесты снимка и кэша — высокое покрытие именно контрактов, а не строк.

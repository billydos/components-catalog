## Резюме

Общее состояние кодовой базы хорошее: дисциплина слоёв и ошибок-значений выдержана, инъекций SQL, утечек соединений, паник на пользовательском вводе и нарушений транзакционной дисциплины не найдено; build/vet/gofmt/test зелёные. Все проверенные находки CODEREVIEW-02 в зонах httpapi/cli/i18n/importer/qa подтверждённо исправлены коммитом `030efbd` (A1–A4, B1–B8, B10–B16, C5 — см. «Выполненные проверки» и C50 об устаревших статусах того отчёта); регрессий исправления не внесли, кроме одного нового зазора во входном контуре импорта (A1).

Главные новые проблемы концентрируются в трёх местах. Во-первых, входной контур NDJSON-импорта: строка-обёртка `{"catalog":…, "<класс>":…}` обходит гейт смешанного файла `catalog import` — каталог применяется, запись строки молча теряется, команда завершается кодом 1 уже после мутации (A1); невалидный JSON-хвост после полного значения строки принимается без диагностики вопреки собственному контракту декодера (A2). Во-вторых, производительность и контракты storage: квадратичная чистка сирот-производителей на каждую замену секции (B1), двойное выполнение тяжёлого WHERE поиска с рассинхроном total/страница (B2), незащищённый лимит параметров батч-чтений (B6). В-третьих, семантика валидации значений: значения исполнений обходят проверку секций (B3), деактивация параметра делает записи с его значениями неотрекаемыми и ломает заявленный инвариант «повторный импорт того же файла — Skipped» (B4), недетерминированный выбор ошибки валидации из map-порядка (B5).

Проверено и чисто: пиннинг плейсхолдеров и переносимость DML, race-безопасность кэша снимка, строгий разбор форматов (дубли ключей, YAML-нелитералы), REST (recover, лимит тела, ETag по запросу, 409 без мутации), полнота i18n-бандлов (353/353 msg, 278/278 отображаемых, en/ru паритет), консистентность сидов с реестрами domain. За рамками остались: прогон интеграционных тестов на реальном PostgreSQL (нет службы), нагрузочная прикидка `CATALOG_QA_SCALE=10000` (не входит в задачу аудита), аудит data/ и docs/plan/ по существу (сверялись только точки контакта кода).

## A. Находки высокого приоритета

### A1. Строка-обёртка `{"catalog":…, "<класс>":…}` обходит гейт смешанного файла `catalog import`: каталог применяется, запись теряется молча, код 1 — после мутации

**Где:** `internal/importer/importer.go:166-176` (`importNDJSON` — ветка обёртки), `:197` (инкремент `rep.Records` только для строк-записей), `:205-207` (гейт `catalogOnly && rep.Records > 0`), `:263-279` (`planCatalog` — в решении `apply` участвуют только проблемы формы самой секции catalog, построчные issues не входят); потребитель — `internal/cli/commands.go:513-533` (`printReport` — код 1 при `HasIssues()`, но мутация уже произошла); контракт — собственное сообщение `MsgImportCatalogRecordsMixed` и докомментарий `ImportCatalogFile` («Смешанный файл отвергается до каких-либо записей в БД», importer.go:57-60).

Существо: строка-обёртка с двумя ключами получает проблему `MsgImportNdjsonWrapperSingle` и `continue` — без инкремента `rep.Records` и без пометки каталога (`catTainted` ставится только для ошибок слияния). В режиме `catalog import` гейт «есть записи» не срабатывает (Records == 0), каталог остальных строк применяется через `commitCatalog`. Итог: (1) запись, находящаяся в обёртке, молча теряется — не применяется и не учитывается в сводке; (2) её секция `catalog` тоже молча отбрасывается (строка не сливается); (3) команда завершается кодом 1 уже после применения каталога — «ошибка → не применяется» нарушено на уровне команды. Воспроизведено: файл `{"catalog":{"units":[{"code":"kOhm"}]}}` + `{"catalog":{"units":[{"code":"V"}]},"resistors":{"name":"МЛТ-0.5","system":"gost"}}` → вывод `records: 0, … catalog extended`, «Problem: line 2: the wrapper line must contain exactly one key», `exit=1`, единица V присутствует в каталоге, записей 0. Это тот же класс, что исправленная A2 из CODEREVIEW-02 (тихая потеря записи при exit-кодах успеха/ошибки), — регрессионный зазор фикса A1/A2 того отчёта: гейт смешанного файла не видит записей, «спрятанных» в обёртке.

**Рекомендация:** считать обёртку с классовым ключом записью для гейта: при `catalogOnly` инкрементировать `rep.Records` (или отдельный флаг «виден классовый ключ») до проверки `:205`; тест режима `catalog import` на NDJSON-файл с обёрткой (сейчас покрыт только jsonc-путь, importer_test.go).

**Решено:** —

### A2. Невалидный JSON-хвост после полного значения NDJSON-строки принимается без диагностики

**Где:** `internal/importer/format_jsonc.go:29-43` (`decodeJSONDocument`/`decodeJSONValue` — NDJSON-путь `format.go:78-84` идёт мимо `hujson.Standardize`, который защищает только jsonc-документы); контракт — докомментарий функции: «после значения данных быть не должно» (:29-31) и политика пакета «тихая потеря данных недопустима» (:14-16).

Существо: проверка хвоста `if err := decoder.Decode(new(json.RawMessage)); err == nil { ошибка }` ловит только валидный второй JSON (например, `}{…}` — две записи в одной строке). Если хвост невалиден (`…}}`, `…}} xyz`), `Decode` возвращает `*json.SyntaxError`, `err != nil`, проверка `err == nil` не срабатывает — `SyntaxError` молча отбрасывается, строка принимается как запись. Пользователь, чей файл повреждён (обрыв конкатенации, лишняя скобка), получает успешное чтение записи без какого-либо указания на мусор во входе — вопреки заявленному «после значения данных быть не должно». Воспроизведено: строка `{"resistors":{"name":"МЛТ-0.5","system":"gost"}} xyz` читается как запись (`records: 1`; отказ только по семантике системы), тогда как корректное поведение — жёсткая ошибка синтаксиса файла с `MsgImportUnexpectedToken`.

**Рекомендация:** однострочный фикс — принимать только `io.EOF`: `if err := decoder.Decode(new(json.RawMessage)); !errors.Is(err, io.EOF) { return … unexpectedToken }`; тест на `…}}` и `…}} xyz` для NDJSON-строки.

**Решено:** —

## B. Находки среднего приоритета

### B1. Чистка сирот-производителей — O(N²) на импорте: анти-джойн `NOT IN` без индекса после каждой замены секции

**Где:** `internal/storage/devices.go:920-939` (`ReplaceManufacturers` — чистка после каждой замены), `:1024` (`deleteDeviceWhere`), `:1029-1034` (`deleteOrphanManufacturers` — `DELETE … WHERE id NOT IN (SELECT manufacturer_id FROM device_manufacturers)`); PK таблицы связей ведёт `device_id`, индекса по `manufacturer_id` нет (ddl.go).

Существо: на каждый upsert записи с производителями и на каждое удаление выполняется полный анти-джойн растущей таблицы — при импорте N записей это O(N²) сканов плюс 2–3 оператора на имя (insert-or-select + связь). Заявленная нагрузочная прикидка CI (`CATALOG_QA_SCALE=10000`) уже платит за это; при росте базы импорт деградирует квадратично.

**Рекомендация:** чистить сирот один раз в конце транзакции импорта (флаг на `Tx` или отдельный метод, вызываемый пакетно); заменить `NOT IN` на переносимый `NOT EXISTS`; добавить индекс по `device_manufacturers(manufacturer_id)` с инкрементом `SchemaVersion` (правило AGENTS: изменение DDL — с инкрементом константы).

**Решено:** —

### B2. Поиск: COUNT и страница — два тяжёлых запроса, рассинхрон total/страница; отрицательный Limit — расхождение диалектов

**Где:** `internal/storage/search.go:254-291` (`Search` — `COUNT(*)` и постраничный SELECT двумя вызовами из пула чтения); Related: контракт пагинации REST (openapi.yaml), нагрузочная прикидка qa.

Существо: WHERE с коррелированными EXISTS вариантной семантики вычисляется дважды на каждый поиск; Statements разные — при конкурентной записи `total` отвечает одному снимку, страница — другому (несуществующая страница/«съехавший» total). Побочно: отрицательный `Limit` postgres отвергает ошибкой протокола, sqlite молча трактует как «без лимита» — ноги CI расходятся поведением на одном входе.

**Рекомендация:** один запрос с `COUNT(*) OVER()` (оконные функции переносимы: sqlite ≥ 3.25 / postgres); валидировать limit/offset на входе storage доменной ошибкой.

**Решено:** —

### B3. Значения исполнений обходят проверку секций

**Где:** `internal/service/state.go:185-199` (`merge` — секции варианта flatten'ятся без имени секции), `:403-408` (`toCatalogDevice` — `Section: ""` для значений исполнений); `internal/catalog/engine.go:207-212` (`validateValues` — пустая секция пропускает проверку принадлежности).

Существо: для значений типа движок проверяет принадлежность параметра секции группы (`param_wrong_section`), а для значений исполнений секция не передаётся и проверка молча пропускается: параметр группы ratings, положенный в секцию dimensions варианта, принимается и хранится как валидный. Некорректные данные попадают в БД и экспорт — движок валидации не выполняет заявленную роль для секций исполнений.

**Рекомендация:** пронести имя секции в значения варианта (как для типа) и проверять его движком; пин-тест на значение варианта из чужой секции.

**Решено:** —

### B4. Деактивация параметра делает записи с его значениями неотрекаемыми: ломается инвариант «повторный импорт того же файла — Skipped»

**Где:** `internal/service/devices.go:148-155` (`applyUpsert` — `sameState` проверяется после валидации слитого состояния), `internal/catalog/engine.go:113-116, 197-201` (`validateAttributes`/`validateValues` — неактивные параметры/атрибуты отвергают значения); инвариант — AGENTS.md: «Повторный импорт того же файла — исход `Skipped` по всем записям: без записи в БД и без инкремента ревизий»; деактивация — поддерживаемый путь эволюции каталога (`is_active=0`).

Существо: валидация выполняется над слитым состоянием, включающим незатронутые секции. После деактивации параметра, на который ссылаются существующие значения записи, любой upsert этой записи (включая побайтовый повторный импорт файла, обязанный дать `Skipped`) отвергается целиком — запись нельзя ни обновить, ни даже «прогнать повторно» без ручного выпиливания значений. Заявленный инвариант AGENTS нарушен для целого класса эволюции каталога.

**Рекомендация:** понижать до предупреждения валидацию значений из нетронутых секций upsert (сравнивать структуру записи до/после) либо разрешить повторный импорт как `Skipped` до валидации неактивных ссылок; как минимум — зафиксировать ограничение в плане 04 и тестом.

**Решено:** —

### B5. Недетерминированный выбор ошибки валидации: `probs[0]` при map-порядке `groupValues`

**Где:** `internal/service/state.go:394-402` (`toCatalogDevice` — сбор `d.Values` итерацией `for g, vals := range st.groupValues`: карта → случайный порядок), `internal/service/devices.go:151-155` (`applyUpsert` возвращает `probs[0].Err()`).

### B6. Батч-чтения по списку id без чанкования и задокументированного лимита

**Где:** `internal/storage/db.go:241-253` (`inList` — один плейсхолдер на id), `internal/storage/devices.go:389-409 … 641-668` (`FindDevicesByIDs`…`LoadBacklinksByIDs`).

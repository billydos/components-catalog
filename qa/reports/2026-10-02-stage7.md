производительности (`plan/05-work-plan.md` этап 7.1). Регламент и формат —

- Локальная рабочая станция: Linux x86-64, Go 1.25 (go.mod), SQLite

  каждым прогоном (`go test ./...`).

## Нагрузочная прикидка (`qa/load_test.go`, SQLite)

Датасет: синтетические транзисторы JEDEC (`2N####` + суффиксы), по записи —
2 параметра с условиями измерения, 2 предельных, 1 массогабаритный,
2 атрибута; импорт боевым путём (NDJSON → importer → валидация → upsert;
транзакция на запись). Медиана 10 прогонов после 3 разогревочных.

Разбор превышений (риск R2): фильтрованный поиск в EAV выполняется
коррелированными EXISTS по `device_designation_fields` /
`device_attribute_values` / `parameter_values` на каждую строку `devices`;
`EXPLAIN QUERY PLAN` показывает `SCAN d` + коррелированные подзапросы —
ведущее множество (устройства) фильтрами не сокращается, стоимость растёт
линейно по устройствам при любом селективе фильтра. `ANALYZE` план не
меняет. Ориентир «поиск с фильтрами ≤ 100 мс» на SQLite при 10⁵ не
выполняется (превышение в 2–9 раз); подстрока, карточки, suggest — в норме.

## Выводы

- Полный контур «импорт → хранение → поиск → карточка → REST» зелёный на
  обеих СУБД (критерии v0.1); карточки и подстрочный поиск укладываются
  в ориентиры во всём диапазоне 10⁴–10⁵.
- На 10⁵ SQLite фильтрованный поиск (EXISTS по EAV) превышает ориентир
  100 мс — материал для плана Б риска R2 (денормализация/материализация
  вынесенных фильтров без смены публичного API), отложенного за пределы
  v0.1 решением плана; в v0.1 зафиксировано ограничение: при 10⁵ и выше
  параметрические фильтры на SQLite выполняются секунды, не миллисекунды.
- Импорт идёт с транзакцией на запись (контракт атомарности записи):
  ~500 записей/с на локальном файле SQLite; массовое наполнение 10⁵
  занимает ~3.5 минуты — приемлемо для справочника, при росте объёмов
  возможна пакетная транзакция на файл как отдельная оптимизация.

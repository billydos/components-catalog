# qa — кроссплатформенные прогоны QA

Прогон целиком на Go — без sh/cmd/bat (внешние команды — только `go`,
`gofmt`, `git` для коммита в отчёте и собранные бинарники проекта);
работает на Linux, macOS, Windows, железо и окружение определяет сам.

## Состав

| Файл | Назначение |
|------|-----------|
| `runner/` | Прогонщик: фазы environment → build → static → сценарии CLI/REST по ногам → load; структурный отчёт `qa-log/1` в `qa/reports/*.log`; код выхода 0 — все проверки зелёные |
| `restsrv/` | Минимальный хост REST `/api/v1` для прогонов (модуль серверов не запускает — план 04 §5); поднимается прогонщиком на свободном порту |
| `load_test.go` | Нагрузочная прикидка: генерация NDJSON-датасета синтетических транзисторов JEDEC, импорт боевым путём, измерения поиска/карточки/suggest против ориентиров; запускается прогонщиком (`-scale`) либо напрямую `go test` |
| `reports/` | Авто-отчёты прогонов `qa-*.log` (формат ниже; коммитятся как свидетельство прогонов) и аналитические отчёты `*.md` |

## Запуск

```
go run ./qa/runner                                        # SQLite
CATALOG_TEST_POSTGRES_DSN=postgres://… go run ./qa/runner # + PostgreSQL
go run ./qa/runner -scale 10000                           # + нагрузочная прикидка
go run ./qa/runner -report qa/reports/x.log -keep         # свой отчёт, не удалять временный каталог
```

Ключи: `-report` (путь файла отчёта; по умолчанию
`qa/reports/qa-<дата>-<goos>-<goarch>.log`), `-postgres-dsn`
(DSN PostgreSQL; по умолчанию `CATALOG_TEST_POSTGRES_DSN`, пусто — нога
опущена), `-reset-postgres`, `-scale` (по умолчанию
`CATALOG_QA_SCALE`; 0 — фаза опущена), `-keep`.

Сброс PostgreSQL деструктивен (DROP таблиц модуля) и ограждён: база из
env-конвенции `CATALOG_TEST_POSTGRES_DSN` — одноразовая по регламенту
(`internal/testutil` чистит её каждым `go test`) и сбрасывается
автоматически; база из флага `-postgres-dsn` — произвольная, сбрасывается
только с явным `-reset-postgres`, без него нога идёт по текущему
состоянию базы (грязная база падает на абсолютных проверках видимым
образом — безопасный отказ вместо разрушения данных). Список таблиц —
`storage.TableNames()`, выводится из DDL хранилища.

Код выхода: 0 — PASS, 1 — есть отказы проверок, 2 — прогон не начат
(не найден корень модуля, не открыт отчёт).

CI (`.github/workflows/ci.yml`): Linux-нога со службой PostgreSQL 16
и прикидкой 10⁴, Windows-нога на SQLite — кроссплатформенность
проверяется каждым пушем; авто-отчёты выгружаются артефактами сборки.

## Фазы прогона

1. **environment** — железо и окружение (см. ниже).
2. **build** — сборка `catalogctl` и `qa/restsrv` во временный каталог.
3. **static** — `go build ./...`, `go vet ./...`, `gofmt -l .` (обязан
   быть пуст), `go test ./...` — полный контур проверки AGENTS.md.
   Отказ фазы не прерывает прогон (итог — в отчёте).
4. **cli / rest по ногам** — SQLite всегда; PostgreSQL при заданном DSN
   (одноразовая база очищается прогонщиком перед ногой по ограждённым
   правилам — см. «Запуск»; абсолютные проверки `count` не зависят от
   остатков прошлых прогонов).
   Сценарии CLI: init, импорт выверенной выборки `data/`, идемпотентность,
   round-trip экспорта (ndjson по классу, yaml полностью), list с
   фильтрами класса/системы/подстроки, info (карточка, матрица исполнений),
   find с подсказкой равнозначного по материалу, parse (автодетект, JEDEC,
   негатив), `--dry-run`, каскадное удаление, битый файл, `catalog list`;
   негативные случаи — префикс `Error: ` (канонический en — D9) и код
   выхода 1. Сценарии REST: kinds/catalog/stats, поиск с фильтрами
   и параметрический фильтр, ETag → 304, карточки по ключу и по id,
   POST/PUT/DELETE с кодами 201/409/422/204/404, suggest, неизвестный
   маршрут; HTTP — `net/http`, без внешних инструментов.
5. **load** (при `-scale`/`CATALOG_QA_SCALE`) — нагрузочная прикидка
   боевым `go test ./qa -run TestLoad`; строки измерений (p50, скорость
   импорта) попадают в отчёт заметками.

## Определение железа и окружения

Прогонщик сам определяет платформу и фиксирует её в секции `[environment]`:

- переносимо (stdlib): ОС (`runtime.GOOS`), архитектура, число логических
  ядер, имя хоста, версия Go, модуль и коммит (build info, при
  отсутствии штампов vcs — `git rev-parse`), грязнота рабочего дерева,
  версии драйверов СУБД, версия библиотеки SQLite, версия сервера
  PostgreSQL (при заданном DSN);
- ядро ОС: Linux — `/proc/sys/kernel/osrelease` (uname -r), macOS — XNU
  (`kern.osrelease`), Windows — номер сборки ядра NT (CurrentBuildNumber
  + UBR из реестра);
- Linux: модель CPU (`/proc/cpuinfo`), память (`/proc/meminfo`),
  издание ОС (`/etc/os-release`);
- macOS: sysctl (`machdep.cpu.brand_string`, `hw.memsize`,
  `kern.osproductversion`) через `golang.org/x/sys/unix`;
- Windows: реестр (`ProcessorNameString`, `ProductName`/`DisplayVersion`)
  и `GlobalMemoryStatusEx` (kernel32) через `golang.org/x/sys/windows`.

Внешних зависимостей не добавлено: `golang.org/x/sys` уже был в графе
модуля.

## Формат отчёта qa-log/1

Отчёт — текстовый `.log` с фиксированной грамматикой (парсится
построчно, читается человеком; пишется построчно — прерванный прогон
оставляет частичный отчёт):

```
# components-catalog QA report
format: qa-log/1

[environment]
ключ: значение          # поля окружения и железа

[phase: cli sqlite]
ok   cli/init — init: база инициализирована
FAIL cli/count — count: записи выборки
      | exit=0          # детали — только у отказов
      | 65

[summary]
checks: 50
passed: 50
failed: 0
verdict: PASS
```

- первая строка — маркер отчёта, поле `format: qa-log/1` — версия формата;
- секции — `[environment]`, `[phase: <имя>]`, `[summary]`;
- поля — `ключ: значение`, отсутствующее значение — `—`;
- проверки — `ok   <id> — <описание>` / `FAIL <id> — <описание>`
  (`<id>` — стабильный латинский идентификатор вида `cli/init`,
  `rest/post-create`, `static/gofmt`); детали отказа — строки с отступом,
  начинающиеся с `|`;
- заметки — строки `note  …`;
- итог — `verdict: PASS|FAIL` (FAIL — код выхода 1).

## Ориентиры производительности (docs/plan/04 §5)

- поиск с фильтрами по 10⁴–10⁵ устройств ≤ 100 мс;
- карточка ≤ 20 мс.

Прикидка — измерение, а не порог: медианы печатаются с меткой `ok` /
`ПРЕВЫШЕНИЕ` и фиксируются отчётом. Превышение ориентира — материал для
плана Б по риску R2 (денормализация/материализация вынесенных фильтров
без смены публичного API), а не автоматический отказ прогона; отказ —
только строгий режим (`CATALOG_QA_STRICT=1`, превышение на порядок) либо
ошибки корректности (отказы импорта).

Переменные прикидки: `CATALOG_QA_SCALE` (число записей),
`CATALOG_QA_DIALECT` (sqlite по умолчанию), `CATALOG_QA_DB` (путь файла
sqlite), `CATALOG_QA_STRICT=1`. Масштаб 10⁵ — ручной прогон по мере
надобности (в аналитический отчёт).

# Коммиты git (git-commits)

Сообщения коммитов — на английском, формат Conventional Commits. Заголовок пишется вручную по диффу, а не копируется из вывода команд.

## Заголовок

```
type(scope): short imperative summary
```

- Описание — английский императив, со строчной буквы, без точки в конце: `add`, `fix`, `support`, не `added`/`fixes`.
- Длина до 50 символов — цель, 72 — жёсткий потолок (вместе с `type(scope): `).
- Ломающее изменение — `!` после type/scope (`feat!:` или `feat(storage)!:`) и обязательная строка `BREAKING CHANGE: ...` в подвале.

### type — характер изменения

| type | когда |
|---|---|
| `feat` | новая функциональность (команда CLI, код параметра в каталоге, новый формат импорта) |
| `fix` | исправление ошибки (неудачный разбор, неверная валидация, дефект SQL) |
| `docs` | только документация (README, AGENTS.md, SKILL.md) |
| `refactor` | перестройка кода без изменения поведения |
| `test` | только тесты |
| `perf` | ускорение без изменения поведения |
| `build` | go.mod / go.sum, сборочная обвязка |
| `ci` | конфигурации CI |
| `style` | только форматирование (gofmt), пробелы, переносы |
| `chore` | обслуживание: данные, служебные файлы, скрипты |
| `revert` | откат предыдущего коммита |

### scope — слой репозитория по путям диффа

| пути | scope |
|---|---|
| `internal/domain/**` | `domain` |
| `internal/storage/**` | `storage` |
| `internal/importer/**` | `importer` |
| `internal/cli/**`, `cmd/**` | `cli` |
| `README.md`, `*.md`, `AGENTS.md` | `docs` |
| `.kilo/skills/**` | `skill` |
| `data/**` | `data` |
| прочее (`go.mod`, корень) | scope опустить |

Затронуто несколько слоёв — берётся доминирующий; нет доминирующего — scope опускается. Один коммит с четырьмя scope — сигнал, что изменение не атомарно.

## Тело

- Отвечает «что и почему», а не «как»: «как» видно из диффа.
- Перенос ~72 символа, абзацы разделять пустой строкой.
- Обязательно, когда: меняется контракт (в этом проекте тексты русских сообщений валидации и вывода — часть контракта, см. AGENTS.md), изменяется схема БД / DDL, причина нетривиальна (обход особенности СУБД, обновление зависимости), затронуто несколько слоёв.
- Подвал (после пустой строки): `BREAKING CHANGE: описание`, `Closes #N`, `Co-authored-by: Name <email>`.

## Правила построения

1. **Атомарность** — одно логическое изменение на коммит: код + его тесты вместе; рефакторинг отдельно от изменения поведения; правка линтера (`style`) отдельно от `feat`/`fix`; документация отдельно, если она не является частью изменения.
2. **Staged — осознанно**: stage конкретными путями (`git add internal/domain/parameters.go`), перед коммитом просмотреть `git diff --cached`; не пользоваться вслепую `git add -A`.
3. **Не коммитить никогда**: секреты и ключи, `transistors.db` (генерируется импортом), временные и служебные файлы. `data/*.jsonc` — коммитится.
4. **Коммит — только по явной просьбе пользователя**; сообщения черновиком не предлагать без запроса.
5. Не amend/force-push опубликованные коммиты, не переписывать историю без явного запроса; merge- и revert-коммиты не переформулировать (у revert в заголовке — хеш отбрасываемого коммита).
6. Пустые коммиты не создавать; упавший хук — починить причину и закоммитить заново, не `--no-verify`.

## Порядок составления

1. `git status`, `git diff`, `git diff --cached`, `git log --oneline -10` (стиль и контекст).
2. По характеру изменения выбрать `type`, по путям — `scope`, сформулировать заголовок.
3. Определить, нужно ли тело (критерии выше), написать при необходимости.
4. Проверки (см. чеклист), stage нужных файлов, коммит.

## Чеклист перед `git commit`

- [ ] `go build ./...`, `go vet ./...` — без ошибок; `gofmt -l .` — пусто.
- [ ] Правились пакеты `internal/` — `go test ./...` зелёные.
- [ ] `git diff --cached` просмотрен: в коммите только задуманное, нет `transistors.db` и мусора.
- [ ] Заголовок: английский императив, ≤ 50 (потолок 72), без точки.
- [ ] `type` и `scope` соответствуют таблицам.

Многострочное сообщение — несколькими `-m` (переносимо между оболочками):

```
git commit -m "feat(importer): accept yaml data files" -m "Map .yaml/.yml to the same section tree as jsonc. Validation and ordered-key semantics are shared with the jsonc reader."
```

## Примеры

Хорошие:

```
feat(domain): add Pnorm parameter to catalog
fix(cli): reject find without argument as UserError
refactor(storage): extract dialect DDL composition
docs(skill): document yaml import in SKILL.md
chore(data): extend verified dataset with KT315 variants
feat(storage)!: drop composite key for manufacturers

Add surrogate id for manufacturers and rewire FKs.

BREAKING CHANGE: schema re-created by re-import; working db is disposable during development.
```

Плохие:

```
fix: fix parser bug              — тип дублирует глагол, нет scope, «bug» ни о чём
update files                     — не императив, не видно что изменилось
Feat(Domain): Added parameter.   — заглавные, прошедшее время, точка
```

## Особые случаи

- **Частично staged** (`git add -p`): сообщение описывает только staged-часть; про unstaged-остаток — отдельный коммит.
- **Одинаковые правки в двух местах контракта** (валидатор домена + CHECK в sqlite.go): это один коммит — правило двойной синхронизации из AGENTS.md запрещает коммитить только одну сторону.
- **Генерируемое вместе с исходником** (например, новый код параметра в каталоге и порождённые им CHECK/справка): коммитить вместе, это одно логическое изменение.
- **`fixup`** к только что сделанному коммиту до публикации: допустим отдельный коммит с пометкой `fixup! <заголовок>` либо (по запросу пользователя) amend.

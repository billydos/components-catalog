## Резюме

Общее состояние кодовой базы хорошее: слоистость (SQL не выше `storage`, семантика формата не выходит из `importer`, бизнес-правила не живут в транспортах) и дисциплина ошибок-значений выдержаны, инъекций SQL, утечек `rows`/горутин, паник на пользовательском вводе и обходов транзакционной дисциплины не найдено; build/vet/gofmt/test — зелёные. Выборочно перепроверены исправления CODEREVIEW-01..03 — держатся: positional-перезапись `@имя→$n`, ON CONFLICT-подавление гонок, single-flight кэш, гейты смешанного файла и NDJSON-хвоста, ETag по строке запроса, строгий YAML (не-конечные числа), `WaitDelay` в qa/runner, маскировка DSN. Пин-тесты (состав сида против реестров, маршруты против openapi, паритет бандлов en/ru, плейсхолдеры форматов) — на месте и зелёные.

Новые находки высокого приоритета — обе про «тихое» расхождение «провалидировано ≠ записано/прочитано». Во-первых, метасхема не отвергает дубликаты условий внутри набора, дубликаты enum-значений и классов в списке применимости, а батч-вставки каталога идут с `ON CONFLICT DO NOTHING` — в БД молча остаётся первая строка, тогда как валидация (и последующий контроль файла) видит «гипотетический» вариант; порядок «optional, затем required» реально ослабляет обязательность условия (A1, воспроизведено). Во-вторых, NDJSON-строка `{"sources": <не-массив>}` после корректной строки sources исчезает без единой проблемы — итог зависит от порядка строк, «опечатки не молчат» нарушен (A2, воспроизведено).

Средний приоритет группируется в четыре зоны: (1) целостность применения записей — утечка транзакции записи на ошибочных путях `applyUpsert`/`writeUpsert` (на встраивании с SQLite первая же ошибка посреди записи навсегда блокирует единственное соединение записи — B1), дубликаты id в батч-чтениях дублируют дочерние строки и условия в карточках публичного `GetByIDs` (B2), уникальность синонимов D11 не подкреплена ограничением БД — гонка check-then-insert на postgres (B3); (2) контракты входа/выхода — bool-атрибутный фильтр молча даёт пустой результат через Go API (B4), неразрешимый аналог в теле даёт 404 вместо 422 (B5), повторный `catalog import` не идемпототенен — ревизия дрейфует на пустых применениях (B6), экспорт теряет источники без ссылок (B7), dry-run оптимистичен к записям, которые реальный прогон отвергнет (B8), класс с кодом `source` неотличим от корневой секции `sources` (B9); (3) REST — ETag не различает локали и не отдаёт `Vary: Accept-Language` (B10), отчёт импорта теряет `sources_applied` (B11), `suggest`/`parse` молча игнорируют посторонние ключи запроса (B12); (4) прочие заявленные свойства — «события+ревизия одним снимком» не выполняется на postgres READ COMMITTED (B13), `ParseDesignationCandidates` нарушает обещанную эквивалентность с основным разбором при подсказке kind (B14), тихая порча subclass у jis/pro при рассинхронизации словаря (B15), «задать равным fixed_value» невыполнимо для нулевых констант при позитивном условии — план и движок расходятся (B16), env-DSN не регистрируется секретом qa-отчёта при явном флаге (B17). Низкий приоритет — 31 находка: производительность (отсутствие индекса по `devices(designation)` для any-kind find и автодополнения, двойной проход экспорта), диагностика (пустой файл — три исхода, «неизвестный ключ» вместо неверного типа), гигиена (мутация входного среза сервисом, зависимость от коллации СУБД).

Проверено и чисто: переносимость DML и плейсхолдеры, транзакционная дисциплина (кроме отмеченных), кэш снимка и race-безопасность, семантика секций upsert (замена целиком, `[]`-очистка, частичное применение исключено), идемпотентность записей (`Skipped` без инкремента ревизий, включая случай деактивации параметра — регресс CR-03 B4 не воспроизводится), круглый цикл импорт→экспорт→импорт по всем трём форматам на данных `data/` (82 записи — байтово идентичный повторный экспорт), полнота бандлов (351=351 отображаемых, паритет плейсхолдеров en/ru на всех 218 точках `NewErrorf`), состав сида против фиксированного списка единиц и реестров domain (включая новые словари part2). За рамками: нога PostgreSQL локально (нет службы; сужено по отчётам CI), нагрузочная прикидка `CATALOG_QA_SCALE`, содержательный аудит предметных данных `data/` и текстов плана.

## A. Находки высокого приоритета

### A1. Дубликаты в наборах условий/enum-значениях проходят валидацию, но молча теряются при записи — записанный каталог ≠ провалидированный

**Где:** `internal/catalog/metaschema.go:39-101` (`validateInputSelf`), `internal/storage/catalog_write.go:165-199` (`WriteCatalog`, вставки наборов и enum), `internal/storage/db.go:368-373` (`withOnConflict` — `insertMulti` подавляет конфликт PK); заявка контракта — `internal/service/search.go:38-39` («Записываются те же строки, что валидировались»).

`validateInputSelf` проверяет дубликаты кодов строк разделов (`checkCodes`), но не дубликаты условий внутри одного набора (`ConditionSets[j].Items` — проверяется только `Mode.Valid()`, metaschema.go:77-84), не дубликаты enum-значений и не дубликаты классов в списках применимости. Батч-вставки наборов/элементов/enum идут с `ON CONFLICT DO NOTHING`: вторая строка конфликта PK молча отбрасывается (побеждает первая). Валидация записей импорт-файла идёт по «гипотетическому» снимку из `ApplyCatalog` (вход целиком), а в БД попадает урезанный вариант — контроль при импорте и контроль после импорта расходятся. Путь достижим из файла: читатель секции каталога дубликаты условий в наборе и enum-значения не отсекает.

Воспроизведено (эксперимент на копии, SQLite): вход с параметром, у которого набор №1 содержит `freq required` + `freq optional`, и `enum_values: ["A","A"]` → `ApplyCatalog problems: 0`, `WriteCatalog err: nil`; в БД по каждому ключу остаётся только первая строка. При порядке «optional, затем required» валидатор счёл условие обязательным, БД хранит `optional` — ослабление семантики без единой проблемы в отчёте.

**Рекомендация:** расширить `validateInputSelf`: дубликат условия в наборе, дубликат enum-значения, дубликат класса в `kinds` — `metaProblem` с новыми MsgID (константа + форматы en/ru + тест полноты одним изменением); закрепить тестом инвариант «валидированное = записанное» (применить вход с дубликатами — ожидается отказ).

**Решено:** да — `validateInputSelf` отвергает повторы в подсписках строки каталога: дубликат условия одного набора (`meta_cond_set_dup`), дубликат номера набора условий (`meta_cond_set_number_dup` — остаток, найденный независимым аудитом фикса: дубликат `set_no` проходил валидацию и урезался при записи — второй набор отбрасывался по PK, его элементы сливались в первый; из файла unreachable — нумерация по позиции, достижимо из Go API фасада), дубликат enum-значения параметра/атрибута (`meta_param_enum_dup`/`meta_attr_enum_dup`), дубликат класса применимости (`meta_param_kind_dup`/`meta_attr_kind_dup`); константы + форматы en/ru + реестр `msgRegistry` одним изменением. Проблемы самопроверки отсекают и перенос входа в снимок, и запись — в БД не попадает урезанный вариант «первой строки» ON CONFLICT; покрыты все 14 батч-вставок `WriteCatalog` с ON CONFLICT. Тесты: кейсы таблиц `TestMetaschemaViolations`/`TestMetaschemaAttributeViolations` (дословные сообщения), `TestApplyCatalogRejectsSublistDuplicates` (все четыре повтора одной строкой → отказ целиком, снимок не тронут) и `TestApplyCatalogAllowsDistinctSublists` (легитимные входы не отвергаются: одно условие в разных наборах, одно enum-значение у разных параметров, класс без коллизии секции); воспроизведено CLI (дубликаты условий набора + enum — `Problem` × 2, exit 1). План 03 §12 дополнен инвариантом повторов.

### A2. NDJSON: строка `{"sources": <не-массив>}` после корректной строки sources молча теряется

**Где:** `internal/importer/importer.go:279-284` (ветка sources проверяет только `kindNull`), `importer.go:346-362` (`mergeSourceItems` конкатенирует `v.items` без проверки формы); контраст — `mergeCatalogTrees` (importer.go:383-386), который форму каталога проверяет.

Ветка sources принимает строку с единственным ключом `sources`, не равным `null`, и добавляет значение в `srcItems` без проверки, что это массив. У не-массива (объект — данные в `members`, число/строка — пусто) `items` пуст, и `mergeSourceItems` конкатенирует ничего: содержимое строки исчезает без проблемы в `Report` и без счётчика. Одиночная такая строка даёт ошибку `sources_array` (форма проверяется на слитном дереве из одного элемента), т.е. итог зависит от порядка строк — «опечатки не молчат» нарушен ровно там, где это заявлено моделью Issues.

Воспроизведено (CLI, SQLite): файл из `{"sources": [{"code":"ref1",…}]}` + `{"sources": 42}` (и вариант с объектом `{"sources": {"code":"ref2",…}}`) + `{"transistors": {"name": "КТ315"}}` → «записей: 1, добавлено: 1 … источники обновлены», exit 0, проблем нет.

**Рекомендация:** при чтении строки-обёртки проверять `srcVal.kind` (не массив и не null → проблема строки + `sourcesTainted`) по образцу `mergeCatalogTrees`; тесты на обе формы не-массива в первой и последующих строках.

**Решено:** да — ветка sources `importNDJSON` проверяет форму значения каждой строки: null — секция не задана, массив — сливается, прочее (число, строка, объект, логическое значение) — проблема строки с номером (`MsgImportSourcesArray`, переиспользован) + `sourcesTainted`: блок источников не применяется, позднейшая чистая строка блок не реабилитирует (семантика как у строк catalog), итог не зависит от порядка строк; гейт catalogOnly видит испорченную строку как присутствие секции. Тест `NDJSONSourcesNonArrayValue` (все формы не-массива — число, объект, логическое значение — × первая/последующая строка: дословный текст с номером строки, реестр не применён, ссылка записи — unknown_source); воспроизведено CLI (число, объект и bool — `Problem`, exit 1). Вместе с этим закрыты C14 и C15 (та же зона — вход sources): `ReadSourcesSection` накапливает проблемы всех определений вместо fail-fast на первом (Issues-модель; тест `AllDefProblemsAccumulated` — дефектные №1/№3 и валидное №2: полный список, реестр не применяется вовсе; дополнено вторым аудитом — проблемы формы не маскируют проблемы значений: `planSources` валидирует прочитанные определения сервисом и накопляет обе категории вместе, тест `FormAndValueProblemsAccumulated`), известное каталогу условие с неверным типом значения (`"Ta": "25"`/`null`) получает отдельное сообщение `import_value_condition_number` (константа + форматы en/ru + реестр одним изменением) вместо вводящего в заблуждение «неизвестный ключ»; тест `TestReadDocumentConditionValueType` (строка/null у известного условия — новый дословный текст, неизвестный ключ — прежний). План формата дополнен: fill-format §9 (не-массивное значение строки sources) и две строки в таблице §12.

## B. Находки среднего приоритета

### B1. Утечка транзакции записи на ошибочных путях applyUpsert/writeUpsert

**Где:** `internal/service/devices.go:208-214` (`applyUpsert`, фаза записи), `devices.go:342-404` (`writeUpsert` — каждый `return err` без отката); контраст — соседние `Delete`, `CatalogService.Import`, `SourceService.Apply` имеют `defer tx.Rollback()`.

Пути чтения и дрейфа откатываются явно (devices.go:181, 187, 191, 204), а пути после строки 208 — нет: ошибка `skippedOrValidatedCommit` и любой `return err` внутри `writeUpsert` (включая гонку createOnly на 359-364 — `return` после `InsertDevice` без отката) покидают функцию с открытой транзакцией. `sql.Tx` не освобождает соединение сам (только отмена контекста). На SQLite пул записи — одно соединение (`sqlite.go` `SetMaxOpenConns(1)`): с долгоживущим контекстом (штатный пример встраивания использует `context.Background()`) первая же ошибка посреди записи навсегда блокирует все последующие записи процесса; на postgres остаётся idle-in-transaction с блокировками строк.

**Рекомендация:** обернуть тело итерации цикла записи в замыкание с `defer tx.Rollback()` (безопасен и после `Commit` — `ErrTxDone`), либо добавить явные откаты в точках возврата: ошибка `skippedOrValidatedCommit`, оба возврата `writeUpsert`, гонка createOnly. Тест: ошибка посреди `writeUpsert` (например, unknown_source) не блокирует следующую запись.

**Решено:** да — тело итерации цикла записи `applyUpsert` обёрнуто в замыкание с `defer tx.Rollback()` (закрывает все выходы: ошибки `readMerged`/`CatalogRevision`, валидации в `skippedOrValidatedCommit`, промежуточные возвраты `writeUpsert`, гонку createOnly, дрейф ревизии, а также ошибку `Commit` при отменённом контексте, которую `sql.Tx` сам не закрывает); обновление кэша снимка при дрейфе выполняется по-прежнему вне соединения записи, контракт закрытия `skippedOrValidatedCommit` зафиксирован комментарием (devices.go). Тест `write phase rollback` (service_test.go): детерминированный сбой посреди применения — FK на параметр из снимка-переопределения, запись не применяется вовсе, следующая запись проходит под ограниченным контекстом; утечку детектируют SQLite-ноги (мутационно подтверждено: без отката — зависание единственного соединения записи).

### B2. Дубликаты id в батч-чтениях дублируют дочерние строки и условия в карточках

**Где:** `internal/storage/db.go:315-326` (`eachIDChunk` — режет список, не множество), `internal/storage/devices.go:606-640, 664-697, 724-796, 966-998` (`loadFieldsByIDs`/`loadAttributesByIDs`/`loadValuesByIDs`/`loadSynonymsByIDs`); публичная точка — `service.DeviceService.GetByIDs` (алиас в `components/service.go`, без валидации дубликатов).

Повторяющийся id во входном списке длиной > 1000 попадает в два чанка; обе порции возвращают строки одного устройства и добавляются повторно. Для `loadValuesByIDs` дублируются не только строки, но и условия: карта `pos` по `parameter_values.id` находит уже созданную запись и повторно аппендит те же `parameter_value_conditions`. Внутренние потребители не попадают (экспорт — пакеты уникальных id; поиск — ≤200), REST закрыт валидацией (`service/search.go:412-415` — дубликат id → 400); встраивание через фасад — нет.

**Рекомендация:** дедуплицировать ids в `eachIDChunk` (или в загрузчиках до чанкования); зафиксировать контракт «список уникален» в докомментариях `Load*ByIDs`/`FindDevicesByIDs`; тест на дубликат id, пересекающий границу чанка.

**Решено:** да — `eachIDChunk` отбрасывает повторяющиеся id (учитывается первое вхождение) до чанкования: все батч-чтения (`internal/storage/devices.go`, `sources.go` — поля, атрибуты, значения с условиями, исполнения и их атрибуты, производители, аналоги/встречные, синонимы, источники, `FindDevicesByIDs`) получают чанки без повторов — повтор id на границе чанка не дублирует строки и условия в слиянии; контракт «повторы игнорируются, первое вхождение» зафиксирован в докомментариях всех `Load*ByIDs`/`FindDevicesByIDs`/`LoadDeviceSourcesByIDs` и `GetByIDs`/`buildCards`; сборка карточек дополнительно дедуплицирует список id (карточка по одному экземпляру, порядок — первое вхождение). Тест `TestBatchReadsDuplicateIDs` (sqlite+postgres): вход длины 1001 с повтором цели на позициях 999/1000 — записи без дубликатов, поля/значения/условия цели по одному набору; сервисный `suiteGetByIDs` дополнен повторами id (карточки без повторов, эквивалентность одиночной карточке).

### B3. Уникальность синонима в классе не подкреплена БД — гонка check-then-insert на PostgreSQL

**Где:** `internal/service/devices.go:676-730` (`resolveSynonyms` — проверки `FindSynonymOwner`/`FindDevice` перед вставкой), `internal/storage/ddl.go:321-328` (`device_synonyms` — только `PRIMARY KEY (device_id, designation)`); инвариант D11 — «синоним уникален в пределах класса и не в тени точного ключа».

Все проверки инварианта — чтения до вставки. При READ COMMITTED два параллельных писателя проходят обе проверки до коммита друг друга и коммитят оба: два владельца одного синонима в классе, либо синоним, скрытый одноимённой записью (UNIQUE(kind, designation) на `devices` не конфликтует с синонимами). `FindSynonymOwner` после этого молча возвращает «первого». На SQLite гонка закрыта одним соединением записи; класс проблемы тот же, что закрытые B6 (CR-01) и C14 (CR-03) — там конфликт гасился `ON CONFLICT`, здесь гасить нечем.

**Рекомендация:** денормализовать `kind_code` в `device_synonyms` + `UNIQUE(kind_code, designation)` (инкремент версии схемы, D5), конфликт маппить в доменную ошибку по образцу `InsertIfAbsentReturningID`; либо сериализовать заявки синонимов (advisory lock по обозначению).

**Решено:** да — оба механизма рекомендации. (1) Уникальность в БД: `device_synonyms.kind_code` (класс владельца, денормализация) + `UNIQUE (kind_code, designation)`, версия схемы 15 (DDL, пин-тест версии, план 02 §2/§3/§5, план 03 §9 — одним изменением); `ReplaceSynonyms` получает класс владельца и вставляет через `InsertIfAbsent` — подавленная вставка (конфликт уникальности с синонимом другой записи класса, чья заявка закоммитилась между проверками сервисного слоя и вставкой) — доменная ошибка `svc_synonym_conflict_other` по перечитыванию владельца в той же транзакции (перечитывание ничего не нашло — внутренняя `storage_reread_missing`, образец `InsertDevice`); транзакция после конфликта остаётся рабочей. (2) Транзитная гонка «создание записи против заявки синонима» (UNIQUE в разных таблицах не конфликтует) закрыта сериализацией: метод диалекта `LockDesignations` (`Tx.LockDesignations`, postgres — `pg_advisory_xact_lock` по хэшу «kind\x1fобозначение» до конца транзакции, ключи сортируются — несколько блокировок не тупикуются; sqlite — no-op, единственное соединение записи), вызывается в фазе записи `applyUpsert` до всех проверок чтением — для обозначения записи и канонических синонимов секции. Тесты: `TestReplaceSynonyms` дополнен (конфликт того же класса — дословная `svc_synonym_conflict_other`, тот же синоним в другом классе допустим, транзакция жива после ошибки); CLI-прогон синонимов (импорт → find по синониму → экспорт → повторный импорт `Skipped`). План 02 §4/§6 дополнены (исключение из подавления конфликтов, сериализация заявок).

### B6. Повторный `catalog import` того же файла не идемпототенен: ревизия и «каталог расширен» каждый раз

**Где:** `internal/service/search.go:44-58` (`Catalog.Import` — безусловные `WriteCatalog` + `BumpCatalogRevision`), `internal/importer/importer.go:431-441` (`CatalogApplied=true` без проверки изменения), `internal/cli/commands.go:557` (печать «каталог расширен»).

В отличие от записей (`Skipped` без движения ревизий) и источников (`sourceEqual` — повтор без `BumpDataRevision`), повторный импорт идентичного каталога переписывает определения, инкрементирует `catalog_revision` и рапортует расширение. ETag каталога дрейфует на пустых применениях, отчёт вводит в заблуждение («расширен» без расширения).

Воспроизведено (CLI): три подряд `catalog import` одного и того же файла — трижды «каталог расширен».

**Рекомендация:** детекция «нет изменений» в `Catalog.Import` (сравнение строк, как `sourceEqual`) — не писать и не двигать ревизию; в отчёте различать «расширен»/«без изменений».

**Решено:** да — `CatalogService.Import` возвращает признак изменения: гипотетический снимок применения (`ApplyCatalog`) сравнивается с текущим новым `catalog.RowsEqual` — разделы и подсписки строки (применимость, enum-значения, элементы наборов условий) сравниваются как множества, поскольку чтение БД упорядочивает строки канонически, применение дописывает новые в конец, а хранение порядок входа не фиксирует (ложных отличий и «залипающих» отличий нет: повторный импорт одного файла стабильно без изменений). Без изменений — без `WriteCatalog`, `BumpCatalogRevision` и инвалидации кэша; сигнатура `(bool, error)` (симметрия `SourceService.Apply`, обновлены сидирование и план 04 §1). Вердикт «нет изменений» перепроверяется свежей `catalog_revision` с единственным контролируемым ретраем по свежему снимку — параллельный писатель между чтением снимка и решением не даёт устаревшего пропуска (образец — записи устройств; дополнение независимого аудита фикса). `commitCatalog` поднимает `CatalogApplied` только при фактическом изменении — CLI больше не печатает «каталог расширен» на пустом применении, REST `catalog_applied` получил семантику «применена с изменением» (описание в openapi обновлено), `catalog_revision`/ETag `/catalog` на повторных импортах стабильны. Тесты: `TestRowsEqual` (переупорядочение разделов/подсписков — равенство; новая/изменённая строка, `fixed_value` и потолок nil≠0 — отличие), повторный импорт в `suiteRevisions` (признак false, ревизия на месте) и importer-сьют `CatalogImportIdempotent` (`catalog import`, `import` и NDJSON со слиянием строк catalog одного файла), CLI `TestCatalogCommands` (повтор — без «catalog extended», положительный путь — файлом расширения). План 02 §5.4 дополнен.

### B10. ETag не различает локали, `Vary: Accept-Language` не отдаётся

**Рекомендация:** на локализуемых ответах (200 и 304) отдавать `Vary: Accept-Language` и/или включать negotiated locale в ETag; зафиксировать в плане 04 §5.

**Решено:** да — оба механизма рекомендации. (1) ETag идентифицирует конкретное представление: negotiated-локаль входит в тег — `catalogETag` → `catalog-<n>-<lang>`, `searchETag` → `data-<n>-<hash>-<lang>` (локаль замкнута реестром бандлов en/ru — формат остаётся валидным opaque-tag RFC 9110; `etagMatch` сравнивает полную строку — суффикс не ломает списки/`W/`/`*`); 304 не пересекается между локалями (ETag чужой локали — 200), синонимы локали («ru» и «ru-RU») дают одно представление и один ETag. (2) `Vary: Accept-Language` — общий хелпер `varyLanguage` (списковое дополнение через `Add` с проверкой вхождения: Vary сайта вроде Accept-Encoding не затирается) — на локализуемых GET-ответах 200 и 304: `/kinds`, `/catalog`, `/components`, `/stats?kind`, обе карточки; нелокализуемые (`/stats` без kind, `/changes`, `/suggest`, `/parse`) Vary не несут. Дополнено независимым аудитом фикса: локализованные error-ответы (текст `message` — каталог по локали, в том числе эвристически кэшируемые 404/405 — RFC 9111) тоже несут Vary — общий путь ошибок `writeError`/`writeDomainErr`/`writeErr`; POST/PUT/import без Vary — ответы не-GET/HEAD без явной информации свежести конформный кэш не хранит. Контракты одним изменением: openapi — заголовки Vary (переиспользуемый `components/headers/VaryLanguage`, включая все переиспользуемые error-ответы и inline-404 гонки удаления), описания ETag с локалью, параметр Accept-Language документирован у карточки по id и POST-создания; план 01 §3 и план 04 §2 (абзац локализации, строки `/catalog` и `/components`) + §5 (кэширование). Тесты: `TestETagLocale` — ETag различает локали, та же локаль — 304 с Vary, ETag чужой локали — 200, синоним локали — 304, Vary на 200/304 локализуемых, отсутствие на нелокализуемых, Vary error-ответов (404 карточки, 400 постороннего ключа `/changes`). Аудит также поймал случайное выпадение 405 из спецификации `/kinds` в черновике — возвращено; QA-прогон (sqlite, scale 0) — PASS.

### B13. «События и ревизия одним снимком» не выполняется на PostgreSQL

**Где:** `internal/storage/change_events.go:67-71,100` (`LoadChangeEvents`), `internal/storage/db.go:163-169` (`BeginReadOnly` — уровень по умолчанию); контраст — `LoadSnapshot` задаёт REPEATABLE READ явно (`catalog_read.go:21`).

Комментарий и `ChangesPage` (service/changes.go:40-45) обещают страницу событий и ревизию из одного снимка, но `BeginReadOnly` открывает транзакцию с уровнем по умолчанию — на postgres это READ COMMITTED, где каждый оператор получает свой снапшот: фикс между двумя SELECT даст ревизию, опережающую страницу событий. **Решено:** да — контракт читающих транзакций пула чтения — «снимок»: `BeginReadOnly` задаёт `sql.LevelRepeatableRead` (как `LoadSnapshot`; sqlite-драйвер уровень игнорирует — WAL-чтение и так держит стабильный снимок) — страница событий и `data_revision` в `LoadChangeEvents` идут одним снимком на postgres, а заодно закреплено смежное обещание `buildCards` («один снимок данных — карточка без смешанного состояния», прежде на READ COMMITTED не обеспеченное) и все прочие составные чтения пула чтения (фаза чтения upsert, dry-run, статистика). Тест `TestBeginReadOnlySnapshotIsolation` (postgres-нога): `current_setting('transaction_isolation')` внутри `BeginReadOnly` — `repeatable read`. План 02 §2.3 (чтение фида одним снимком) и §4 (таблица диалектов — транзакции чтения REPEATABLE READ postgres) дополнены.

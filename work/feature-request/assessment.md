## Детальный разбор

### CC-1. Эндпоинт разбора обозначения — низкая

Текущее состояние: сервисные методы `Designations.Parse` / `ParseForSystem` / `Suggest` уже существуют (`internal/service/parse.go`), их использует CLI `catalogctl parse`. REST-маршрута разбора нет.

Работа: маршрут в таблице `routes` (`internal/httpapi/api.go`), хендлер, JSON-модель (`wire.go`), `api/openapi.yaml`, тесты, `docs/plan/04-module-functionality.md` §2. Сервисный слой готов полностью.

Единственная дизайн-задача — «конфиденс». Парсер строгий (детерминированные грамматики, фиксированный порядок автодетекта — `internal/domain/designation.go`, `autodetect`), числовой уверенности нет и ввести её честно нельзя. Эквивалент по UX: возвращать список всех систем, принявших обозначение (кандидатов), — небольшое расширение `domain.ParseDesignation`. Fallback из запроса (suggest + ручной выбор) уже покрыт существующим `GET /api/v1/suggest`.

Оценка: ~1 день с тестами и openapi.

### CC-2. Change feed / хуки изменений — средняя–высокая

Текущее состояние: инкрементальных событий нет вовсе; есть только монотонный счётчик `data_revision` в `schema_meta` (`internal/storage/meta.go`), инкрементируемый в транзакциях записи (`internal/service/devices.go`, `BumpDataRevision` в Upsert/Delete). Сайт сегодня видит только факт «данные изменились» через `/stats`.

Работа:

- новая таблица событий (ревизия, операция created/updated/deleted, kind, designation, id) — изменение DDL, инкремент `SchemaVersion` (сейчас 8) с пересозданием базы импортом (D5; выверенное наполнение в `data/` делает это приемлемым);
- запись событий в тех же транзакциях записи, что и `BumpDataRevision` — все пути: `Create`/`Upsert`/`Delete` сервисного слоя, включая компенсационные удаления импортёра (`internal/importer/importer.go`, `recordIssue` — уже сегодня шумят в `data_revision`);
- `GET /api/v1/changes?since=<revision>&limit=`: storage-запрос, сервисный метод, хендлер, openapi;
- политика ретенции/очистки событий;
- правка планов `02-database.md` (новая таблица + версия схемы) и `04-module-functionality.md` — осознанное изменение, по правилам AGENTS.md отдельным коммитом со всеми связанными местами.

Замечание по варианту «callback-хук OnChange в Go API»: значительно дешевле (без DDL), но не закрывает заявленный в запросе сценарий записи в обход сайт-обёртки (`catalogctl` напрямую в ту же базу) — событие в процессе сайта не возникнет. Раз нужен именно этот случай, правильный дизайн — таблица событий в БД; колбэк можно дать дополнительно как удобство для встраивания.

Оценка: 3–5 дней + прогон QA-матрицы (linux/SQLite, linux/PostgreSQL, windows/SQLite).

### CC-5. Диапазоны значений параметров для фильтров — низкая

Переносимый агрегатный запрос `GROUP BY parameter_code` с `MIN/MAX` по `parameter_values × devices` (фильтр классом); индексы `idx_pv_code_*` уже покрывают доступ; частоты enum — `GROUP BY value_text`. Новый метод storage, сервисный метод, экспозиция в `/stats?kind=`, openapi, тесты.

Дизайн-решение одно: конвенция min/max при смешанных формах значений — брать ту же семантику, что у параметрических фильтров поиска (`paramCondSQL` в `internal/storage/search.go`: границы учитывают и `value_min/value_max`, и `value_exact`).

Оценка: ~1 день.

### CC-6. Импорт больших файлов стримингом — низкая–средняя

Текущее состояние: Go API уже стриминговый — `importer.Importer.Import(ctx, io.Reader, name, dryRun)` читает NDJSON построчно без загрузки файла целиком (`internal/importer/ndjson.go`), отчёт — аккумулятор Issues. Записи буферизуются до конца файла ради семантики «всё-или-ничего» на синтаксисе — при 10⁴–10⁵ записей это структуры, а не сырые байты, память приемлема. Прогресс-колбэк в Go API — небольшое расширение сигнатуры (option).

Отсутствует REST-путь импорта: маршрутов импорта в `/api/v1` нет. Основная работа — `POST /api/v1/import` (NDJSON-тело, стриминговое чтение без `http.MaxBytesReader` с лимитом одной записи `maxBodyBytes`; лимит целесообразно заменить на лимит строки сканера, уже 16 МиБ), синхронный ответ отчётом после EOF; прогресс по REST — только polling/SSE (отдельное удорожание, в запросе не обязателен). Семантика частичных отказов (Issues) готова.

Оценка: 2–3 дня REST + тесты; Fallback с партиями по 2000 записей после появления эндпоинта не нужен.

### CC-8. Фильтр по набору id в GET /components — низкая

Сценарий F12 — составной поиск «FTS сайта × параметрика модуля» без дублирования данных каталога на сайте: сайт отбирает по релевантности ≤ 200 id и передаёт модулю вместе с остальными фильтрами (07). Предложение — повторяемый параметр `id` (до 200 значений), семантика — пересечение с прочими фильтрами; сортировка — существующий `sort`, без него — порядок передачи id. 200 id ≈ 4–5 КиБ строки запроса — в пределах типовых лимитов; выдача укладывается в действующий потолок `limit` 200.

Семантика пересечения ложится на существующий конструктор WHERE: `buildSearchWhere` объединяет условия через AND (`internal/storage/search.go`) — добавляется `d.id IN (...)` именованными аргументами самого конструктора WHERE (схема имён — как у хелпера `inList`, `internal/storage/db.go`; мутация чужой map аргументов хелпером туда не подходит); 200 аргументов далеки от пределов драйверов, `maxInList`-чанкование не требуется. Total (`COUNT(*) OVER()`) и пагинация работают без изменений. Дырки в наборе (id без записи либо отсечённые прочими фильтрами) — просто отсутствие строки в выдаче, отдельной ошибки не нужно.

Работа: `IDs []int64` в `SearchQuery`/`SearchRequest` + валидация в `buildSearchRequest` (потолок 200, положительные int64, дубликат в наборе — 400 либо дедупликация), разбор повторяемого `id` в `parseSearchQuery`, `api/openapi.yaml`, `docs/plan/04-module-functionality.md` §1.1/§2, тесты на обеих СУБД. Без DDL и инкремента версии схемы.

Дизайн-задачи две:

- повторяемый параметр — исключение из действующей строгости разбора: `rejectDuplicateParams` (`internal/httpapi/query.go`) сегодня отвергает любой повтор (?q=a&q=b → 400), `id` станет первым намеренно повторяемым параметром контракта; альтернатива без исключения — одна строка со списком `id=1,2,3`, но повторяемую форму генерировать из FTS-выдачи проще;
- порядок «без sort — порядок передачи id» — новый режим сортировки: переносимый `ORDER BY CASE d.id WHEN @id0 THEN 0 … END` первым ключом в `orderJoinClause`, пока `sort` не задан; обязательный финальный ключ (kind, designation) не мешает — id уникальны.

Fallback заявки (FTS — отдельный режим поиска, фильтр только kind из fts_docs, без комбинации с par./attr.) от модуля не требует ничего: сайт ищет по своему индексу сам, карточки достаются готовым `GET /api/v1/components/{id}`.

Оценка: ~1 день.

### CC-9. Публичный фасад Go-библиотеки — низкая

Текущее состояние: весь Go API модуля лежит в `internal/` — `service.Open` (`internal/service/app.go`), `httpapi.New` (`internal/httpapi/api.go`), `Importer.Import` (`internal/importer/importer.go`) — внешний модуль импортировать их не может (запрет компилятора Go на пакеты `internal/`). Публичные пакеты корня — только `seed` и `qa`, API поверх них не открывается. Пример встраивания из README (раздел «Встраивание (Go API)»: `service.Open`, `httpapi.New`) у потребителя не компилируется. In-process встраивание заблокировано целиком, включая Go-API-импорт с прогрессом из CC-6: прогресс-колбэк расширяет сигнатуру `Importer.Import` — тоже internal.

Фасад зафиксирован планом самого модуля и не реализован: `docs/plan/01-architecture.md` §2.4 («Публичный фасад пакета для встраивания: `components.Open(ctx, cfg) (*App, error)` + `App.Close()`; `App.Services`, `App.Handler()`») и `docs/plan/04-module-functionality.md` §1 (эскиз использования). Реализация догоняет план — новое решение не принимается, правка плановых документов не нужна.

Работа: корневой пакет `components` — тонкий реэкспорт внутренних пакетов без перестройки слоёв: `Open`/`Close`/`Services` поверх `internal/service`, `Handler()` поверх `internal/httpapi` (по плану `Handler` — метод фасадного `App`, объединяющий обе точки; сейчас `Handler()` живёт на `httpapi.API`). Примеры README и контрактные тесты модуля переводятся на фасад: компилируемость у потребителя — часть контракта, а внутримодульные тесты internal-импорты разрешают и подлинности не доказывают — нужна нога «внешний потребитель»: пример-модуль с `replace` на локальный путь, собираемый QA-прогоном. Без DDL и инкремента версии схемы.

Fallback: отсутствует. `replace` на форк с патчем допустим только в dev-ветках сайт-проекта (Версионирование — документ сайт-проекта); out-of-process REST-хост по образцу `qa/restsrv` — смена интеграционной модели (02), а не fallback: сам `restsrv` — dev-заглушка только для QA (модуль по построению не запускает серверов).

Оценка: ~1 день (фасад + README + контрактный потребитель в QA).

### CC-11. Словари значений полей обозначения в снимке GET /catalog — низкая

Текущее состояние: факты заявки подтверждены по коду. Снимок `GET /api/v1/catalog` (wire-модель `catalogSnapshotJSON`, `internal/httpapi/wire.go`) содержит классы, системы, единицы, условия, группы, параметры, атрибуты, правила — словарей значений полей обозначения нет. `/stats?kind=` агрегирует только параметры (`internal/service/stats.go`). Источники словарей неоднородны: материал (`ge`, `si`, `ga`, `in`, `sic`, `gaas`, `other`), подкласс (`bjt`, `fet`, … — 18 кодов) и подстройка (`fixed`, `variable`, `preset`) — константные реестры `internal/domain`; категория — словарь данных (таблица `categories`), расширяемый импортом, причём снимок в памяти уже несёт `Snapshot.Categories` (`internal/catalog/snapshot.go`) — wire-модель их просто не сериализует. Локализованные названия всех четырёх словарей есть в бандлах en/ru (`material.*`, `subclass.*`, `adjustment.*`, `category.*` в `internal/i18n`), вне CLI (`internal/cli/print.go`) не используются. REST `/components` фильтрует по material/subclass/adjustment/category (`canonicalizeFieldCode`, `internal/httpapi/query.go`, принимает и код, и локализованное название); повтор любого параметра, кроме намеренно повторяемого `id` (CC-8), — 400 `validation_failed` (`rejectDuplicateParams`).

Работа:

- секция словарей в снимке: для каждого фильтруемого словарного поля — стабильные коды + отображаемые названия по локали, по образцу KindDef/UnitDef (`i18n.MaterialName`/`SubclassName`/`AdjustmentName`/`CategoryName`; локаль — Accept-Language, как в `handleCatalog`); категория — из `Snapshot.Categories` (расширяемость данными), остальные — из реестров `internal/domain`; кэширование наследуется: ETag `catalog-<catalog_revision>` + 304 и сервисный кэш с перечётом ревизии при каждом доступе уже работают — словари едут в том же снимке;
- мультивыбор словарных фильтров (`material=si&material=ge`, семантика ИЛИ): второй намеренно повторяемый параметр после `id` — расширение `rejectDuplicateParams` и разбора в `parseSearchQuery`; `IN`-список в `buildSearchWhere` (`internal/storage/search.go`) именованными аргументами самого конструктора WHERE — по проторённому пути фильтра `id` (CC-8), `maxInList`-чанкование не требуется (словари конечны);
- `api/openapi.yaml` (новая секция снимка + повторяемые словарные параметры; попутно закрывается существующий пробел — фильтры `adjustment`/`category` в openapi-прозе не упомянуты), `docs/plan/04-module-functionality.md` §2, тесты на обеих СУБД. Без DDL и инкремента версии схемы.

Дизайн-задачи две:

- граница повторяемости: заявка предлагает повторяемость только для словарных полей (конечные стабильные множества значений); повтор составных текстовых полей (letters, family, series…) — отдельное решение, остаётся 400;
- источник истины по составу: для категорий — БД (может расшириться импортом, поэтому только `Snapshot.Categories`, не константы), для material/subclass/adjustment — реестры `internal/domain` с пин-тестом полноты по образцу `seed/seed_test.go`.

Fallback заявки (текстовый ввод кода значения с подсказкой формата) работоспособен уже сегодня: коды стабильны, отражены в `docs/class-keys.md`, фильтр принимает и код, и локализованное название; мультивыбор и счётчики — после реализации.

Оценка: 1–2 дня (снимок ближе к готовности — категории уже грузятся; мультивыбор — повторение пути `id`).

### CC-12. Сортировка по числовым параметрам в GET /components — низкая–средняя

Текущее состояние: факты заявки подтверждены по текущему коду. Допустимые ключи `sort` — только `designation`, `id` и коды полей обозначения (текстовые: material, subclass, letters, prefix, family, series, adjustment, category, base; числовые: assembly, feature, dev_number, modification, chip, junctions, group; `parseSort`, `internal/httpapi/query.go`, дубль проверки в `buildSearchRequest`, `internal/service/search.go`); `sort=-fT` — 400 `validation_failed` (`api_sort_key_unknown`). Каркас сортировки — `orderJoinClause` (`internal/storage/search.go`): `LEFT JOIN device_designation_fields` на каждое ключевое поле (уникальность PK `(device_id, field)` исключает размножение строк), записи без значения — всегда в конце (`CASE WHEN col IS NULL THEN 1 …`), финальный ключ `(kind, designation)` добавляется всегда. Схема заявки (комбинация с существующими ключами, финальный `(kind, designation)`, «без значения — в конце») ложится на готовый каркас без переделки.

Работа: допустимость в `sort` кодов числовых параметров, применимых к классу запроса, — валидация по снимку по образцу параметрических фильтров (`snap.Parameter` + `AppliesTo(kind)` + отсечение текстовых/enum типов; `buildSearchRequest` уже делает это для фильтров `param_*`); сортировочный JOIN — производная таблица по `parameter_values` (производные таблицы разрешены правилами переносимости DML); `api/openapi.yaml`, `docs/plan/04-module-functionality.md` §2, тесты на обеих СУБД. Без DDL и инкремента версии схемы.

Дизайн-задачи две:

- выбор значения у записи: числовое значение разложено в три колонки (`value_exact`/`value_min`/`value_max`); параметрические фильтры уже сводят их вместе (`paramCondSQL`), для сортировки правило за модулем — естественные кандидаты: COALESCE с фиксированным приоритетом либо MIN/MAX по направлению сортировки;
- размножение строк: в отличие от полей обозначения, у `parameter_values` нет уникальности `(device_id, parameter_code)` — у устройства может быть несколько значений одного кода (вариантные с `variant_id`, повторные записи); наивный LEFT JOIN по образцу `device_designation_fields` размножит строки устройств и сломает total — значение обязано агрегироваться в производной таблице (`GROUP BY device_id`), заодно решается, входят ли вариантные значения (`variant_id IS NOT NULL`) в сортировочное значение.

Неприменимый/неизвестный код — 400 как сейчас (для неизвестного ключа сообщение уже есть — `api_sort_key_unknown`).

Fallback заявки (сортировка по обозначению и полям разбора) — действующее поведение; отказ от клиентской сортировки текущей страницы обоснован: страница — проекция серверного total при пагинации.

Оценка: 1–2 дня (механика ORDER BY готова; основная работа — агрегирующий JOIN и правило выбора значения).

## Сквозные замечания

- **Планы и контракты**: CC-2 — осознанное изменение зафиксированных решений; по AGENTS.md требует отдельного коммита с правкой всех связанных мест плана (`02-database.md`, `04-module-functionality.md`, `api/openapi.yaml`, `docs/fill-format.md`). CC-9 — обратный случай: реализация догоняет зафиксированный планом фасад (01 §2.4, 04 §1), осознанного изменения решений нет; до него сайт-проекту недоступны Go-API-части CC-6 (прогресс-колбэк `Importer.Import`) и CC-2 (колбэк OnChange как удобство встраивания). CC-11 и CC-12 — обратимо-совместимые расширения контракта REST без DDL и без смены версии схемы (решения D1–D10 не затрагивают); правки — `api/openapi.yaml` и `04-module-functionality.md` §2, отдельного коммита с правкой планов не требуют.
- **Тесты**: все новые ноги интеграционных тестов обязаны проходить на SQLite и PostgreSQL (`CATALOG_TEST_POSTGRES_DSN`, `go test ./... -p 1`) и попасть в сценарии `qa/runner`.

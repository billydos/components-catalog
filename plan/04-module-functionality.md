# 04. Функционал модуля (сервисный слой, REST, CLI, интеграция)

## 1. Публичный Go API (фасад библиотеки)

```go
app, err := components.Open(ctx, components.Config{
    Dialect: "sqlite" | "postgres",
    DSN:     "path/to.db" | "postgres://…",
    Pool:    components.PoolConfig{…},   // только для postgres
    Log:     slog.Default(),
})
defer app.Close()

app.Services   // сервисный слой
app.Handler()  // http.Handler REST /api/v1 (для монтирования в роутер сайта)
```

### 1.1. Интерфейсы сервисного слоя (эскиз)

```go
type DeviceService interface {
    Upsert(ctx, dev DeviceInput) (Outcome, error)   // Added | UpdatedExisting | Skipped:
                                                     // Skipped — данные записи не изменились
                                                     // (повторное применение тех же значений)
    Get(ctx, kind, designation) (*Card, bool, error)
    GetByID(ctx, id) (*Card, bool, error)
    Find(ctx, kind, designation) (FindResult, error) // точное совпадение + подсказка
                                                     // равнозначных по материалу
                                                     // (полупроводники)
    Delete(ctx, kind, designation) (bool, error)     // каскад + чистка сирот
    Search(ctx, SearchQuery) (SearchPage, error)     // фильтры, сортировка, пагинация
    Count(ctx, *KindFilter) (int, error)
}

type CatalogService interface {
    Snapshot(ctx) (*CatalogSnapshot, error)          // параметры/атрибуты/условия/единицы/
                                                     // группы/kinds — для UI и валидации
    Import(ctx, CatalogInput, dryRun bool) error     // расширение каталога, метасхема
    Export(ctx, w io.Writer, format Format) error    // round-trip
}

type ImportService interface {
    Import(ctx, r io.Reader, name string, dryRun bool) (ImportReport, error)
    Export(ctx, w io.Writer, format Format, kind *Kind) error
}

type DesignationService interface {
    Parse(ctx, text string) (ParsedDesignation, error) // kind + system + каноническая
                                                      // строка + поля (автодетект)
    Suggest(ctx, prefix string, kind *Kind, limit int) ([]Suggestion, error)
}
```

`SearchQuery`: класс; система обозначений (`gost`/`ost`/`pro`/`jedec`/`jis`/`series`/`other`); префикс/подстрока обозначения; фильтры по полям обозначения (material, subclass, junctions, group, dev_number, series…), по атрибутам (код op значение), по параметрам (код op min/max/условие, например `h21e.min ≥ 50`); сортировка (designation — по умолчанию, id, любому фильтруемому полю); пагинация (`limit` ≤ 200, `offset`/курсор — решается на этапе 5). Параметрические фильтры, затрагивающие вариантные параметры, применяются **в пределах одного исполнения** (EXISTS по `device_variants`): запрос `Unom=25 AND diameter≤10` находит записи, у которых габарит исполнения на 25 В не больше 10 мм, а не любые сочетания значений разных исполнений.

Семантика `Upsert`: отсутствует/`null` секция — не менять; задана — заменить целиком; `[]`/`{}` — очистить; ошибка в любом значении секции — запись не применяется вовсе; `manufacturers: null` — не менять список; секция `variants` заменяет набор исполнений целиком вместе с их значениями (атрибуты при этом остаются на уровне типа); секция `analogs` — полная замена прямых ссылок на аналоги (обозначения того же класса, опционально с заметкой — `03-data-model.md` §8). Идемпотентность повторного импорта.

## 2. REST API `/api/v1`

Транспорт: JSON, UTF-8; ошибки — `{ "code": "<машиночитаемый>", "message": "<русский текст>", "details": [...] }` с корректными HTTP-статусами (400/404/409/422/500). Аутентификация/авторизация/лимитирование — на стороне сайта (модуль не занимается); запись через REST монтируется сайтом только в защищённые маршруты.

| Метод и путь | Назначение |
|--------------|-----------|
| `GET /api/v1/kinds` | классы приборов |
| `GET /api/v1/catalog` | снимок каталога (параметры/атрибуты/условия/единицы/группы/системы обозначений/семейства) — для построения форм и фильтров; `ETag` по `catalog_revision` |
| `GET /api/v1/components?kind=&system=&q=&<поля обозначения>=&attr.<код>=&par.<код>.min=&sort=&limit=&offset=` | поиск: подстрока обозначения, система, фильтры полей/атрибутов/параметров, сортировка, пагинация; ответ — список с обозначением, классом, системой, ключевыми полями; `ETag` по `data_revision` |
| `GET /api/v1/components/{kind}/{designation}` | карточка: обозначение + система + поля, атрибуты, значения параметров по группам с условиями, исполнения-варианты (матрица «номинал × напряжение → габариты/масса»), аналоги, производители; 404 — не найдено |
| `GET /api/v1/components/id/{id}` | карточка по стабильному id |
| `GET /api/v1/suggest?q=&kind=&limit=` | автодополнение по префиксу обозначения; входит в первый релиз, может отключаться конфигурацией модуля (хендлер не монтируется) |
| `POST /api/v1/components` | создание (тело = запись наполнения: name/поля + секции) |
| `PUT /api/v1/components/{kind}/{designation}` | upsert с семантикой секций |
| `DELETE /api/v1/components/{kind}/{designation}` | удаление (каскад) |
| `GET /api/v1/stats` | количества по классам, версия схемы, ревизии |

Обозначение в пути URL-кодируется; обозначения, содержащие символ `/` (например, MIL-имена `M39003/…`), адресуются через `GET /components/id/{id}` или поиск — прямой путь для них не гарантируется (роутеры по-разному трактуют `%2F`).

OpenAPI 3.1-спецификация (`api/openapi.yaml`) — обязательный артефакт этапа 5; хендлеры пишутся по спецификации, контракт закрепляется тестами через `httptest`.

Замечания по фильтрации параметров: фильтр `par.<код>.min=N` отбирает записи, у которых хотя бы одно значение параметра удовлетворяет условию (EXISTS по `parameter_values`); фильтры по условиям значений (`par.KShum.freq=…`) — второй очередью, если понадобятся UI.

## 3. CLI (`catalogctl`)

Команды: `init`, `parse <обозначение>…` (автодетект класса и системы), `add <обозначение>…`, `import <файл> [--dry-run]`, `list [фильтры]` (`--kind`, `--system`, `--material`, `--subclass`, `--junctions`, `--group`, `--series`, `--number`, `--letters`, `--limit`…), `info <обозначение>`, `find <обозначение>` (подсказка равнозначных по материалу — только `gost`), `delete <обозначение>… [--dry-run]`, `count [--kind]`, `export [--kind] [--format jsonc|yaml|ndjson]` (устройства, round-trip формат наполнения), `catalog export|import`.

Команды `info`/`find`/`delete`/`add` разрешают класс автодетектом по обозначению; при неоднозначности или системе `other` обязателен `--kind`. Общие опции: `--db/--dsn`, `--dialect`, `--system`, `--kind`, `--dry-run`. Вывод: ожидаемые ошибки — префикс «Ошибка: », прочие — «Непредвиденная ошибка: », код выхода 1; тексты сообщений — контракт.

## 4. Формат наполнения

- jsonc/json и yaml/yml (реестр форматов) и ndjson; корень:

```jsonc
{
  "catalog": { … },        // опционально: расширение каталога (метасхема) — параметры,
                           // атрибуты, условия, семейства series
  "transistors": [ … ],
  "diodes": [ … ],
  "resistors": [ … ],
  "capacitors": [ … ]
}
```

- запись: `"КТ315Б"` | `{"name": …}` | `{"name": …, "system": "pro"}` (ключ `system` необязателен — автодетект; обязателен для `other`) | явные поля обозначения + секции `attributes`, `parameters`, `ratings`, `dimensions` (имена секций — из групп каталога; форма всех секций групп — единые списки объектов, `03-data-model.md` §12), `variants` (исполнения: метка + те же секции групп, см. `03-data-model.md` §7) и `analogs` (прямые ссылки на аналоги, см. `03-data-model.md` §8);
- Issues-модель: корневые проблемы + проблемы записей накапливаются за один прогон; жёсткая ошибка — только синтаксис формата; дубликаты ключей — ошибка разбора файла (тихая потеря данных недопустима);
- NDJSON (`.ndjson`, одна JSON-строка — одна сущность) — машинный потоковый формат реестра для больших объёмов (10⁴–10⁵ записей): построчный разбор без загрузки файла целиком, конкатенация файлов и частичный догрузочный импорт; корневые секции выражаются строками-обёртками `{"catalog": …}` (одна строка на блок каталога) и `{"<класс>": <запись>}`; блок `catalog` должен предшествовать записям, использующим вводимые им определения; Issues-модель та же; комментариев и якорей нет — для ручного редактирования и ревью остаются jsonc/yaml;
- экспорт — тот же формат (round-trip), включая каталог (`catalog export`); все форматы реестра, по умолчанию — jsonc, NDJSON — явным указанием формата.

## 5. Интеграция в веб-бэкэнд

- **Встраивание**: модуль не запускает серверов, не читает глобальных флагов/env (кроме явной передачи конфигурации); сайт создаёт `App` при старте и закрывает при завершении. SQLite: WAL + `busy_timeout` позволяют сайту и CLI работать с одним файлом одновременно (запись сериализуется на уровне файла); несколько пишущих `App` на одну базу SQLite не допускается.
- **Читаемость данных сайтом напрямую** (мимо модуля) не поддерживается и не гарантируется: единственная гарантия совместимости — REST/Go API и схема `schema_meta`.
- **Кэширование**: `ETag` (`catalog_revision`, `data_revision`) на `GET /catalog` и `GET /components`; сайт может кэшировать снимок каталога до смены версии.
- **Наблюдаемость**: `log/slog` (передаётся сайтом); хук метрик (интерфейс) — счётчики и гистограммы вызовов/ошибок по операциям; трассировка — через `context.Context` сайта.
- **Производительность**: целевые ориентиры первого релиза — поиск с фильтрами по 10⁴–10⁵ устройств ≤ 100 мс (индексы из `02-database.md`), карточка ≤ 20 мс; при росте — денормализация/материализация вынесенных фильтров, не меняя публичный API.
- **Деплой**: модуль компилируется в бинарник сайта (или отдельный сервис — по желанию сайта, REST это позволяет); cgo не требуется (pure Go драйверы).
- **Подбор аналогов**: автоматическое сопоставление компонентов по характеристикам/атрибутам — на стороне сайта, не в модуле; модуль предоставляет для него параметрический поиск и нормализованные данные; прямые ссылки-аналоги — данные модуля.

## 6. Функциональные границы первого релиза

Входит: 4 класса, парсеры систем обозначений (ГОСТ/ОСТ, PRO ELECTRON, JEDEC, JIS — строгие грамматики; серии по реестру-данным; `other` без разбора), каталог-данные с движком валидации, EAV-хранение, семантика секций, поиск/фильтры/пагинация, suggest (отключаемый конфигурацией), аналоги (прямые ссылки, несколько на запись), импорт/экспорт jsonc/yaml/ndjson, CLI, REST v1 + OpenAPI, метрики-хук, ETag, версия схемы.

Не входит (явно): аутентификация/авторизация; автоматический подбор аналогов/заменителей по характеристикам (задача бэкэнда-потребителя); полнотекстовый поиск по атрибутам; изображения/сканы (только `datasheetUrl`); версионирование данных устройств (история правок); изменение каталога через REST (каталог расширяется файлами наполнения через CLI/Go API); миграции схемы (D5).

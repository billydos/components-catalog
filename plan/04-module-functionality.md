# 04. Функционал модуля (сервисный слой, REST, CLI, интеграция)

## 1. Публичный Go API (фасад библиотеки)

```go
app, err := components.Open(ctx, components.Config{
    Dialect: "sqlite" | "postgres",
    DSN:     "path/to.db" | "postgres://…",
    Pool:    components.PoolConfig{…},   // только для postgres
    Log:     slog.Default(),
})
defer app.Close()

app.Services   // сервисный слой
app.Handler()  // http.Handler REST /api/v1 (для монтирования в роутер сайта)
```

### 1.1. Интерфейсы сервисного слоя (эскиз)

```go
type DeviceService interface {
    Upsert(ctx, dev DeviceInput) (Outcome, error)   // Added | UpdatedExisting | Skipped
    Get(ctx, kind, designation) (*Card, bool, error)
    GetByID(ctx, id) (*Card, bool, error)
    Find(ctx, kind, designation) (FindResult, error) // точное совпадение + подсказка
                                                     // равнозначных по материалу
                                                     // (полупроводники)
    Delete(ctx, kind, designation) (bool, error)     // каскад + чистка сирот
    Search(ctx, SearchQuery) (SearchPage, error)     // фильтры, сортировка, пагинация
    Count(ctx, *KindFilter) (int, error)
}

type CatalogService interface {
    Snapshot(ctx) (*CatalogSnapshot, error)          // параметры/атрибуты/условия/единицы/
                                                     // группы/kinds — для UI и валидации
    Import(ctx, CatalogInput, dryRun bool) error     // расширение каталога, метасхема
    Export(ctx, w io.Writer, format Format) error    // round-trip
}

type ImportService interface {
    Import(ctx, r io.Reader, name string, dryRun bool) (ImportReport, error)
    Export(ctx, w io.Writer, format Format, kind *Kind) error
}

type DesignationService interface {
    Parse(ctx, text string) (ParsedDesignation, error) // kind + каноническая строка + поля
    Suggest(ctx, prefix string, kind *Kind, limit int) ([]Suggestion, error)
}
```

`SearchQuery`: класс; префикс/подстрока обозначения; фильтры по полям обозначения (material, subclass, group, dev_number…), по атрибутам (код op значение), по параметрам (код op min/max/условие, например `h21e.min ≥ 50`); сортировка (designation — по умолчанию, id, любому фильтруемому полю); пагинация (`limit` ≤ 200, `offset`/курсор — решается на этапе 5). Параметрические фильтры, затрагивающие вариантные параметры, применяются **в пределах одного исполнения** (EXISTS по `device_variants`): запрос `Unom=25 AND diameter≤10` находит записи, у которых габарит исполнения на 25 В не больше 10 мм, а не любые сочетания значений разных исполнений.

Семантика `Upsert` (переносится из действующего проекта): отсутствует/`null` секция — не менять; задана — заменить целиком; `[]`/`{}` — очистить; ошибка в любом значении секции — запись не применяется вовсе; `manufacturers: null` — не менять список; секция `variants` заменяет набор исполнений целиком вместе с их значениями (атрибуты при этом остаются на уровне типа). Идемпотентность повторного импорта.

## 2. REST API `/api/v1`

Транспорт: JSON, UTF-8; ошибки — `{ "code": "<машиночитаемый>", "message": "<русский текст>", "details": [...] }` с корректными HTTP-статусами (400/404/409/422/500). Аутентификация/авторизация/лимитирование — на стороне сайта (модуль не занимается); запись через REST монтируется сайтом только в защищённые маршруты.

| Метод и путь | Назначение |
|--------------|-----------|
| `GET /api/v1/kinds` | классы приборов |
| `GET /api/v1/catalog` | снимок каталога (параметры/атрибуты/условия/единицы/группы) — для построения форм и фильтров; `ETag` по `catalog_revision` |
| `GET /api/v1/components?kind=&q=&<поля обозначения>=&attr.<код>=&par.<код>.min=&sort=&limit=&offset=` | поиск: подстрока обозначения, фильтры полей/атрибутов/параметров, сортировка, пагинация; ответ — список с обозначением, классом, ключевыми полями; `ETag` по `data_revision` |
| `GET /api/v1/components/{kind}/{designation}` | карточка: обозначение + поля, атрибуты, значения параметров по группам с условиями, исполнения-варианты (матрица «номинал × напряжение → габариты/масса»), производители; 404 — не найдено |
| `GET /api/v1/components/id/{id}` | карточка по стабильному id |
| `GET /api/v1/suggest?q=&kind=&limit=` | автодополнение по префиксу обозначения |
| `POST /api/v1/components` | создание (тело = запись наполнения: name/поля + секции) |
| `PUT /api/v1/components/{kind}/{designation}` | upsert с семантикой секций |
| `DELETE /api/v1/components/{kind}/{designation}` | удаление (каскад) |
| `GET /api/v1/stats` | количества по классам, версия схемы, ревизии |

OpenAPI 3.1-спецификация (`api/openapi.yaml`) — обязательный артефакт этапа 5; хендлеры пишутся по спецификации, контракт закрепляется тестами через `httptest`.

Замечания по фильтрации параметров: фильтр `par.<код>.min=N` отбирает записи, у которых хотя бы одно значение параметра удовлетворяет условию ( EXISTS по `parameter_values`); фильтры по условиям значений (`par.KShum.freq=…`) — второй очередью, если понадобятся UI.

## 3. CLI (`catalogctl`)

Команды и поведение — преемники действующего проекта: `init`, `parse <обозначение>…` (автодетект класса), `add <обозначение>…`, `import <файл> [--dry-run]`, `list [фильтры]` (`--kind`, `--material`, `--subclass`, `--group`, `--family`, `--number`, `--letters`, `--limit`…), `info <обозначение>`, `find <обозначение>` (подсказка равнозначных по материалу), `delete <обозначение>… [--dry-run]`, `count [--kind]`, `catalog export|import`. Опции `--db/--dsn`, `--dialect`, `--dry-run`; коды выхода и префиксы ошибок — как сейчас.

## 4. Формат наполнения

- jsonc/json и yaml/yml (реестр форматов, как в действующем проекте); корень:

```jsonc
{
  "catalog": { … },        // опционально: расширение каталога (метасхема)
  "transistors": [ … ],
  "diodes": [ … ],
  "resistors": [ … ],
  "capacitors": [ … ]
}
```

- запись: `"КТ315Б"` | `{"name": …}` | явные поля обозначения + секции `attributes`, `parameters`, `ratings`, `dimensions` (имена секций — из групп каталога) и `variants` (исполнения: метка + те же секции групп, см. `03-data-model.md` §7);
- Issues-модель: корневые проблемы + проблемы записей накапливаются за один прогон; жёсткая ошибка — только синтаксис формата;
- NDJSON для больших объёмов — этап 4 (решение `plan/README.md`, вопрос 3);
- экспорт — тот же формат (round-trip), включая каталог (`catalog export`).

## 5. Интеграция в веб-бэкэнд

- **Встраивание**: модуль не запускает серверов, не читает глобальных флагов/env (кроме явной передачи конфигурации); сайт создаёт `App` при старте и закрывает при завершении; несколько `App` на одну базу SQLite не допускается (односоединённая модель записи).
- **Читаемость данных сайтом напрямую** (мимо модуля) не поддерживается и не гарантируется: единственная гарантия совместимости — REST/Go API и схема `schema_meta`.
- **Кэширование**: `ETag` (`catalog_revision`, `data_revision`) на `GET /catalog` и `GET /components`; сайт может кэшировать снимок каталога до смены версии.
- **Наблюдаемость**: `log/slog` (передаётся сайтом); хук метрик (интерфейс) — счётчики и гистограммы вызовов/ошибок по операциям; трассировка — через `context.Context` сайта.
- **Производительность**: целевые ориентиры первого релиза — поиск с фильтрами по 10⁴–10⁵ устройств ≤ 100 мс (индексы из `02-database.md`), карточка ≤ 20 мс; при росте — денормализация/материализация вынесенных фильтров, не меняя публичный API.
- **Деплой**: модуль компилируется в бинарник сайта (или отдельный сервис — по желанию сайта, REST это позволяет); cgo не требуется (pure Go драйверы).

## 6. Функциональные границы первого релиза

Входит: 4 класса, парсеры (новые системы + легаси-реестры R/D/C), каталог-данные с движком валидации, EAV-хранение, семантика секций, поиск/фильтры/пагинация, suggest, импорт/экспорт jsonc/yaml, CLI, REST v1 + OpenAPI, метрики-хук, ETag, версия схемы.

Не входит (явно): аутентификация/авторизация; полнотекстовый поиск по атрибутам; изображения/сканы (только `datasheetUrl`); версионирование данных устройств (история правок); редактирование каталога через REST (только импорт); миграции схемы (D5).

# 01. Архитектура проекта components-catalog

## 1. Общая форма

Go-модуль (библиотека + встраиваемый REST API + CLI), без внешних сервисов и демонов. Потребители:

- **веб-бэкэнд сайта** — импортирует Go-пакет и/или монтирует `http.Handler` с REST API `/api/v1/...` в свой роутер; аутентификация, авторизация, rate limiting, CORS — на стороне сайта;
- **администратор/наполнитель** — CLI `catalogctl` (init, import, add, list, info, find, delete, count, parse, catalog export);
- **наполнение** — файлы jsonc/yaml и NDJSON (для больших объёмов) через сервисный слой; тот же путь использует и CLI, и REST-импорт.

```
components-catalog/
├── cmd/catalogctl/            точка входа CLI (только main)
├── internal/
│   ├── domain/                обозначения (парсеры систем: ГОСТ/ОСТ, PRO ELECTRON, JEDEC, JIS; серии), единицы, классы приборов, ошибки
│   ├── catalog/               доступ к каталожным таблицам; движок валидации по правилам из БД
│   ├── storage/               переносимое реляционное ядро (database/sql) + диалекты sqlite/postgres
│   ├── service/               бизнес-операции: upsert, поиск, карточка, импорт/экспорт, производители
│   ├── importer/              реестр форматов наполнения (jsonc/json, yaml/yml, ndjson), семантика секций
│   ├── httpapi/               REST /api/v1 (net/http), OpenAPI-совместимые хендлеры
│   └── cli/                   разбор аргументов, команды, вывод
├── api/openapi.yaml           спецификация REST API (артефакт этапа 5)
├── seed/                      базовые сиды каталога (единицы, условия, стартовые каталоги 4 классов)
├── sample-data/               примеры наполнения (по классам)
├── AGENTS.md                  правила разработки (аналог действующего проекта)
└── README.md
```

Правило слоёв (как в действующем проекте, сохраняется):

- `domain` не зависит от БД и форматов; ошибки — значения (`*domain.Error` с кодом), не паника;
- `storage` не знает бизнес-правил: только переносимый DML + диалекты;
- `catalog`, `service`, `importer`, `httpapi`, `cli` — надстройки; `httpapi` и `cli` — тонкие транспорты над `service`, без бизнес-логики.

## 2. Слои и ответственности

### 2.1. `internal/domain` — обозначения и базовые понятия

- Классы приборов: `Kind` (`transistor`, `diode`, `resistor`, `capacitor`) — реестр в коде синхронизирован с сидами `kinds`; системы обозначений — реестр кодов синхронизирован с сидами `designation_systems` (пин-тесты).
- **Парсеры обозначений — код для строго формальных систем** (грамматики стабильны; гибкость требуется к параметрам и реестрам, не к грамматикам):
  - полупроводники: ГОСТ 10862-64 (материал, подкласс `Т`,`П` | `Д`,`С`,`В`,`А`,`И`,`Г`,`Л`,`Ц`, сборка, признак, номер, буквы, модификация, бескорпусное); PRO ELECTRON (материал `A…R`, класс `A…Z`, номер, суффикс); JEDEC (число переходов, `N`, номер регистрации, суффикс); JIS (переходы, `S`, класс, номер, суффикс);
  - резисторы — ГОСТ 13453-68 (`С2-33Н`, `СП3-19А`) + ОСТ 11.074.009;
  - конденсаторы — К-система (`К10-17Б`, `К50-35`);
  - `series` — единая слабая грамматика хвоста над реестром семейств (данные `series_families`: бывшие легаси-семейства и мировые дом-номера);
  - `other` — без разбора, только канонизация.
- Результат разбора: система + каноническое обозначение-строка (точный ключ) + набор полей «код → текст/число» (уходит в `device_designation_fields`), класс прибора.
- Материалы: пары равнозначных символов `Г/1, К/2, А/3, И/4` — только `gost` (подсказка `find`, сохраняется поведение действующего проекта); `pro` кодирует материал первой буквой (`A`/`B`/`C`) — в поле `material` с единым словарём значений для сквозного фильтра между `gost` и `pro`.
- Единицы: канонический справочник — данные (`units`), в домене — только отображение и форматирование чисел (`Fmt`-аналог: целое без точки, дробное — кратчайшей записью; инженерные суффиксы для больших/малых величин — пФ, МОм).
- Ошибки: `domain.Error{Code, Message}`; коды машиночитаемые (`invalid_designation`, `unknown_parameter`, `validation_failed`, `not_found`, `schema_version_mismatch`, `invalid_import_file`, ...); русские тексты — дословный контракт (как в действующем проекте), тесты закрепляют.

### 2.2. `internal/catalog` — каталог как данные + движок валидации

- Чтение определений: параметры (код, класс, группа, единица, тип значения, границы, потолок, enum-значения, наборы условий), атрибуты (код, класс, тип, enum, группа, правило), условия, единицы, группы, именованные правила.
- **Движок валидации**: проверка значения параметра по `value_type` (точное/не менее/не более/диапазон/текст/enum), позитивность, потолок, комбинации условий (наборы «required/optional/остальные запрещены» из БД), правила атрибутов; сложные межполевые правила — вызов именованных код-валидаторов из реестра (привязка — строкой в БД; неизвестное имя правила — громкая ошибка).
- Кэш каталога в памяти с инвалидацией по версии (обновление каталога — редкая админ-операция); каталог иммутабелен в рамках обработки одного запроса.
- Валидация целостности самих определений (метасхема): единица существует, enum непуст для enum-типа, наборы условий ссылаются на известные условия и т.п. — при импорте каталога.

### 2.3. `internal/storage` — переносимое реляционное ядро

- `database/sql` + `sql.Named` (`@имя`), только переносимые конструкции: `LIMIT/OFFSET`, производные таблицы, `INSERT ... SELECT`, `EXISTS`; булевы — INTEGER 0/1; NULL — «не задано»; без JSON-функций, без диалектных типов (схема — `02-database.md`).
- `Dialect{Open, CreateTableSql, ...}` + две реализации:
  - **sqlite** (`modernc.org/sqlite`, pure Go, без cgo): `SetMaxOpenConns(1)`, `PRAGMA foreign_keys = ON` — односоединённая модель как в действующем проекте;
  - **postgres** (`pgx/v5/stdlib`): пул соединений, параметры пула из конфигурации.
- Версия схемы: при первом обращении чтение `schema_meta.schema_version`; несовпадение — `*domain.Error` c кодом `schema_version_mismatch` («база создана другой версиией модуля; пересоздайте её импортом» — политика D5, миграций нет).
- `EnsureCreated` — только у команд записи (init/import/add), один запуск — один DDL; чтение и delete без DDL (сохраняется).
- Запись — в транзакции (`Begin` + `defer Rollback` + `Commit`); чистка осиротевших производителей после замены связей и удалений — как в действующем проекте.

### 2.4. `internal/service` — сервисный слой (публичный API библиотеки)

Единственная точка входа для CLI, REST и внешнего кода сайта. Интерфейсы (эскизы сигнатур — в `04-module-functionality.md`):

- устройства: `Upsert` (семантика секций как в действующем проекте: отсутствует/null — не менять, задана — заменить целиком, `[]`/`{}` — очистить, ошибка в секции — запись не применяется вовсе; секция `variants` — исполнения типа: замена набора целиком; секция `analogs` — прямые ссылки на аналоги: замена целиком), `Get`/`Card` (включая матрицу исполнений «номинал × напряжение → габариты/масса» и блок аналогов), `Find` (точное обозначение + подсказка равнозначных по материалу для полупроводников `gost`), `Delete` (каскад), `Search` (фильтры + сортировка + пагинация; вариантные фильтры — в пределах одного исполнения), `Count`;
- каталог: `Catalog` (полный снимок для UI), `ImportCatalog`, `ExportCatalog`;
- импорт/экспорт: `Import(reader, format, dryRun)`, `Export(writer, format, kind)`;
- обозначения: `ParseDesignation(text)` (класс + система + каноническая строка + поля; автодетект, §2.4 `03-data-model.md`).
- производители: привязка записей.

Публичный фасад пакета для встраивания: `components.Open(cfg) (*App, error)` + `App.Close()`; `App.Services`, `App.HTTPHandler()`.

### 2.5. `internal/importer`

- Реестр форматов: jsonc/json (`tailscale/hujson`) и yaml/yml (`goccy/go-yaml`) — как в действующем проекте — плюс ndjson (построчный JSON, stdlib) для больших объёмов; семантика секций и дословные тексты ошибок — внутри `importer`.
- Корень: необязательные ключи-классы (`transistors`, `diodes`, `resistors`, `capacitors`) + опциональный `catalog`; хотя бы один ключ обязателен.
- Записи: `"КТ315Б"` | `{"name": ...}` | `{"name": ..., "system": "pro"}` (ключ `system` необязателен — автодетект; обязателен для `other`) | явные поля обозначения + секции `attributes` / секции групп параметров (`parameters`, `ratings`, `dimensions` — имя секции задаётся группой каталога).
- Идемпотентность импорта; Issues-модель (корневые проблемы + проблемы записей, накопление за один прогон) — как в действующем проекте.

### 2.6. `internal/httpapi` — REST API

Версияемый префикс `/api/v1`, `net/http` (Handler, монтируется в роутер сайта), JSON, OpenAPI-спецификация — артефакт. Список ресурсов и семантика — `04-module-functionality.md`. Аутентификация/авторизация — вне модуля.

### 2.7. `internal/cli`

Команды над `service`: `init`, `parse` (автодетект класса и системы), `add`, `import`, `list`, `info`, `find`, `delete`, `count`, `catalog` (export/import). Поведение и тексты — по образцу действующего проекта (`--db`, `--dialect`, `--system`, `--dry-run`, префиксы «Ошибка: »/«Непредвиденная ошибка: », коды выхода).

## 3. Сквозные механизмы

- **Конфигурация**: структура (диалект+DSN/путь, уровни логирования, параметры пула, лимиты пагинации, отключение `suggest`); без глобальных переменных; загрузка — код сайта или CLI-флаги/env.
- **Логирование**: `log/slog`, структурные поля, без обязательного глобального логгера (передаётся в `Open`).
- **Метрики**: интерфейс-хук (счётчики запросов/ошибок, длительности) — реализация на стороне сайта; свой экспорт метрик в модуле не заводим.
- **Контекст**: все сервисные операции принимают `context.Context`; тайм-ауты/отмена — на вызывающем.
- **Конкурентность**: библиотека безопасна для одновременного использования (stateless поверх пула соединений; SQLite — сериализация на уровне одного соединения); каталог-кэш — атомарная замена указателя.
- **Кэширование ответов REST**: `ETag` по версии каталога и ревизии данных (счётчик изменений) — сайт сам решает, как использовать.

## 4. Зависимости (критерии — как в действующем проекте)

База — stdlib. Внешние: `modernc.org/sqlite` (pure Go), `jackc/pgx/v5` (stdlib-режим), `tailscale/hujson`, `goccy/go-yaml`. Новые зависимости — только если заменяют самописный разбор или существенно сокращают код; pure Go без cgo.

## 5. Что переносится из действующего проекта, что пересматривается

| Аспект | Решение |
|--------|---------|
| Ошибки — значения, префиксы вывода, коды выхода | переносится |
| Семантика секций импорта (null/отсутствует/замена/атомарность, идемпотентность) | переносится |
| Обозначение — точный ключ; материалы равнозначны только физически; раздельные записи `КТ315`/`2Т315` | переносится (тождество — строка, а не набор колонок) |
| Парсер обозначений с по-позиционными русскими сообщениями | переносится подход; грамматики расширяются на 4 класса и 7 систем (ГОСТ/ОСТ, PRO ELECTRON, JEDEC, JIS, серии) |
| Переносимость DML, диалект, транзакции, чистка сирот производителей, `EnsureCreated` только у записи | переносится |
| Односоединённость как универсальное правило | пересматривается: только для SQLite (D3) |
| Каталог в коде + генерация CHECK/справки из него | заменяется каталогом-данными (D1) |
| Типизированные колонки условий/атрибутов, reflect-источники имён полей | заменяются EAV (D2) |
| CHECK-ограничения семантики значений в DDL | сокращаются до структурных (FK, NOT NULL, типы, 0/1); семантика — в движке валидации по данным |
| Русские тексты ошибок как контракт | сохраняется + добавляются машиночитаемые коды |
| Без миграций | сохраняется (D5) + защита версией схемы |
| AGENTS.md/SKILL.md, отчёты ANALYSIS-NN, гигиена go vet/gofmt/go test | переносится культура; правила переписываются под новую архитектуру |

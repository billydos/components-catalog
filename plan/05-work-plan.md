# 05. План работ

Оценки относительные (S ≤ недели фокусной работы, M — 2–4, L — больше); главный множитель этапов 1 и 6 — предметная каталогизация и выверка по первоисточникам, не код. Правило гигиены (из действующего проекта, переносится): после каждого пакета — `go build ./... && go vet ./... && gofmt -l .` и `go test ./...`; тексты русских сообщений — контракт, закреплены тестами дословно.

## Риски

| ID | Риск | Мера |
|----|------|------|
| R1 | Предметная неточность каталогов/реестров (ГОСТ, легаси-семейства) | выверка на этапе 6 до релиза; каталог — данные: правка без кода; примеры — golden-тестами |
| R2 | EAV-производительность фильтров при росте данных | индексы из `02-database.md`; ориентиры и прикидка в этапе 7; план Б — денормализация/материализованные представления без смены публичного API |
| R3 | Расхождение диалектов SQLite/PostgreSQL (типы, пулы, RETURNING) | один набор интеграционных тестов на обе СУБД; диалектная изоляция как в действующем проекте |
| R4 | Без миграций при «длинной» жизни бэкэнда станет больно | защита `schema_version` (громкий отказ, без тихой порчи); пересоздание импортом; эскорт-решение о миграциях вынесено в будущее (не в v0.1) |
| R5 | Гибкость каталога vs целостность данных (валидация по данным сложнее CHECK) | метасхема + движок валидации как единственная точка записи (сервисы); прямые записи в БД — вне контракта |
| R6 | Неоднозначность автодетекта класса (легаси-обозначения) | ключ класса в файлах наполнения, `--kind` в CLI, отказ с перечнем поддерживаемых систем |
| R7 | Объём именованных правил растёт (каждое — код) | правило добавляется только когда не выражается данными (условия/типы/enum); реестр правил мал по построению |
| R8 | Вариантная семантика (исполнения) усложняет запросы и импорт: фильтры — EXISTS в пределах варианта, матрицы — многострочные данные | единая точка семантики в сервисах; тесты на вариантные фильтры и атомарность секции `variants`; контроль производительности EXISTS в этапе 7 (индекс `parameter_values(variant_id)`) |

# План проекта «Справочник электронных компонентов»

Рабочее имя модуля: **components-catalog** (рабочее имя пакета Go: `componentscatalog`; совпадает с именем репозитория — решено; лицензия — MIT; путь импорта Go зависит от хостинга, фиксируется на этапе 0). Проект разрабатывается с нуля и охватывает советскую и мировую элементную базу; структура и правила действующего репозитория `SovietTransistorsDatabase` (см. `AGENTS.md`, `ANALYSIS-01/02/03.md`) используются как ориентир — что именно переносится, а что пересматривается, описано ниже.

## Назначение

Локальный/встраиваемый справочник электронных компонентов (советская и мировая элементная база) четырёх классов — **транзисторы, диоды, резисторы, конденсаторы** — с несколькими системами обозначений (ГОСТ/ОСТ, PRO ELECTRON, JEDEC, JIS, серии), электрическими параметрами с условиями измерения, предельными эксплуатационными данными, массогабаритными и описательными атрибутами. Проект — **модуль веб-бэкэнда** (не бэкэнд целиком): Go-библиотека с сервисным слоем + встраиваемый версияемый REST API; консольная утилита — админ-инструмент над той же библиотекой.

## Ключевые архитектурные решения (зафиксированы по итогам обсуждения)

| # | Решение | Отказ от подхода действующего проекта |
|---|---------|----------------------------------------|
| D1 | **Каталог параметров/атрибутов — данные в БД.** Коды, названия, единицы, типы значений, границы, комбинации условий и enum-значения хранятся в каталожных таблицах и расширяются без правки кода. Сложные межполевые правила — именованные валидаторы в коде, привязка — данными | Было: декларативный Go-каталог, из которого генерируются валидатор, справка, поля jsonc и CHECK-ограничения (AGENTS.md правило 1). Новый параметр = правка кода + пересборка + пересоздание БД — противоречит требованию гибкости |
| D2 | **Значения — EAV: строка на значение.** Таблица значений параметров + таблица условий измерения; атрибуты — ключ-значение; поля обозначения — ключ-значение | Было: типизированные колонки, отдельная колонка на каждое условие — разреженность при 4 классах и ALTER TABLE на каждое новое условие |
| D3 | **SQLite и PostgreSQL равноправны.** Переносимое ядро DML на `database/sql` + два диалекта (DDL, открытие, пулы). Для PostgreSQL — пул соединений; SQLite остаётся односоединённой моделью записи | Было: только SQLite (`SetMaxOpenConns(1)` как обязательное ограничение) |
| D4 | **Модуль = Go-библиотека + REST API.** Слои: домен → каталог → хранилище → сервисы; тонкий версияемый REST-слой (`net/http`) внутри модуля; CLI над сервисами | Было: консольная утилита как конечный продукт |
| D5 | **Без миграций схемы.** Изменение схемы = пересоздание базы импортом (данные справочные, восстанавливаются из файлов наполнения). Защита от рассинхронизации — таблица `schema_meta` с версией схемы: модуль отказывается работать с базой другой версии с внятной ошибкой | Сохранено как в действующем проекте (AGENTS.md правило 5), но добавлена явная защита версией схемы |
| D6 | **Исполнения (варианты) типа.** Зависимости «номинал × напряжение → габариты/масса» — норма для электролитических конденсаторов (`К50-35`: 1 мкФ выпускается только на 160 В) и ряды мощностей резисторов (`С2-33`: 0.125–2 Вт, габариты зависят от мощности). Вариант — группа значений параметров внутри записи типа: свои `Unom`/`Cnom` и свои массогабаритные данные | Плоский набор значений на запись (как в действующем проекте, где варианты не нужны: буква классификации транзистора уже задаёт отдельную запись) — недостаточен; отдельная запись на каждое сочетание ломала бы принцип «обозначение — точный ключ», т.к. напряжение в обозначение К-системы не входит |

Следствия из решений (детали — в документах плана):

- обозначение — по-прежнему **точный строковый ключ** записи внутри класса (`КТ315Б` ≠ `2Т315Б`), но составные NULL-безопасные предикаты тождества уходят: тождество — это `kind + designation`; система обозначений — атрибут записи, не часть ключа;
- парсеры **строгих систем обозначений** (ГОСТ/ОСТ, PRO ELECTRON, JEDEC, JIS) остаются кодом (грамматики стабильны), реестры семейств `series` — данные, поэтому новые семейства не требуют менять код; результат разбора хранится как данные (ключ-значение), поэтому новые классы приборов не требуют менять схему;
- секции «предельные данные» и «массогабаритные данные» — не отдельные жёсткие структуры, а **группы каталога** с собственными ключами секций импорта;
- reflect-источники имён полей и генерация CHECK из каталога не нужны (в схеме нет жёстких колонок атрибутов/условий); вместо этого — метасхема каталога и движок валидации, читающий правила из БД;
- сообщения об ошибках получают **машиночитаемые коды** рядом с дословными русскими текстами (тексты — по-прежнему контракт, но теперь и коды — тоже).

## Открытые вопросы и зафиксированные решения

1. **Имя и лицензия — решено:** модуль `components-catalog`, лицензия MIT. Остаётся формальность пути импорта Go (зависит от хостинга) — этап 0.
2. Состав стартового наполнения: минимальные каталоги из плана (`03-data-model.md`) или расширенные — решается при подготовке данных этапа 6.
3. **Формат хранения файлов наполнения (открыт, этап 4).** Суть вопроса: нынешние форматы — человекочитаемые jsonc/yaml (комментарии, ревью в git, якоря yaml), но они разбираются только целиком: при 10⁴–10⁵ записей растут память и время разбора, невозможны стриминг, конкатенация файлов и частичный догрузочный импорт. Вопрос: добавить ли машинный потоковый формат NDJSON (одна JSON-запись на строку) для больших объёмов наряду с человекочитаемыми, сохранив симметричный round-trip экспорта, или остаться на одном семействе форматов. Минусы NDJSON: нет комментариев и якорей, тяжелее править руками. Смежные подвопросы: выражение корневых секций (`catalog`, классы) в NDJSON; накопление Issues-модели при стриминге; формат экспорта по умолчанию. Критерии решения: фактические объёмы наполнения и ориентиры производительности импорта (`04-module-functionality.md`).
4. **Автодополнение `suggest` — решено:** входит в первый релиз; может отключаться конфигурацией модуля (хендлер `/suggest` не монтируется).
5. **Аналоги — решено:** прямое указание аналога — данные модуля (`device_analogs`: ссылки между записями одного класса, заметка о характере замены); автоматическое соотношение/поиск по характеристикам или атрибутам — вне модуля, задача бэкэнда-потребителя (модуль обеспечивает его параметрическим поиском и нормализованными полями/единицами).

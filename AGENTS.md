# AGENTS.md — правила разработки

Проект **components-catalog** — справочник электронных компонентов (советская и мировая элементная база): Go-библиотека + встраиваемый REST API `/api/v1` + CLI `catalogctl`. Хранилища: SQLite и PostgreSQL, равноправные. Источник истины по архитектуре и контрактам — план `docs/plan/`: `README.md` (решения D1–D12), `01-architecture.md`, `02-database.md`, `03-data-model.md`, `04-module-functionality.md`, `06-examples.md`, отчёты выверки `07-r1-verification.md` и `08-data-verification.md`; порядок работ — `05-work-plan.md`, карта документов — таблица в конце `README.md`. Пользовательские справочники: `docs/fill-format.md` (регламент наполнения), `docs/class-keys.md` (ключи по классам), контракт REST — `api/openapi.yaml`; выверенное наполнение — `data/`. Код не расходится с планом; осознанное изменение решения — отдельный коммит с правкой всех связанных мест плана.

## Проверка

После каждого пакета и перед коммитом:

```
go build ./... && go vet ./... && go test ./...
git ls-files -z --cached --others --exclude-standard -- '*.go' | xargs -0 gofmt -l   # вывод обязан быть пуст
```

`gofmt` проверяется по файлам репозитория (отслеживаемым и новым неигнорируемым), а не обходом дерева: внутри дерева может лежать кэш модулей (`GOPATH=$CI_PROJECT_DIR/.go` — конвенция GitLab-джоб), и `gofmt -l .` уходил бы разбирать чужие `testdata` (exit 2). Так же считает QA-прогонщик (`static/gofmt`).

CI (`.gitlab-ci.yml`, GitLab) — три контура: автоматически на каждый пуш и MR — короткое QA: `lint` (gofmt, vet), `test` (`go test ./...`) и прогонщик `go run ./qa/runner` без нагрузочной прикидки (`CATALOG_QA_SCALE=0`) на linux/SQLite и linux/PostgreSQL 16 (`CATALOG_QA_DIALECT` задаёт единственную ногу джобы); вручную кнопкой `full-qa` — дочерний пайплайн `.gitlab/ci/full-qa.yml` с полным контуром: короткий плюс `crossbuild` (сборка под windows/darwin/arm64 с Linux-раннера), `vuln` (`govulncheck`) и нагрузочная прикидка `CATALOG_QA_SCALE=10000`; вручную — зеркало на GitHub (джоба `github-mirror`, см. «Релизы»). Ноги QA на Windows в CI нет — Windows-раннера в инсталляции нет, поэтому windows-совместимость проверяется только сборкой; отчёт прогона — структурный лог `qa/reports/*.log` (формат `qa-log/1`), в GitLab он выгружается артефактом `qa-artifact/qa-report.log`. Локальный прогон интеграционных тестов на PostgreSQL — задать `CATALOG_TEST_POSTGRES_DSN` (без переменной нога пропускается; `go test ./...` — с `-p 1`: одноразовая база одна на все пакеты, параллельные пакеты конфликтуют на DROP/CREATE таблиц; прогонщик `qa/runner` добавляет флаг сам).

Релизы: теги в GitLab пайплайнов не создают — QA и релизы по тегу полностью на стороне GitHub: джоба `github-mirror` отправляет `main` и теги в зеркало `github.com/billydos/components-catalog`, а `.github/workflows/release.yml` гонит полный QA того же коммита и выпускает GitHub Release. Параллельно действует GitHub Actions (`.github/workflows/`): `ci.yml` — дешёвые lint/test на пул-реквестах; `qa.yml` — полный QA-контур (linux/SQLite, linux/PostgreSQL, windows/SQLite) без автозапуска на пуш: вручную (`workflow_dispatch`, в том числе на конкретный коммит через `gh workflow run qa.yml --ref <SHA>`) и как вызываемый гейт релиза (`workflow_call`); `release.yml` — релиз по тегу `vX.Y.Z` (маска покрывает prerelease-теги `v1.2.3-rc.1` — публикуются с `--prerelease`): verify → полный QA того же коммита (отказ останавливает релиз) → кросс-сборка → GitHub Release с контрольными суммами и заметками из раздела `CHANGELOG.md` с заголовком тега (отсутствие раздела — ошибка, релиз останавливается). Зеркало `github.com/billydos/components-catalog` обновляется вручную: джоба `github-mirror` (пайплайн основной ветки, `when: manual`) пушит HEAD ветки и все теги по токену из protected-переменной `GITHUB_MIRROR_TOKEN`; в зеркало напрямую не пушат (main — `--force-with-lease` с зеркальной семантикой, теги — обычным push), поэтому релизный воркфлоу GitHub срабатывает только после ручного прогона зеркала.

## Слои и зависимости

- `internal/domain` — обозначения, единицы (коды), классы, ошибки; не знает БД и форматов.
- `internal/storage` — переносимый DML на `database/sql` + диалекты sqlite/postgres; без бизнес-правил.
- `internal/catalog` — чтение каталожных таблиц, движок валидации по правилам из БД.
- `internal/service` — публичный сервисный слой: единственная точка входа для CLI, REST и встраивания.
- `internal/importer` — реестр форматов наполнения (jsonc/yaml/ndjson), семантика секций; тексты ошибок формата — каталог сообщений.
- `internal/i18n` — бандлы отображаемых строк (en — канонический и обязательный, ru), переговоры локали; потребители локализованного рендера — только транспорты (`httpapi`, `cli`) и тесты полноты. Исключение — locale-нейтральное ядро рендера (`Canonical`, `Arg`, `MsgArg`): его использует `internal/domain` для канонического en-рендера сообщений `Error.Message` — бандлы и локали в `domain` не проникают.
- `internal/httpapi`, `internal/cli` — тонкие транспорты над `service`: разбор запросов/аргументов и вывод, без бизнес-логики.
- `internal/testutil` — общий код интеграционных тестов: доступ к локальному PostgreSQL (`CATALOG_TEST_POSTGRES_DSN`) и очистка одноразовой базы; только из `_test.go`.

Корневые пакеты: `components` — публичный фасад встраивания (план 01 §2.4, 04 §1): тонкий реэкспорт алиасами `internal/service`/`internal/importer`/`internal/httpapi` и типов `internal/domain`/`internal/catalog` из их сигнатур, без перестройки слоёв; контракт «внешний потребитель» — пример-модуль `examples/embed` (require + replace на локальный путь), его сборка и запуск — фаза consumer QA-прогонщика. `seed` — стартовый каталог (единицы, условия, группы, параметры, атрибуты, правила, реестры `domain`); применяется `service` на пустую базу при открытии, состав закреплён пин-тестами `seed/seed_test.go` против реестров `internal/domain` и `internal/catalog`. `qa` — кроссплатформенный прогонщик QA `qa/runner` (Go, без sh/bat: сборка, статика, пример встраивания, сценарии CLI/REST на SQLite/PostgreSQL, структурный отчёт `qa-log/1`), нагрузочная прикидка (`load_test.go`), отчёты прогонов — `qa/reports/`.

Направление зависимостей: `domain` ← `catalog`/`storage` ← `service` ← `importer`/`httpapi`/`cli`; `components` — тонкий фасад над `service`/`httpapi`/`importer` плюс алиасы `domain`/`catalog` из сигнатур (без собственной логики); `seed` — над `domain`/`catalog`, потребитель — `service`; `i18n` — отдельно от внутренних слоёв (зависит только от кодов-строк), локали не проникают в `domain`/`catalog`/`storage`/`service`. Не пропускать слои: SQL не поднимается выше `storage`, разбор форматов не выходит из `importer`, бизнес-правила не живут в транспортах.

## Ошибки

- Ошибки — значения: `*domain.Error{Code, MsgID, Args}` из `internal/domain`; без паник и магических строк в слоях выше.
- Код ошибки — машиночитаемая латиница snake_case; реестр — константы `domain.Code…`; дублирование строк кодов по месту использования запрещено.
- Сообщения — каталог (D9, этап 8.3): стабильный MsgID (латиница snake_case, реестр констант `domain.Msg…` в `internal/domain/messages.go`) + аргументы; форматы en (канонический) и ru — бандлы `internal/i18n`. `Message`/`Problem.Message` — канонический en-рендер; локализованный рендер — только транспорты (`Accept-Language`/`--lang`). Новое сообщение — константа + реестр + форматы en/ru одним изменением (полнота закреплена тестом `internal/i18n/messages_test.go`); изменение формата — несовместимое изменение. Аргументы-сообщения — `domain.MsgArg`, не конкатенация строк.
- CLI: ожидаемые ошибки (`*domain.Error`) выводятся с префиксом `Ошибка: `, прочие — `Непредвиденная ошибка: `; код выхода 1 (константы и вывод — `internal/cli`).
- REST: модель `{"code", "message"}`, статусы 400/404/405/409/422/500 — по `04-module-functionality.md` §2.

## Семантика секций (upsert и импорт)

Для секций записи наполнения (`fields`, `attributes`, секции групп параметров, `manufacturers`, `variants`, `analogs`, `synonyms`, `sources`):

- отсутствует или `null` — не менять;
- задана — заменить целиком;
- `[]`/`{}` — очистить;
- ошибка в любом значении секции — запись не применяется вовсе; частичное применение запрещено.

`variants` заменяет набор исполнений целиком вместе с их значениями и атрибутами исполнений (атрибуты — двухуровневые: запись и исполнение, план 03 §7/§10); `manufacturers` — замена списка связей + чистка сирот-производителей; `analogs` — замена только исходящих ссылок (встречные ссылки других записей не затрагиваются, решение D8); `synonyms` — замена исторических названий записи целиком (алиасы записи, не записи и не аналоги — D11: обозначение-синоним канонизируется, уникально в пределах класса, разрешается в запись-владельца в find/поиске); `sources` — замена ссылок на источники данных записи (реестр с библиографией и заметкой места, определения — корневая секция `sources` файла, D13; атрибут `datasheetUrl` упразднён — ссылки на документацию несут `urls` источников). Повторный импорт того же файла — исход `Skipped` по всем записям: без записи в БД и без инкремента ревизий.

## Именование кодов и ключей

- Коды ошибок — латиница snake_case (`invalid_designation`).
- Коды параметров/атрибутов/условий/единиц/групп/систем обозначений — стабильные ключи каталога и формата наполнения (совпадают с ключами JSON; коды единиц — латиница, см. «Единицы»); значения словарей классификации (материалы `si`, `ge`, `ga`, `in`, `sic`, `other`, `gaas`; подклассы `bjt`, `fet`, `zener`, `rectifier`…; подстройка `fixed`, `variable`, `preset`; категории — коды каталожного словаря `categories`; градации значимости параметров — `primary`, `secondary`, `tertiary`, план 03 §5.1) — коды в полях разбора/секции `fields`, ключе `priority` строк каталога и фильтрах; переименование кода каталога — несовместимое изменение формата, экспорт всегда пишет актуальные коды. Отображаемые названия сущностей — бандлы `internal/i18n` (ключ — код; en — канонический и полный, ru — полный; расширения каталога данными без записи в бандле отображаются кодом).
- Секция `fields` формата наполнения — словарная классификация поверх систем (D10): задаёт только поле, которое парсер системы записи не устанавливает сам, и только применимое к классу; значения — коды словарей; семантика секции — общая (замена целиком).
- Коды параметров и условий измерения — международная даташитная номенклатура IEC/JEDEC (U→V: `Vce`, `Vds`, `hfe`, `fT`, `Icbo`, `Idss`, `Ciss`, `RdsOn`…); правила именования «величина/квалификатор» и словарь квалификаторов (пары выводов `ce`/`cb`/`eb`/`ds`/`gs`, суффиксы `Sat`/`Off`/`Th`/`On`/`Max`/`Min`/`Pulse`, JEDEC-буквы `o`/`r`) — `docs/plan/03-data-model.md` §4, §6, §6.9: регистр токена кодирует роль (символ величины, режимы и пределы — с прописной; выводы, свойства-слова и JEDEC-буквы — строчными; составные свойства-слова — camelCase: `coilNom` в `VcoilNom`), словесные коды величин без международного символа — camelCase со строчной первой; новые коды каталога следуют правилам (отклонение — предмет ревью), ru-отображение сохраняет терминологию НТД.
- Таблицы и колонки БД — snake_case, имена — по `02-database.md`; в каталожных таблицах текстовых колонок нет (D9).
- Идентификаторы Go — MixedCaps; имена файлов — snake_case.

## Единицы

- Канонический справочник единиц — данные (таблица `units`); коды единиц — латиница, locale-neutral (`V`, `mV`, `mA`, `uA`, `nA`, `A`, `Hz`, `dB`, `pct`, `W`, `mW`, `var`, `ohm`, `mA_per_V`, `uS`, `pF`, `uH`, `ps`, `ns`, `us`, `ms`, `s`, `degC`, `degC_per_W`, `ppm_per_degC`, `pct_per_degC`, `g`, `mm`, `nm`, `mcd`, `deg`, `h`, `mN_m`, `yr`); названия и символы единиц по локалям — бандлы `internal/i18n` (в БД текстов нет — D9). Фиксированные канонические единицы: сопротивление — ohm, ёмкость — pF, частота — Hz, мощность — W (резисторы, предельные данные конденсаторов) и mW (транзисторы/диоды), ТКС — ppm_per_degC, ТКН — pct_per_degC, крутизна полевых — mA_per_V, выходная полная проводимость (h22, g_os) — uS, ток утечки затвора — nA, времена реле — ms, коммунируемый ток контактов реле — A, углы поворота/срабатывания — deg, момент статического трения — mN_m (гс·см переводятся), минимальная наработка — h, срок сохраняемости — yr (месяцы переводятся); безразмерные величины — unit NULL.
- Даташитные единицы (кОм, МОм, мкФ, нФ, кГц, МГц, ГГц) переводятся в канонические до записи; производные единицы отображения (мкФ, МОм, кГц, МГц) форматирует только слой вывода — в хранилище их нет.

## Переносимость DML

- Только `database/sql` с позиционными аргументами: текст DML — `@имя`-плейсхолдеры, перезапись в `$n` — единая точка `internal/storage/db.go` (`positional` + хелперы `query`/`queryRow`/`exec` и методы диалекта; pgx stdlib имена `@имя` не поддерживает). Переносимые конструкции: `LIMIT/OFFSET`, производные таблицы, `INSERT … SELECT`, `EXISTS`, `INSERT … ON CONFLICT DO NOTHING` (атомарное подавление конфликта уникальности при параллельных писателях postgres; возврат id — метод диалекта `InsertIfAbsentReturningID`, таблицы без суррогатного id — переносимый `Tx.InsertIfAbsent`).
- Булевы значения — INTEGER 0/1; NULL — «не задано»; без JSON-функций СУБД и диалектных типов.
- Всё диалектозависимое (DDL и PK, получение id после вставки, открытие и пулы соединений) — только в `Dialect` (sqlite/postgres) внутри `internal/storage`.
- Весь DML — только в явных транзакциях записи (SQLite: одно выделенное соединение записи, WAL, busy_timeout); вне транзакций — только SELECT из пула чтения. Исключение — обслуживание статистики планировщика после массовой записи: `Dialect.MaintainStats` вне транзакций на пуле записи (docs/plan/02-database.md §4) — ANALYZE/PRAGMA не меняют данные.
- Один и тот же набор интеграционных тестов обязан проходить на SQLite и PostgreSQL.

## Схема: миграции только вперёд от базовой версии

- Свежая база создаётся целиком `EnsureCreated` (`CREATE … IF NOT EXISTS`, сразу актуальная версия); существующая поднимается миграциями — решение D5, регламент `docs/plan/09-schema-migrations.md`.
- Инкремент версии схемы выше `SchemaBaseline` — вместе с шагом реестра миграций (`internal/storage/migrate.go`, `To == SchemaVersion`): непрерывность цепочки закреплена пин-тестом. Эволюция каталога (новые параметры, условия, семейства) — данными, без правки кода и без смены версии схемы.
- Защита от рассинхронизации — `schema_meta.schema_version` (единственный источник истины, журнальной таблицы нет): база новее модуля — `*domain.Error` `schema_version_mismatch`; старее `SchemaBaseline` — `schema_version_unsupported`; отсутствие `schema_meta` — `database_not_initialized`. Тексты сообщений — дословный контракт. Миграция — явное действие (CLI `catalogctl migrate`, `App.Migrate`/`Config.Migrate`), автоматической при чтении нет.

## Зависимости

- База — stdlib. Внешние: `modernc.org/sqlite`, `jackc/pgx/v5`, `tailscale/hujson`, `goccy/go-yaml`, `golang.org/x/sys` (только `qa/runner`: hostinfo на darwin — sysctl, на windows — реестр; pure Go, без cgo). CLI внешних библиотек не использует: разбор аргументов, справка, тексты ошибок и коды выхода — собственный код `internal/cli`.
- Новая зависимость допустима, если: pure Go без cgo, минимум транзитивных, живое сопровождение, заменяет самописный разбор или существенно сокращает код. Граница библиотеки — лексика/синтаксис формата; семантика секций, порядок ключей и русские тексты ошибок — только в `internal/importer`.

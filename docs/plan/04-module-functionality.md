# 04. Функционал модуля (сервисный слой, REST, CLI, интеграция)

## 1. Публичный Go API (фасад библиотеки)

app, err := components.Open(ctx, components.Config{

### 1.1. Интерфейсы сервисного слоя (эскиз)

```go
type DeviceService interface {
    Upsert(ctx, dev DeviceInput) (Outcome, error)   // Added | UpdatedExisting | Skipped:
                                                     // Skipped — слитое состояние записи
                                                     // совпадает с текущим: записи в БД
                                                     // нет, data_revision не инкрементируется
    Create(ctx, dev DeviceInput) (Outcome, error)   // только создание (POST REST): тот же
                                                     // конвейер проверок, что Upsert, но
                                                     // существующий (kind, designation) —
                                                     // ошибка already_exists без применения
                                                     // секций и без изменения базы
                                                     // (409 без мутации по построению)
    Get(ctx, kind, designation) (*Card, bool, error)
    GetByID(ctx, id) (*Card, bool, error)
    Find(ctx, kind, designation) (FindResult, error) // точное совпадение + подсказка
                                                     // равнозначных по материалу
                                                     // (полупроводники)
    Delete(ctx, kind, designation) (bool, error)     // каскад + чистка сирот
    Search(ctx, SearchQuery) (SearchPage, error)     // фильтры, сортировка, пагинация
    Count(ctx, *KindFilter) (int, error)
}

type CatalogService interface {
    Snapshot(ctx) (*CatalogSnapshot, error)          // параметры/атрибуты/условия/единицы/
                                                     // группы/kinds — для UI и валидации
    Import(ctx, CatalogInput, dryRun bool) error     // расширение каталога, метасхема
    Export(ctx, w io.Writer, format Format) error    // round-trip
}

type ImportService interface {
    Import(ctx, r io.Reader, name string, dryRun bool) (ImportReport, error)
    Export(ctx, w io.Writer, format Format, kind *Kind) error
}

type DesignationService interface {
    Parse(ctx, text string) (ParsedDesignation, error) // kind + system + каноническая
                                                      // строка + поля (автодетект)
    Suggest(ctx, prefix string, kind *Kind, limit int) ([]Suggestion, error)
}
```

`SearchQuery`: класс; система обозначений (`gost`/`ost`/`pro`/`jedec`/`jis`/`series`/`other`); префикс/подстрока обозначения; фильтры по полям обозначения (material, subclass, adjustment, category, junctions, group, dev_number, series…; словарные material/subclass/adjustment/category канонизируются на краю: код либо локализованное название → код, словарь category — коды каталога), по атрибутам (код op значение), по параметрам (код op min/max/условие, например `h21e.min ≥ 50`) — фильтр по параметру/атрибуту, неприменимому к классу запроса (D7), — ошибка валидации запроса (`parameter_not_applicable`/`attribute_not_applicable`); сортировка (по умолчанию `(kind, designation)`, также `id` и любое фильтруемое поле; к любому порядку сортировки добавляется финальный `(kind, designation)` — designation уникален только в пределах класса, без этого пагинация недетерминирована); пагинация (`limit` ≤ 200, `offset`; курсор — вне первого релиза). Параметрические фильтры, затрагивающие вариантные параметры, применяются **в пределах одного исполнения** (EXISTS по `device_variants`): запрос `Unom=25 AND diameter≤10` находит записи, у которых габарит исполнения на 25 В не больше 10 мм, а не любые сочетания значений разных исполнений.

Семантика `Upsert`: отсутствует/`null` секция — не менять; задана — заменить целиком; `[]`/`{}` — очистить; ошибка в любом значении секции — запись не применяется вовсе; `manufacturers` — отдельная секция записи (список имён производителей) со стандартной семантикой секций; секция `variants` заменяет набор исполнений целиком вместе с их значениями (атрибуты при этом остаются на уровне типа); секция `analogs` — полная замена исходящих направленных ссылок на аналоги (обозначения того же класса, опционально с заметкой; встречные ссылки других записей не затрагиваются — `03-data-model.md` §8, D8). Идемпотентность повторного импорта: повторное применение того же файла даёт исход `Skipped` по всем записям.

## 2. REST API `/api/v1`

Транспорт: JSON, UTF-8; ошибки — `{ "code": "<машиночитаемый>", "message": "<текст>" }` с корректными HTTP-статусами (400/404/409/422/500); текст сообщения — каталог сообщений по локали запроса (D9, этап 8.3): `Accept-Language`, по умолчанию en, клиенты могут локализовать самостоятельно по `code`. Аутентификация/авторизация/лимитирование — на стороне сайта (модуль не занимается); запись через REST монтируется сайтом только в защищённые маршруты.

Локализация (D9): отображаемые поля ответов (`kind_name`, `system_name`, `name` у атрибутов/групп/параметров, названия и символы единиц в `/catalog`, расшифровки семейств и правила в `/catalog`) заполняются по локали из бандлов `internal/i18n`; локаль запроса — заголовок `Accept-Language` (q-значения, базовый подтег; по умолчанию и при непонятном значении — en). Кодовые поля (`kind`, `system`, `unit`, `parameter`, `attribute`, `section`…) всегда канонические и от локали не зависят; `unit` в значениях карточки — канонический код единицы.

| Метод и путь | Назначение |
|--------------|-----------|
| `GET /api/v1/kinds` | классы приборов |
| `GET /api/v1/catalog` | снимок каталога (параметры/атрибуты/условия/единицы/группы/системы обозначений/семейства) — для построения форм и фильтров; `ETag` по `catalog_revision` |
| `GET /api/v1/components?kind=&system=&q=&<поля обозначения>=&attr.<код>=&par.<код>.min=&sort=&limit=&offset=` | поиск: подстрока обозначения, система, фильтры полей/атрибутов/параметров, сортировка, пагинация; ответ — список с обозначением, классом, системой и ключевыми полями; `ETag` по `data_revision` и канонической строке запроса (разные фильтры — разные ETag; разбор и сервисная валидация запроса предшествуют 304) |
| `GET /api/v1/components/{kind}/{designation}` | карточка: обозначение + система + поля, атрибуты, значения параметров по группам с условиями, исполнения-варианты (матрица «номинал × напряжение → габариты/масса»), аналоги, производители; 404 — не найдено |
| `GET /api/v1/components/id/{id}` | карточка по стабильному id |
| `GET /api/v1/suggest?q=&kind=&limit=` | автодополнение по префиксу обозначения; входит в первый релиз, может отключаться конфигурацией модуля (хендлер не монтируется) |
| `POST /api/v1/components` | создание (тело = запись наполнения: name/system + секции, включая классификационную `fields` — план 03 §2.5); существующий `(kind, designation)` — 409 `already_exists` без изменения записи (сервисный `Create` атомарно отказывает) |
| `PUT /api/v1/components/{kind}/{designation}` | upsert с семантикой секций; `name` тела обязан совпадать с designation пути (иначе 422 `designation_mismatch`) |
| `DELETE /api/v1/components/{kind}/{designation}` | удаление (каскад) |
| `GET /api/v1/stats` | количества по классам, версия схемы, ревизии |

Обозначение в пути URL-кодируется; обозначения, содержащие символ `/` (например, MIL-имена `M39003/…`), адресуются через `GET /components/id/{id}` или поиск — прямой путь для них не гарантируется (роутеры по-разному трактуют `%2F`).

OpenAPI 3.1-спецификация (`api/openapi.yaml`) — обязательный артефакт этапа 5; хендлеры пишутся по спецификации, контракт закрепляется тестами через `httptest`.

Замечания по фильтрации параметров: фильтр `par.<код>.min=N` отбирает записи, у которых хотя бы одно значение параметра удовлетворяет условию (EXISTS по `parameter_values`); фильтр по параметру/атрибуту, неприменимому к классу запроса, — 400 `parameter_not_applicable`/`attribute_not_applicable` (D7); фильтры по условиям значений (`par.KShum.freq=…`) — второй очередью, если понадобятся UI.

## 3. CLI (`catalogctl`)

Команды: `init`, `parse <обозначение>…` (автодетект класса и системы; без `--db/--dsn` — стартовый реестр домена), `add <обозначение>…`, `import <файл> [--dry-run]` (формат — по расширению имени; «-» — stdin), `list [фильтры]` (`--kind`, `--system`, `--material`, `--subclass`, `--adjustment`, `--category`, `--junctions`, `--group`, `--series`, `--number`, `--letters`, `--q`, `--limit`…), `info <обозначение>`, `find <обозначение>` (подсказка равнозначных по материалу — только `gost`), `delete <обозначение>… [--dry-run]`, `count [--kind]`, `export [--kind] [--format jsonc|yaml|ndjson]` (устройства, round-trip формат наполнения), `catalog export|import|list` (`list` — справка из каталога: классы, системы, группы/секции, параметры, атрибуты), `help [команда]`.

Команды `info`/`find`/`delete`/`add` разрешают класс автодетектом по обозначению; при неоднозначности или системе `other` обязателен `--kind`. Общие опции: `--db/--dsn`, `--dialect`, `--system`, `--kind`, `--dry-run`, `--lang en|ru` (локаль вывода отображаемых строк — названия классов/систем/групп/параметров/атрибутов, символы единиц; по умолчанию en — D9). Вывод: ожидаемые ошибки — префикс локали («Error: »/«Ошибка: »), прочие — «Unexpected error: »/«Непредвиденная ошибка: », код выхода 1; сообщения и интерфейсные строки (заголовки, справка, итоги прогона) — каталог сообщений по `--lang`, тексты — контракт.

## 4. Формат наполнения

- jsonc/json и yaml/yml (реестр форматов) и ndjson; корень:

```jsonc
{
  "catalog": { … },        // опционально: расширение каталога (метасхема) — параметры,
                           // атрибуты, условия, семейства series
  "transistors": [ … ],
  "diodes": [ … ],
  "resistors": [ … ],
  "capacitors": [ … ]
}
```

- запись: `"КТ315Б"` | `{"name": …}` | `{"name": …, "system": "pro"}` (ключ `system` необязателен — автодетект; обязателен для `other`) + секции `attributes`, `parameters`, `ratings`, `dimensions` (имена секций — из групп каталога; форма всех секций групп — единые списки объектов, `06-examples.md`), `manufacturers` (список имён производителей), `variants` (исполнения: метка + те же секции групп, см. `03-data-model.md` §7) и `analogs` (исходящие ссылки на аналоги, см. `03-data-model.md` §8); ключи атрибутов и условий в файле — их коды (отдельных jsonc_key нет; переименование кода каталога — несовместимое изменение формата, экспорт всегда пишет актуальные коды); порядок элементов массивов секций — это `sort_order` значений и вариантов (экспорт порядок сохраняет);
- Issues-модель: корневые проблемы + проблемы записей накапливаются за один прогон; жёсткая ошибка — только синтаксис формата; дубликаты ключей — ошибка разбора файла (тихая потеря данных недопустима);
- NDJSON (`.ndjson`, одна JSON-строка — одна сущность) — машинный потоковый формат реестра для больших объёмов (10⁴–10⁵ записей): построчный разбор без загрузки файла целиком, конкатенация файлов и частичный догрузочный импорт; записи выражаются строками-обёртками `{"<класс>": <запись>}`; блок `catalog` разбивается по подразделам — по одной строке-обёртке `{"catalog": {"<подраздел>": […]}}` на подраздел (units, categories, conditions, parameter_groups, parameters, attributes, series_families, …); строк `catalog` может быть несколько, они сливаются до валидации метасхемы; блок(и) `catalog` должны предшествовать записям, использующим вводимые ими определения; Issues-модель та же; комментариев и якорей нет — для ручного редактирования и ревью остаются jsonc/yaml;
- ключи полей подразделов секции `catalog` повторяют колонки каталожных таблиц (snake_case: `code`, `value_type`, `condition_sets`, `enum_values`, `is_active`, …), ключи ссылок — коды (систем, классов, групп, условий, правил, единиц — латиница); текстовых ключей `name`/`description`/`symbol`/`display_name` формат не содержит (D9: отображаемые строки — бандлы `internal/i18n`, не данные); эталон формы — `catalog export` (round-trip);
- экспорт — тот же формат (round-trip), включая каталог (`catalog export`); все форматы реестра, по умолчанию — jsonc, NDJSON — явным указанием формата.

## 5. Интеграция в веб-бэкэнд

- **Встраивание**: модуль не запускает серверов, не читает глобальных флагов/env (кроме явной передачи конфигурации); сайт создаёт `App` при старте и закрывает при завершении. SQLite: пул чтения + одно соединение записи на процесс; WAL + `busy_timeout` позволяют сайту и CLI работать с одним файлом одновременно (запись сериализуется на уровне файла — один пишущий `App` на базу, читатели не блокируются записью); несколько пишущих `App` на одну базу SQLite не допускается.
- **Читаемость данных сайтом напрямую** (мимо модуля) не поддерживается и не гарантируется: единственная гарантия совместимости — REST/Go API и схема `schema_meta`.
- **Кэширование**: `ETag` (`catalog_revision` — на `GET /catalog`; `data_revision` + каноническая строка запроса — на `GET /components`); сайт может кэшировать снимок каталога до смены версии.
- **Наблюдаемость**: `log/slog` (передаётся сайтом); хук метрик (интерфейс) — счётчики и гистограммы вызовов/ошибок по операциям; трассировка — через `context.Context` сайта.
- **Производительность**: целевые ориентиры первого релиза — поиск с фильтрами по 10⁴–10⁵ устройств ≤ 100 мс (индексы из `02-database.md`), карточка ≤ 20 мс; при росте — денормализация/материализация вынесенных фильтров, не меняя публичный API.
- **Деплой**: модуль компилируется в бинарник сайта (или отдельный сервис — по желанию сайта, REST это позволяет); cgo не требуется (pure Go драйверы).
- **Подбор аналогов**: автоматическое сопоставление компонентов по характеристикам/атрибутам — на стороне сайта, не в модуле; модуль предоставляет для него параметрический поиск и нормализованные данные; прямые ссылки-аналоги — данные модуля.

## 6. Функциональные границы первого релиза

Входит: 4 класса, парсеры систем обозначений (ГОСТ/ОСТ, PRO ELECTRON, JEDEC, JIS — строгие грамматики; серии по реестру-данным; `other` без разбора), каталог-данные с движком валидации и применимостью параметров/атрибутов (D7), EAV-хранение, семантика секций, поиск/фильтры/пагинация, suggest (отключаемый конфигурацией), аналоги (направленные исходящие ссылки, несколько на запись; встречные — отображение на карточке), импорт/экспорт jsonc/yaml/ndjson, CLI, REST v1 + OpenAPI, метрики-хук, ETag, версия схемы.

Не входит (явно): аутентификация/авторизация; автоматический подбор аналогов/заменителей по характеристикам (задача бэкэнда-потребителя); полнотекстовый поиск по атрибутам; изображения/сканы (только `datasheetUrl`); версионирование данных устройств (история правок); изменение каталога через REST (каталог расширяется файлами наполнения через CLI/Go API); миграции схемы (D5).

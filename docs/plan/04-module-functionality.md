### 1.1. Интерфейсы сервисного слоя (эскиз)

```go
type DeviceService interface {
    Upsert(ctx, dev DeviceInput) (Outcome, error)   // Added | UpdatedExisting | Skipped:
                                                     // Skipped — слитое состояние записи
                                                     // совпадает с текущим: записи в БД
                                                     // нет, data_revision не инкрементируется
    Create(ctx, dev DeviceInput) (Outcome, error)   // только создание (POST REST): тот же
                                                     // конвейер проверок, что Upsert, но
                                                     // существующий (kind, designation) —
                                                     // ошибка already_exists без применения
                                                     // секций и без изменения базы
                                                     // (409 без мутации по построению)
    Get(ctx, kind, designation) (*Card, bool, error)
    GetByID(ctx, id) (*Card, bool, error)
    Find(ctx, kind, designation) (FindResult, error) // точное совпадение → синоним
                                                      // (историческое название, помечается)
                                                      // → подсказка равнозначных
                                                      // по материалу (полупроводники)
                                                      // и соседом по типу (поле base,
                                                      // 03 §2.6, §9)
    Delete(ctx, kind, designation) (bool, error)     // каскад + чистка сирот
    Search(ctx, SearchQuery) (SearchPage, error)     // фильтры, сортировка, пагинация
    Count(ctx, *KindFilter) (int, error)
    Changes(ctx, after int64, limit int) (ChangesPage, error)
                                                       // поток событий изменений записей
                                                       // (change feed): события
                                                      // created/updated/deleted с классом,
                                                      // обозначением и стабильным id;
                                                      // курсор — монотонный id события
                                                      // (after), Skipped событий не
                                                      // оставляет; покрывает только
                                                      // data_revision (каталог — ETag
                                                      // /catalog), лимиты — 100/1000
}

type CatalogService interface {
    Snapshot(ctx) (*CatalogSnapshot, error)          // параметры/атрибуты/условия/единицы/
                                                     // группы/kinds — для UI и валидации
    Import(ctx, CatalogInput, dryRun bool) error     // расширение каталога, метасхема
    Export(ctx, w io.Writer, format Format) error    // round-trip
}

type ImportService interface {
    Import(ctx, r io.Reader, name string, dryRun bool, opts ...ImportOption) (ImportReport, error)
                                                      // потоковое чтение (NDJSON — построчно,
                                                      // без загрузки файла целиком); опция
                                                       // WithProgress — колбэк нарастающих
                                                      // счётчиков чтения и применения записей
    Export(ctx, w io.Writer, format Format, kind *Kind) error
}

type DesignationService interface {
    Parse(ctx, text string) (ParsedDesignation, error) // kind + system + каноническая
                                                      // строка + поля (автодетект)
    Suggest(ctx, prefix string, kind *Kind, limit int) ([]Suggestion, error)
}
```

`SearchQuery`: класс; система обозначений (`gost`/`ost`/`pro`/`jedec`/`jis`/`other`); префикс/подстрока обозначения; фильтр по набору стабильных id (до 200 положительных значений; пересечение с прочими фильтрами, дырки — id без записи либо отсечённые фильтрами — просто отсутствие строки в выдаче; без явной сортировки порядок выдачи — порядок передачи id; REST — повторяемый параметр `id`, дубликат значения — ошибка валидации); фильтры по полям обозначения (material, subclass, adjustment, category, junctions, group, dev_number, series, base…; словарные material/subclass/adjustment/category канонизируются на краю: код либо локализованное название → код, словарь category — коды каталога; REST — словарные поля повторяемы (мультивыбор): каждое значение канонизируется отдельно, набор — семантика ИЛИ внутри поля, дубликат канонического кода — ошибка валидации; base — базовое обозначение (тип) записи, значение канонизируется как обозначение (03-data-model.md §2.6); поля series/dev_number/letters у записей other — из секции fields), по атрибутам (код op значение), по параметрам (код op min/max/условие, например `hfe.min ≥ 50`) — фильтр по параметру/атрибуту, неприменимому к классу запроса (D7), — ошибка валидации запроса (`parameter_not_applicable`/`attribute_not_applicable`); сортировка (по умолчанию `(kind, designation)`, также `id`, любое фильтруемое поле и код числового параметра каталога, применимого к классу запроса; значение записи по параметру — MIN нижних границ на возрастание и MAX верхних на убывание с падением COALESCE на точное/единственную границу (намеренно определено для любой численной строки — в отличие от фасетов `ParameterBounds`, где односторонние формы нижнюю/верхнюю грань не приближают), в сортировочное значение входят и вариантные значения — как в фильтрах; text/enum-параметры и неприменимые — ошибка валидации запроса; к любому порядку сортировки добавляется финальный `(kind, designation)` — designation уникален только в пределах класса, без этого пагинация недетерминирована); пагинация (`limit` ≤ 200, `offset`; курсор — вне первого релиза). Параметрические фильтры, затрагивающие вариантные параметры, применяются **в пределах одного исполнения** (EXISTS по `device_variants`): запрос `Vnom=25 AND diameter≤10` находит записи, у которых габарит исполнения на 25 В не больше 10 мм, а не любые сочетания значений разных исполнений.

Семантика `Upsert`: отсутствует/`null` секция — не менять; задана — заменить целиком; `[]`/`{}` — очистить; ошибка в любом значении секции — запись не применяется вовсе; `manufacturers` — отдельная секция записи (список имён производителей) со стандартной семантикой секций; секция `variants` заменяет набор исполнений целиком вместе с их значениями (атрибуты при этом остаются на уровне типа); секция `analogs` — полная замена исходящих направленных ссылок на аналоги (обозначения того же класса, опционально с заметкой; встречные ссылки других записей не затрагиваются — `03-data-model.md` §8, D8); секция `synonyms` — полная замена исторических названий записи (строки либо объекты `{name, note, yearFrom, yearTo}`; канонизация обозначений, уникальность в пределах класса, границы годов — `03-data-model.md` §9, D11; создание записи с обозначением, занятым синонимом другой записи, — отказ `already_exists`). Идемпотентность повторного импорта: повторное применение того же файла даёт исход `Skipped` по всем записям — каноническое сравнение слитого состояния выполняется до валидации, поэтому эволюция каталога (деактивация параметра/атрибута) не делает существующие записи неотрекаемыми. `DryRun` (контрольный прогон без записи в БД) возвращает исход, который вернул бы `Upsert`: помимо плана создаваемых записей (разрешение ссылок-аналогов вперёд) он ведёт последовательную симуляцию применённой части прогона — созданные записи и заявки синонимов регистрируются по порядку файла после успешной проверки, поэтому конфликты уникальности синонимов dry-run видит в той же записи файла, что и реальный импорт. Остаточное ограничение: изменённый upsert записи, чьи незатронутые секции ссылаются на деактивированные параметры, отвергается целиком — чтобы изменить такую запись, сначала замените или очистите секции с неактивными параметрами.

## 2. REST API `/api/v1`

Транспорт: JSON, UTF-8; ошибки — `{ "code": "<машиночитаемый>", "message": "<текст>" }` с корректными HTTP-статусами (400/404/405+Allow/409/422/500; неизвестный путь — 404 `api_route_not_found`); текст сообщения — каталог сообщений по локали запроса (D9, этап 8.3): `Accept-Language`, по умолчанию en, клиенты могут локализовать самостоятельно по `code`. Аутентификация/авторизация/лимитирование — на стороне сайта (модуль не занимается); запись через REST монтируется сайтом только в защищённые маршруты.

Локализация (D9): отображаемые поля ответов (`kind_name`, `system_name`, `name` у атрибутов/групп/параметров, названия и символы единиц в `/catalog`, названия значений словарей полей обозначения (`dictionaries`) в `/catalog`, описания правил в `/catalog`) заполняются по локали из бандлов `internal/i18n`; локаль запроса — заголовок `Accept-Language` (q-значения, базовый подтег; по умолчанию и при непонятном значении — en). Кодовые поля (`kind`, `system`, `unit`, `parameter`, `attribute`, `section`…) всегда канонические и от локали не зависят; `unit` в значениях карточки — канонический код единицы.

| Метод и путь | Назначение |
|--------------|-----------|
| `GET /api/v1/kinds` | классы приборов |
| `GET /api/v1/catalog` | снимок каталога (параметры/атрибуты/условия/единицы/группы/системы обозначений, словари значений словарных полей обозначения — `dictionaries`: material/subclass/adjustment из реестров домена, category из словаря каталога) — для построения форм и фильтров; `ETag` по `catalog_revision` |
| `GET /api/v1/components?kind=&system=&q=&id=&<поля обозначения>=&attr.<код>=&par.<код>.min=&values=&sort=&limit=&offset=` | поиск: подстрока обозначения, система, фильтр по набору стабильных id (`id` — повторяемый параметр, ≤ 200 значений: пересечение с прочими фильтрами, без `sort` — порядок передачи id), мультивыбор словарных фильтров (`material`/`subclass`/`adjustment`/`category` повторяемы — семантика ИЛИ внутри поля, дубликат канонического кода — 400; повтор прочих параметров — 400), фильтры полей/атрибутов/параметров, сортировка (в `sort` допустимы коды числовых параметров, применимых к классу запроса: агрегирующая производная таблица по `parameter_values`, записи без значения — в конце), колонки значений (`values` — повторяемый параметр, ≤ 16 кодов параметров либо `attr.<код>`: пакетная проекция значений в `items[].values` формы CardValue; численные при нескольких строках записи — агрегат границ MIN/MAX, текстовые/enum — данные типа поверх исполнений; логические атрибуты и неприменимые к классу коды — 400), пагинация; ответ — список с обозначением, классом, системой и ключевыми полями; `ETag` по `data_revision` и канонической строке запроса (разные фильтры — разные ETag; разбор и сервисная валидация запроса предшествуют 304) |
| `GET /api/v1/components/{kind}/{designation}` | карточка: обозначение + система + поля, атрибуты, значения параметров по группам с условиями, исполнения-варианты (матрица «номинал × напряжение → габариты/масса»), группа типа (`type_group`: соседние записи того же базового обозначения и мини-матрица различий данных типа — 03-data-model.md §2.6; опущено без соседей), аналоги, производители; 404 — не найдено |
| `GET /api/v1/components/id/{id}` | карточка по стабильному id |
| `GET /api/v1/suggest?q=&kind=&limit=` | автодополнение по префиксу обозначения; входит в первый релиз, может отключаться конфигурацией модуля (хендлер не монтируется) |
| `GET /api/v1/parse?designation=&system=&kind=` | разбор обозначения (основа UX ввода обозначения на сайте): без `system` — автодетект (порядок 03 §2.4), с `system` — явная система (`other` — только с явным `kind`); обозначение канонизируется; ответ — класс, система, каноническое обозначение, поля разбора и кандидаты: все успешные строгие разборы в порядке автодетекта без дублей пары класс/система — эквивалент «конфиденса» строгих грамматик (первый кандидат при автодетекте совпадает с основным результатом; числовой уверенности нет) |
| `POST /api/v1/components` | создание (тело = запись наполнения: name/system + секции, включая классификационную `fields` — план 03 §2.5); существующий `(kind, designation)` — 409 `already_exists` без изменения записи (сервисный `Create` атомарно отказывает) |
| `PUT /api/v1/components/{kind}/{designation}` | upsert с семантикой секций; `name` тела обязан совпадать с designation пути (иначе 422 `designation_mismatch`) |
| `DELETE /api/v1/components/{kind}/{designation}` | удаление (каскад) |
| `GET /api/v1/stats` | количества по классам, версия схемы, ревизии; `?kind=<код>` — фасетные агрегаты значений параметров класса: min/max численных параметров для слайдеров фильтров (семантика границ — как у параметрических фильтров поиска: `value_min`/`value_max` и `value_exact`; `at_least` задаёт только min, `at_most` — только max) и частоты текстовых/enum значений по записям класса (значение в нескольких исполнениях одной записи считается один раз); данные типа и исполнений, параметры без данных и неприменимые к классу (D7, включая данные, оставшиеся после изменения применимости каталогом) не входят, порядок — алфавит кодов, повтор параметра и посторонний ключ запроса — 400 |
| `GET /api/v1/changes?after=&limit=` | поток событий изменений записей (change feed) для инкрементальной синхронизации производных индексов: события `created`/`updated`/`deleted` с классом, обозначением и стабильным id записи в порядке возрастания id события; курсор — монотонный id события (`after=0` — с начала фида; не ревизия: id присваивается вставкой и остаётся плотным курсором, связь ревизии с событиями — деталь пути записи), `limit` ≤ 1000 (по умолчанию 100); ответ — события (всегда массив) и текущая `data_revision`; события пишет та же транзакция, что меняет данные (исход `Skipped` событий не оставляет, компенсационные удаления импортёра — штатный `deleted`); фид покрывает только `data_revision` — изменения каталога отслеживаются ETag `/catalog`; акторов и before/after нет (не аудит); автоматической ретенции нет — очистка вручную SQL, REST-пути очистки нет |
| `POST /api/v1/import` | потоковый импорт файла наполнения: тело — NDJSON (строки-обёртки записей и блок `catalog` строками-подразделами до записей, §4), чтение построчное без потолка тела запроса — память ограничена потолком строки сканера (16 МиБ); ответ — синхронный отчёт после EOF (счётчики исходов + Issues — полный список проблем прогона; 200 и при проблемных записях); жёсткая ошибка — только синтаксис формата и чтение потока (400 `invalid_import_file`); единственный параметр запроса — `dry_run=true|false` (контрольный прогон без записи в БД, как у Go API и CLI; значение строго true либо false, повтор — 400), прочие ключи — 400; прогресс по REST не отдаётся (запрос синхронный, наблюдение — хук метрик сайта); запись монтируется сайтом только в защищённые маршруты |

Обозначение в пути URL-кодируется; обозначения, содержащие символ `/` (например, MIL-имена `M39003/…`), адресуются через `GET /components/id/{id}` или поиск — прямой путь для них не гарантируется (роутеры по-разному трактуют `%2F`).

OpenAPI 3.1-спецификация (`api/openapi.yaml`) — обязательный артефакт этапа 5; хендлеры пишутся по спецификации, контракт закрепляется тестами через `httptest`.

Замечания по фильтрации параметров: фильтр `par.<код>.min=N` отбирает записи, у которых хотя бы одно значение параметра удовлетворяет условию (EXISTS по `parameter_values`); фильтр по параметру/атрибуту, неприменимому к классу запроса, — 400 `parameter_not_applicable`/`attribute_not_applicable` (D7); фильтры по условиям значений (`par.NF.freq=…`) — второй очередью, если понадобятся UI.

## 3. CLI (`catalogctl`)

Команды: `init`, `parse <обозначение>…` (автодетект класса и системы; без `--db/--dsn` — стартовый реестр домена), `add <обозначение>…`, `import <файл> [--dry-run]` (формат — по расширению имени; «-» — stdin), `list [all] [фильтры]` (`--kind`, `--system`, `--material`, `--subclass`, `--adjustment`, `--category`, `--junctions`, `--group`, `--series`, `--number`, `--letters`, `--base` (тип записи — значение канонизируется как обозначение), `--q`, `--limit`…; необязательный позиционный аргумент `all` — вывести все записи без пагинации: CLI итерирует страницы поиска по потолку limit, сервисный контракт пагинации не меняется; несовместим с `--limit`/`--offset`), `info <обозначение>` (карточка, включая секцию «группа типа» с мини-матрицей различий), `find <обозначение>` (точное обозначение, затем синоним — историческое название записи с пометкой «найдено по синониму», затем подсказка равнозначных по материалу — только `gost`; далее сосед по типу — та же база обозначения с иной буквой классификации), `delete <обозначение>… [--dry-run]`, `count [--kind]`, `export [--kind] [--format jsonc|yaml|ndjson]` (устройства, round-trip формат наполнения), `catalog export|import|list` (`list` — справка из каталога: классы, системы, группы/секции, параметры, атрибуты), `version` (версия сборки; значение внедряется релизной сборкой через `-ldflags -X …/internal/cli.Version`), `help [команда]`. Общая справка (`catalogctl help`) собирается генератором по реестру команд: секции команд, общих опций и примеров, примечание о позиции опций; карточка `help <команда>` (и `help catalog <подкоманда>`) — строка использования с полным набором флагов реестра и описания опций; строки использования в ошибках числа аргументов — те же сообщения.

Команды `info`/`find`/`delete`/`add` разрешают класс автодетектом по обозначению; при неоднозначности или системе `other` обязателен `--kind`. Общие опции: `--db/--dsn`, `--dialect`, `--system`, `--kind`, `--dry-run`, `--lang en|ru` (локаль вывода отображаемых строк — названия классов/систем/групп/параметров/атрибутов, символы единиц; по умолчанию en — D9). Разбор аргументов — собственный код `internal/cli` по реестру команд, без CLI-библиотек: контрактная лексика флагов — форма флага ровно два дефиса («-имя»/«---имя» — неизвестный флаг), значение флага не может быть следующим флагом, булев флаг не принимает «--имя=значение», каждое вхождение флага проверяется на месте (повторное — перезаписывает значение), «--» — конец флагов (далее — позиционные аргументы), опции задаются после команды (и после подкоманды `catalog`). Вывод: ожидаемые ошибки — префикс локали («Error: »/«Ошибка: »), прочие — «Unexpected error: »/«Непредвиденная ошибка: », код выхода 1; сообщения и интерфейсные строки (заголовки, справка, итоги прогона) — каталог сообщений по `--lang`, тексты — контракт.

## 4. Формат наполнения

- jsonc/json и yaml/yml (реестр форматов) и ndjson; корень:

```jsonc
{
  "catalog": { … },        // опционально: расширение каталога (метасхема) — параметры,
                           // атрибуты, условия, категории
  "transistors": [ … ],
  "diodes": [ … ],
  "resistors": [ … ],
  "capacitors": [ … ],
  "relays": [ … ]
}
```

- запись: `"КТ315Б"` | `{"name": …}` | `{"name": …, "system": "pro"}` (ключ `system` необязателен — автодетект; обязателен для `other`) + секции `attributes`, `parameters`, `ratings`, `dimensions` (имена секций — из групп каталога; форма всех секций групп — единые списки объектов, `06-examples.md`), `manufacturers` (список имён производителей), `variants` (исполнения: метка + те же секции групп, см. `03-data-model.md` §7), `analogs` (исходящие ссылки на аналоги, см. `03-data-model.md` §8) и `synonyms` (исторические названия записи: строки либо объекты `{name, note, yearFrom, yearTo}`, см. `03-data-model.md` §9); ключи атрибутов и условий в файле — их коды (отдельных jsonc_key нет; переименование кода каталога — несовместимое изменение формата, экспорт всегда пишет актуальные коды); порядок элементов массивов секций — это `sort_order` значений и вариантов (экспорт порядок сохраняет);
- Issues-модель: корневые проблемы + проблемы записей накапливаются за один прогон; жёсткая ошибка — только синтаксис формата; дубликаты ключей — ошибка разбора файла (тихая потеря данных недопустима);
- NDJSON (`.ndjson`, одна JSON-строка — одна сущность) — машинный потоковый формат реестра для больших объёмов (10⁴–10⁵ записей): построчный разбор без загрузки файла целиком, конкатенация файлов и частичный догрузочный импорт; записи выражаются строками-обёртками `{"<класс>": <запись>}`; блок `catalog` разбивается по подразделам — по одной строке-обёртке `{"catalog": {"<подраздел>": […]}}` на подраздел (units, categories, conditions, parameter_groups, parameters, attributes, …); строк `catalog` может быть несколько, они сливаются до валидации метасхемы; блок(и) `catalog` должны предшествовать записям, использующим вводимые ими определения; Issues-модель та же; комментариев и якорей нет — для ручного редактирования и ревью остаются jsonc/yaml;
- ключи полей подразделов секции `catalog` повторяют колонки каталожных таблиц (snake_case: `code`, `value_type`, `condition_sets`, `enum_values`, `is_active`, …), ключи ссылок — коды (систем, классов, групп, условий, правил, единиц — латиница); текстовых ключей `name`/`description`/`symbol`/`display_name` формат не содержит (D9: отображаемые строки — бандлы `internal/i18n`, не данные); эталон формы — `catalog export` (round-trip);
- экспорт — тот же формат (round-trip), включая каталог (`catalog export`); все форматы реестра, по умолчанию — jsonc, NDJSON — явным указанием формата.

## 5. Интеграция в веб-бэкэнд

- **Встраивание**: модуль не запускает серверов, не читает глобальных флагов/env (кроме явной передачи конфигурации); сайт создаёт `App` при старте и закрывает при завершении. SQLite: пул чтения + одно соединение записи на процесс; WAL + `busy_timeout` позволяют сайту и CLI работать с одним файлом одновременно (запись сериализуется на уровне файла — один пишущий `App` на базу, читатели не блокируются записью); несколько пишущих `App` на одну базу SQLite не допускается.
- **Читаемость данных сайтом напрямую** (мимо модуля) не поддерживается и не гарантируется: единственная гарантия совместимости — REST/Go API и схема `schema_meta`.
- **Кэширование**: `ETag` (`catalog_revision` — на `GET /catalog`; `data_revision` + каноническая строка запроса — на `GET /components`); сайт может кэшировать снимок каталога до смены версии.
- **Наблюдаемость**: `log/slog` (передаётся сайтом); хук метрик (интерфейс) — счётчики и гистограммы вызовов/ошибок по операциям; трассировка — через `context.Context` сайта.
- **Производительность**: целевые ориентиры первого релиза — поиск с фильтрами по 10⁴–10⁵ устройств ≤ 100 мс (индексы из `02-database.md`), карточка ≤ 20 мс; при росте — денормализация/материализация вынесенных фильтров, не меняя публичный API.
- **Деплой**: модуль компилируется в бинарник сайта (или отдельный сервис — по желанию сайта, REST это позволяет); cgo не требуется (pure Go драйверы).
- **Подбор аналогов**: автоматическое сопоставление компонентов по характеристикам/атрибутам — на стороне сайта, не в модуле; модуль предоставляет для него параметрический поиск и нормализованные данные; прямые ссылки-аналоги — данные модуля.

## 6. Функциональные границы первого релиза

Входит: 5 классов, парсеры систем обозначений (ГОСТ/ОСТ, PRO ELECTRON, JEDEC, JIS — строгие грамматики; серии по реестру-данным; `other` без разбора), каталог-данные с движком валидации и применимостью параметров/атрибутов (D7), EAV-хранение, семантика секций, поиск/фильтры/пагинация, suggest (отключаемый конфигурацией), аналоги (направленные исходящие ссылки, несколько на запись; встречные — отображение на карточке), импорт/экспорт jsonc/yaml/ndjson, CLI, REST v1 + OpenAPI, метрики-хук, ETag, версия схемы.

Не входит (явно): аутентификация/авторизация; автоматический подбор аналогов/заменителей по характеристикам (задача бэкэнда-потребителя); полнотекстовый поиск по атрибутам; изображения/сканы (только `datasheetUrl`); версионирование данных устройств (история правок); изменение каталога через REST (каталог расширяется файлами наполнения через CLI/Go API); миграции схемы (D5).

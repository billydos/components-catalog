# План проекта «Справочник электронных компонентов»

Рабочее имя модуля: **components-catalog** (рабочее имя пакета Go: `componentscatalog`; совпадает с именем репозитория; лицензия — MIT; путь импорта Go зависит от хостинга, фиксируется на этапе 0). Проект разрабатывается с нуля и охватывает советскую и мировую элементную базу. План самодостаточен: все правила, семантика и контракты зафиксированы в его документах.

## Назначение

Локальный/встраиваемый справочник электронных компонентов (советская и мировая элементная база) четырёх классов — **транзисторы, диоды, резисторы, конденсаторы** — с несколькими системами обозначений (ГОСТ/ОСТ, PRO ELECTRON, JEDEC, JIS, `other`), электрическими параметрами с условиями измерения, предельными эксплуатационными данными, массогабаритными и описательными атрибутами. Проект — **модуль веб-бэкэнда** (не бэкэнд целиком): Go-библиотека с сервисным слоем + встраиваемый версияемый REST API; консольная утилита — админ-инструмент над той же библиотекой.

## Ключевые архитектурные решения (зафиксированы)

| # | Решение | Мотивация |
|---|---------|-----------|
| D1 | **Каталог параметров/атрибутов — данные в БД.** Коды, названия, единицы, типы значений, границы, комбинации условий и enum-значения хранятся в каталожных таблицах и расширяются без правки кода. Сложные межполевые правила — именованные валидаторы в коде, привязка — данными | Справочник наполняют редакторы, а не разработчики: новый параметр не должен требовать правки кода, пересборки и пересоздания БД |
| D2 | **Значения — EAV: строка на значение.** Таблица значений параметров + таблица условий измерения; атрибуты — ключ-значение; поля обозначения — ключ-значение | Четыре класса приборов с разными наборами данных: типизированные колонки дали бы разреженную таблицу и `ALTER TABLE` на каждое новое условие/атрибут |
| D3 | **SQLite и PostgreSQL равноправны.** Переносимое ядро DML на `database/sql` + два диалекта (DDL, открытие, пулы). Для PostgreSQL — пул соединений; SQLite — пул чтения + одно выделенное соединение записи (WAL + `busy_timeout`) | Справочник одинаково работает как встраиваемая локальная база и как серверная база веб-бэкэнда; переносимость не должна быть «заделом», а свойством ядра |
| D4 | **Модуль = Go-библиотека + REST API.** Слои: домен → каталог → хранилище → сервисы; тонкий версияемый REST-слой (`net/http`) внутри модуля; CLI над сервисами | Ядро — библиотека, встраиваемая в сайт напрямую; REST и CLI — лишь два транспорта над одним сервисным слоем, без дублирования бизнес-логики |
| D5 | **Без миграций схемы.** Изменение схемы = пересоздание базы импортом (данные справочные, восстанавливаются из файлов наполнения). Защита от рассинхронизации — таблица `schema_meta` с версией схемы: модуль отказывается работать с базой другой версии с внятной ошибкой | Данные справочные и восстановимы из файлов наполнения; стоимость миграций в первом релизе выше выгоды, а тихая порча данных исключена версией схемы |
| D6 | **Исполнения (варианты) типа.** Зависимости «номинал × напряжение → габариты/масса» — норма для электролитических конденсаторов (`К50-35`: 1 мкФ выпускается только на 160 В) и ряды мощностей резисторов (`С2-33`: 0.125–2 Вт, габариты зависят от мощности). Вариант — группа значений параметров внутри записи типа: свои `Unom`/`Cnom` и свои массогабаритные данные | Плоский набор значений на запись таких зависимостей не выражает, а отдельная запись на каждое сочетание ломала бы принцип «обозначение — точный ключ»: напряжение в обозначение К-системы не входит |
| D7 | **Применимость параметров/атрибутов — многие-ко-многим.** Таблицы `parameter_kinds`/`attribute_kinds`; пустой набор строк = «все классы», включая добавленные в будущем | Категории «резисторы+конденсаторы» (`Dop`, `Riz`) и «только конденсаторы» (`polarized`) не выражаются одной колонкой kind; движок валидации и фильтры обязаны отклонять неприменимые параметры — иначе каталог молча принимает бессмысленные значения (допуск у транзистора) |
| D8 | **Аналоги — направленные ссылки.** `device_analogs`: запись-владелец → аналог, note на ребре; секция `analogs` записи заменяет только исходящие ссылки; обратная ссылка — отдельное самостоятельное утверждение | Симметричная пара с «заменой целиком» затирала заметки, введённые с другой стороны, и делала round-trip зависимым от порядка импорта; направленность соответствует физике замены: «B заменяет A» не означает «A заменяет B» |
| D9 | **База языконезависима, локализация — на краю (i18n/l10n).** Каталожные таблицы хранят только коды и структурные метаданные: текстовые колонки (названия классов/систем/групп/параметров/атрибутов/условий/единиц, описания, символы единиц) в БД отсутствуют (схема v2). Отображаемые строки — бандлы пакета `internal/i18n`; канонический и обязательный язык — **en**, полный словарь есть также для **ru**. Локаль выбирают только транспорты: REST — `Accept-Language` (по умолчанию en), CLI — `--lang` (по умолчанию en); `domain`/`catalog`/`storage`/`service` локали не знают. Сообщения об ошибках — машиночитаемый код + текст; до перехода на каталог сообщений (этап 8.3 плана работ) тексты формируются по-русски, контракт дословности сохраняется | Справочник не привязан к языку: одна и та же база обслуживает интерфейсы на любом языке бандлов; тексты не дублируются между БД и форматом наполнения; расширение каталога данными не требует параллельного перевода строк в базе; ключи формата (коды, в том числе коды единиц — латиница) переносимы между локалями |
| D10 | **Словарная классификация — секция `fields` поверх систем обозначений** (схема v4). Материал/подкласс/подстройка — доменные словари стабильных кодов (отображения букв систем задают парсеры, многие-к-одному), категория — каталожный словарь (данные). `fields` задаёт только поле, которое парсер системы записи не устанавливает сам (пер-полое правило), и только применимое к классу; для записей без разбора (`other`) секция дополнительно задаёт грамматические поля `series`/`dev_number`/`letters` (семейство, номер, буквы — компенсация исключённой системы series, схема v6); фильтры `material=`/`subclass=`/`adjustment=`/`category=` сквозные между системами с канонизацией на краю (код либо локализованное название). Атрибут `category` переименован в `description` (описание по справочнику), словарная суть ушла в `fields` | Буквы подклассов сталкиваются между системами (gost `Д` — выпрямительный диод, pro `D` — мощный биполярный транзистор) — фильтр по сырому значению бессмыслен; системы other/jedec материал и подкласс не кодируют вовсе, но нужны сквозные запросы («все кремниевые транзисторы»); свободнотекстовая категория не фильтруется канонически |

Следствия из решений (детали — в документах плана):

- обозначение — **точный строковый ключ** записи внутри класса (`КТ315Б` ≠ `2Т315Б`); тождество — это `kind + designation`; система обозначений — атрибут записи, не часть ключа;
- парсеры **строгих систем обозначений** (ГОСТ/ОСТ, PRO ELECTRON, JEDEC, JIS) остаются кодом (грамматики стабильны); слабоструктурированные семейства (МЛТ, ВС, КСО…) системой не разбираются — записи `other`, семейство/номер/буквы задаются секцией `fields` (справочник кодов — `docs/class-keys.md` §11); результат разбора хранится как данные (ключ-значение), поэтому новые классы приборов не требуют менять схему;
- секции «предельные данные» и «массогабаритные данные» — не отдельные жёсткие структуры, а **группы каталога** с собственными ключами секций импорта;
- полные обозначения не входят в ключ записи: хвост мощности резисторов (`С2-33Н-0.125`) и напряжение/ёмкость электролитических конденсаторов — элементы заказа, а не обозначения; ввод обозначения с таким хвостом — ошибка разбора с подсказкой, величины задаются исполнениями-вариантами (D6);
- в схеме нет жёстких колонок атрибутов/условий — CHECK-ограничения в DDL только структурные; семантика значений — в движке валидации, читающем правила из БД;
- сообщения об ошибках получают **машиночитаемые коды** рядом с дословными текстами (и тексты, и коды — контракт); язык текстов — D9: канонический en, ru — бандл (этап 8.2);
- база и формат наполнения языконезависимы (D9): только коды (единицы — латиница: `V`, `ohm`, `pF`…); отображаемые названия и символы — бандлы `internal/i18n`, выбор локали — на краю (REST/CLI);
- классификация записей — словарные коды (D10): значения полей material/subclass/adjustment и словаря категорий — коды; отображение — бандлы, канонизация входа фильтров — на краю.

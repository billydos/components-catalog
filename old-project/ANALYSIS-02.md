## Резюме

Код импортёра в целом качественный и соответствует заявленной архитектуре: реестр форматов расширяемый, ошибки — значения (`*domain.UserError`), атомарность записи («ошибка в секции — запись не применяется вовсе») реализована аккуратно, числа хранятся исходным текстом без потери точности. Юнит-тесты актуальны коду: все проходят, дословные тексты русских сообщений в тестах совпадают с текущими, при правках доменных сообщений тесты импортера сработают сторожем.

Главная активная опасность — A1: дубликаты ключей в jsonc молча игнорируются («выигрывает первый»), включая повтор ключа `transistors` или `name` в записи; yaml тот же файл отвергает. Поведение задокументировано, но для пользователя это тихая потеря данных при случайном дублировании. **A1 исправлено по результатам отчёта** (дубли — ошибка разбора файла с именем ключа и номером строки; см. блок «Решено»). Второй по важности класс — латентные рассинхронизации (A2, B1): список допустимых ключей параметров генерируется из каталога `domain.AllConditionKeys`, а фактическое чтение значений в структуру захардкожено; пин-теста нет. Сейчас списки совпадают, но при добавлении нового `ConditionKey` значение станет «допустимым» и будет молча отброшено. Аналогично вручную синхронизируются `extraFields`/`ratingFields`. **A2 исправлено (2026-09-27)**: чтение условий генерируется из каталога и закреплено пин-тестами обоих уровней (см. блок «Решено»); заодно закрыт позитивный путь `readParameterItem` из B4. **B1 исправлено (2026-09-27)**: `extraFields` производится из `domain.AttributeFieldNames`, `ratingFields` зажат пином соответствия `domain.RatingFieldNames` (заявка диагностики «ключи ratings — точные имена полей» при реализации не подтвердилась — см. блок «Решено»), чтение обеих секций закреплено round-trip пин-тестами.

Тестовая организация хорошая (reader тестируется напрямую на дереве value, фронтенды — своими smoke-сценариями), но на базовом коммите покрытие было неравномерным: 72.8% по операторам, позитивный путь `readParameterItem` (условия реально попадают в структуру) не утверждался ни одним тестом — именно тот участок, что является ручной точкой синхронизации (B4). Слабо покрыты `readAttributes` (56%), `readOptionalIntField` (27%, поля `modification`/`chip` не встречаются ни в одном тесте), негативные ветки полей формы явного обозначения. Проверено и за рамками тестов: хвостовой мусор после корня hujson отвергает, yaml-якоря/теги/merge-ключ/числовые ключи обрабатываются корректно. **B4 исправлено (2026-09-27)**: целевые table-driven тесты по семантическим группам подняли покрытие до 97.0%, весь `reader.go` — 100% (см. блок «Решено»); при закреплении конвертаций yaml обнаружено и в тот же день исправлено молчаливое неразрешение алиасов (B5).

## A. Находки высокого приоритета

### A1. Дубликаты ключей в jsonc молча игнорируются — тихая потеря данных

**Где:** `internal/importer/value.go:36-43` (`value.has`), `internal/importer/format_jsonc.go:69` (`decodeValue`, построение `members` без детекции повторов); заявки: комментарий `format_yaml.go:14-16` и SKILL.md («повторяющиеся ключи в yaml отвергаются при разборе (в jsonc выигрывает первый)»).

`value.has` возвращает первое совпадение имени; `decodeValue` кладёт оба одноимённых ключа в `members`, но никто не сравнивает повторы. Воспроизведено зондажным тестом: `{"transistors": ["МП39"], "transistors": ["КТ315Б"]}` — второй массив полностью игнорируется, ни ошибки, ни Issue; повторный `"name"` внутри записи (`{"name": "МП39", "name": "КТ315Б"}`) — то же самое, `checkEntryKeys` не замечает дубль, т.к. имя «допустимое». Для yaml goccy отвергает повторы на этапе разбора (проверено) — асимметрия между форматами задокументирована, но у пользователя при случайном дублировании ключа (частая опечатка при ручном наборе jsonc) данные теряются без предупреждения. Контраст с AGENTS.md правилом 4 («ошибка хотя бы в одном значении — секция отвергается» — защита от частичного применения) — здесь защита не срабатывает: файл применяется, но не весь.

**Рекомендация:** при построении объекта в `decodeValue` (или проходом в `parseRoot`/`readEntry`) детектировать повтор имени и выдавать `Issue` (или `UserError`) с именем ключа и номером записи. Минимум — зафиксировать ограничение предупреждением в SKILL.md рядом с существующей оговоркой.

**Решено:** (2026-09-26, правки поверх базового коммита, не закоммичены) основным вариантом рекомендации — детекция при построении объекта в `decodeValue` (`format_jsonc.go:41`, карта имён и проверка повтора — строки 59–72): повтор ключа — ошибка разбора, файл отвергается целиком как `*domain.UserError` — «файл не является корректным JSONC: повторяющийся ключ «IkMax» (строка 5)». Из двух вариантов рекомендации выбран `UserError` (отвержение файла), а не `Issue` по записи: goccy отвергает дубли yaml при разборе на всех уровнях вложенности (проверено зондажем: корень, запись, вложенная секция), поэтому единая реакция обоих фронтендов устраняет и задокументированную асимметрию форматов. Инвариант «имена ключей в дереве value уникальны» задокументирован в `value.go`; устаревшие оговорки «в jsonc выигрывает первый» убраны из комментария `format_yaml.go` и SKILL.md (описание формата + новое сообщение в разделе типичных ошибок).

Сверх рекомендации сообщение содержит номер строки исходного файла: хелпер `lineOfOffset` (`format_jsonc.go:101-107`) вычисляет его из `decoder.InputOffset()` по стандартизованному тексту. Корректность опирается на гарантию `hujson.Standardize` заменять комментарии и висячие запятые пробелами по месту, сохраняя смещения и переводы строк (проверено по исходнику библиотеки, `standard.go:80-89`), и закреплена тестом с комментарием перед дубликатом.

Тесты: `TestParseJsoncText_DuplicateKeys_Rejected` — дубль `transistors` в корне, `name` в записи, `IkMax` во вложенной секции, стабильность номера строки при `//`-комментарии (дословные тексты сообщений); `TestParseYamlText_DuplicateKeys_Rejected` расширен вложенными уровнями — фиксирует симметрию форматов. Проверки после правки: `go build`/`go vet`/`gofmt -l` чисты, `go test ./...` ok; CLI: файл с дублем → «повторяющийся ключ «transistors» (строка 4)», exit 1, записи не применяются; `import sample-data.jsonc --dry-run` → 19 записей, 0 проблем.

### A2. Чтение условий параметра захардкожено и не защищено пин-тестом против каталога

**Где:** `internal/importer/reader.go:354-368` (`readParameterItem`, явный список `Uke, Ukb, Ueb, Ik, Ie, Ib, Freq, Rg, Rbe, Temp`), `internal/importer/reader.go:55-62` (`buildParameterFields` — генерация допустимых ключей из `domain.AllConditionKeys`); инвариант AGENTS.md правило 1: «список полей секции jsonc... генерируются из каталога».

Список *допустимых* ключей растёт из каталога автоматически, а отображение ключ→поле структуры — ручное. Сейчас 9 условий + `temp` совпадают с `ElectricalParameter`, активной ошибки нет (проверено зондажем: `h21e` с `Uke/Ik/temp` читается корректно). Но при добавлении в домен нового `ConditionKey` (например, `CondRl`) ключ автоматически станет допустимым в jsonc, `readParameterItem` его не прочитает, и значение будет молча отброшено; если ключ не обязателен в `ConditionSpec`, валидация ничего не заметит — тихая потеря данных, единственное ручное звено в цепочке, которая иначе генерируется из каталога целиком (валидатор, справка, CHECK-ограничения). Позитивный путь этого маппинга не покрыт тестами (см. B4), т.е. рассинхронизация не будет поймана и тестами.

**Рекомендация:** пин-тест в importer: для каждого ключа `parameterFields` (кроме `parameter`/`min`/`max`) — round-trip «ключ в jsonc → значение в структуре `ElectricalParameter`» (можно через `domain.ConditionValueOf`); при добавлении ключа в каталог тест упадёт, пока не добавится чтение. Альтернатива — генерировать чтение условий отражением/switch'ем по `AllConditionKeys` по образцу `domain.ConditionWithValue`.

**Решено:** (2026-09-27) альтернативным вариантом рекомендации — генеративным чтением из каталога, устраняющим само ручное звено; пин-тесты обоих уровней добавлены сверх того. Захардкоженный литерал в `readParameterItem` заменён циклом по `domain.AllConditionKeys` (`reader.go:362-366`): ключ читается через `domain.ConditionJsoncKey` (исключение `freq` сохранено), значение — `readOptionalNumber`, запись в структуру — доменный `ConditionWithValue`, комментарий которого обновлён (функция больше не «для тестов»). `Temp` читается отдельно после цикла (`reader.go:367`) — порядок пунктов в сообщениях об ошибках сохранён прежним (проверено зондажем: невалидные `Uke` и `temp` в одном параметре → «"Uke" должно быть числом; "temp" должно быть числом»). Пин-тесты: доменный `TestConditionAccessors_CoverAllKeys` (`conditions_test.go`) — для каждого ключа каталога пара `ConditionWithValue`/`ConditionValueOf` пишет и читает согласованно и не затрагивает чужих полей; `TestParseRoot_AllConditionKeys_ReadIntoParameter` (`reader_test.go`) — round-trip «ключ в файле → значение в структуре», самонастраивается по каталогу (первый параметр с вариантом, допускающим ключ; `temp` — отдельным subtest'ом), закрывает заодно позитивный путь `readParameterItem` из B4; ключ без использующей его спецификации — громкое падение теста, тихое состояние исключено. Эффект: новый `ConditionKey` требует правок только в domain (+ каталог и SKILL.md), importer подхватывает его автоматически; окно тихой потери значения условия закрыто.

## B. Находки среднего приоритета

### B1. `extraFields` и `ratingFields` синхронизируются с доменными структурами вручную

**Где:** `internal/importer/reader.go:40-48` (списки), `reader.go:253-269` (построение `TransistorAttributes`), `reader.go:404-419` (построение `MaximumRatings`); доменные источники — `domain/attributes.go:47-59` (`AttributeFieldNames`, reflect), `domain/ratings.go:7-30`.

В БД списки полей атрибутов генерируются из `AttributeFieldNames()` автоматически, в importer — дублируются руками. Новое поле записи «подхватывается автоматически» везде, кроме импорта: здесь его придётся добавить в три места (список, построение структуры, домен). Отказ при рассинхронизации громкий («неизвестное поле» — данные не теряются), но ловится только ручным прогоном: доменный пин-тест `TestAttributeFieldNames_PinExpectedFields` importer не защищает, собственного пин-теста в importer нет.

**Рекомендация:** пин-тесты: `extraFields` (+`manufacturers`) эквивалентен `domain.AttributeFieldNames()` в нижнем регистре первых букв; `ratingFields` — именам полей `MaximumRatings` (по образцу доменного пин-теста через reflect).

**Решено:** (2026-09-27) вариантом 3 из анализа (производные списки + round-trip пины) с коррекцией по результату реализации: заявка «`ratingFields` — точные имена полей `MaximumRatings`» не подтвердилась — у полей-слов (`pulseDuration`, `tempMin`, `tempMax`, `tempJunctionMax`) первая буква строчная (правило именования полей, исключения-слова как `freq`/`temp` у условий), единообразная производная списка отвергала бы задокументированные ключи (воспроизведено падением существующих тестов: `tempMin` → «неизвестное поле», `PulseDuration` → прочитан nil → «длительность импульса обязательна»). Итог: `extraFields` производится из `domain.AttributeFieldNames` (`buildExtraFields`, строчная первая буква — правило равномерно для всех полей записи); в domain добавлен `RatingFieldNames()` (reflect-двойник `attributeFieldNames`, закреплён пином `TestRatingFieldNames_PinExpectedFields` по образцу атрибутного), `ratingFields` остаётся ручным списком, но зажат пином `TestRatingFields_MatchDomain` (та же длина и порядок, совпадение имён без учёта регистра). Чтение обеих секций закреплено самонастраивающимися round-trip пинами `TestParseRoot_AllAttributeFields_ReadIntoStructure`/`TestParseRoot_AllRatingFields_ReadIntoStructure` (`reader_test.go`): объект секции со всеми ключами (значение по типу поля, перекрытия для связанных валидацией годов/массы/температур) → после разбора каждое поле структуры обязано быть не nil. Оба сценария рассинхронизации закрыты и проверены зондажами: забытая строка чтения (`ColorMarking`, `Rth`) роняет round-trip с именем поля и ключом; поле, добавленное в домен без обновления `ratingFields`, роняет пин соответствия. Тексты сообщений не изменились (списки идентичны прежним, порядок — порядок объявления полей). Эффект: новое поле записи подхватывается автоматически (атрибуты) либо требует единственной правки списка под громким пином (ratings); окно тихой потери значения (сценарий 2 из анализа — «ключ допустим, значение молча отброшено») закрыто для обеих секций.

### B2. Неравномерная семантика `null` и расхождение с формулировкой SKILL.md

**Где:** `internal/importer/reader.go:273-274` (`manufacturers: null` — «не менять»), `reader.go:302` и `reader.go:393` (`parameters`/`ratings` не-массив/не-объект — ошибка, включая `null`), `reader.go:241-243` (`attributes: null` — ошибка); SKILL.md, раздел формата (строка 41: «`null` — «не менять»»).

Воспроизведено: `"attributes": null` → Issue «"attributes" должно быть объектом»; `"parameters": null` → «"parameters" должно быть массивом объектов»; при этом `"manufacturers": null` внутри секции — легитимное «не менять». Само поведение консистентно с AGENTS.md правило 4 («задана — заменить целиком», null — не значение), но фраза SKILL.md «null — "не менять"» читается как применимая и к секциям целиком — пользователь, написавший `"ratings": null` по аналогии с `manufacturers`, получит неожиданную ошибку.

**Рекомендация:** уточнить SKILL.md: явно указать, что null-семантика «не менять» действует на *поля* внутри секций (и на `manufacturers`), а null у целой секции — ошибка. Либо (спорнее) поддержать null = «не менять» на уровне секций.

**Решено:** (2026-09-27) альтернативным вариантом рекомендации — поддержан null = «не менять» на уровне целых секций (выбор по результатам анализа вариантов: документация оставляла бы криптичное сообщение, точная диагностика сохраняла бы асимметрию). `readAttributes`/`readParameters`/`readRatings` возвращают nil-секции при null — `"attributes": null`, `"parameters": null`, `"ratings": null` равносильны отсутствию секции во всех деталях поведения, включая CLI: повторный импорт существующей записи с null-секциями даёт «Пропущено (уже есть)», данные не трогаются (проверено end-to-end на temp-базе: атрибуты/производители/параметры/предельные данные сохранены). Семантика null стала равномерной: секция — «не менять» (≡ отсутствию), `manufacturers` — «не менять список», поля внутри секций — «не задано» (при замене секции очищает поле); очистка остаётся только явной (`[]`/`{}`). В yaml пустое значение ключа (`attributes:`), `null` и `~` — равносильны отсутствию секции. Сообщения «"attributes" должно быть объектом» и т.п. сохранены для не-null неверных типов (`5`, строка и т.д.). Принятый риск варианта: пользователь, перепутавший `null` с `[]`/`{}`, молча не получит ни изменения, ни ошибки — как и при отсутствии секции. Тесты: `TestParseRoot_NullSections_Rejected` (закреплял прежнее поведение) заменён на `TestParseRoot_NullSections_SameAsAbsent` — по одной секции и все три сразу: запись валидна, секции nil; негативные кейсы `parameters: 5`/`ratings: 5` добавлены в `TestParseRoot_ParameterAndRatingProblems`, ветки неверных типов остались покрыты. Документация синхронизирована: SKILL.md (неточная фраза «null — "не менять"» убрана из yaml-примечания; семантика null по уровням описана в списке секций), README.md, AGENTS.md правило 4 («отсутствует или null — не менять»).

### B3. Issues, собранные до жёсткой ошибки корня, теряются

**Где:** `internal/importer/reader.go:80-90` (`parseRoot`).

Для `{"extra": 1}` цикл по `root.members` appending Issue про неизвестный ключ, после чего `root.has("transistors")` возвращает `UserError` «отсутствует обязательный ключ "transistors"» — результат с Issue отбрасывается (`return nil, ...`), CLI печатает только последнюю ошибку. **Рекомендация:** перенести проверку наличия/типа `transistors` до цикла по неизвестным ключам, либо включать собранные issues в текст `UserError`.

**Решено:** (2026-09-27) вариантом 3 из анализа сравнения вариантов (все проблемы корня — Issues, без жёсткой ошибки). Предварительный анализ вышел за рамки рекомендации отчёта: вариант «перенос проверок до цикла» для пользователя пуст — issues при жёсткой ошибке просто не успевают собраться, вывод байт-в-байт тот же, «чинить по одной» остаётся; включение issues в текст `UserError` дало бы составные тексты — новый вид сообщений при контракте «дословные тексты»; возврат result вместе с err — слабый контракт «результат при ошибке». Выбран вариант с единой семантикой: `parseRoot` теряет error-канал (сигнатура `func parseRoot(root value) *ParseResult`), не-объектный корень, отсутствие `transistors` и неверный его тип — Issues уровня файла (EntryIndex = 0 — слот «ошибка корневого уровня» уже был заложен в комментарий `Issue` и вывод CLI), накапливаются вместе с проблемами неизвестных ключей: файл с опечаткой в `transistors` и лишними ключами даёт полный список проблем за один прогон. CLI правок не потребовал: печать Issues (EntryIndex = 0 — без префикса «Запись №») и exit 1 по `HasErrors` уже готовы; тексты всех сообщений не изменились, изменился канал — было «Ошибка: …», стало строкой списка проблем с итогом «проблемных: N». Тесты: `TestParseRoot_RootProblems` переписан в table-driven — дословные тексты трёх сообщений, EntryIndex = 0, отсутствие записей, плюс два комбинированных сценария B3 (опечатка `transistor` + `extra` → 3 проблемы; `transistors: 5` + `extra` → 2 проблемы); `TestParseYamlText_RootProblems` переписан аналогично (4 случая — issues, несколько yaml-документов — по-прежнему ошибка разбора); ~20 вызовов `parseRoot` в тестах упрощены до однозначного результата. ### B5. Алиасы yaml не разворачивались в значение якоря — тихая подмена строковых полей

**Где:** `internal/importer/format_yaml.go:76-101` (ветки `AnchorNode`/`AliasNode` конвертера; до правки — `yamlToValue:63-66`); первопричина — `goccy/go-yaml` v1.19.2: `ast.AliasNode.Value` хранит узел имени, а не цели (разрешение алиасов библиотека выполняет только в пути декодера, который импортёр не использует).

Обнаружено при закреплении тестами конвертаций B4: `base: &x 10` читалось числом 10 (якорь разворачивался корректно), но `alias: *x` становилось строкой `"x"`. Последствия по типам полей: строковые поля (`structure`, `tu`, элементы `manufacturers`, ...) молча получали имя алиаса — тихая подмена данных того же класса, что A1; числовые/логические поля — громкая, но вводящая в заблуждение ошибка («"IkMax" должно быть числом» при числовом якоре в файле); переиспользование секции целиком (`attributes: *attrs` — типовой yaml-идиом для серий однотипных записей) — ошибка типа секции. Зондаж исходного отчёта проверял только отсутствие краша и разворачивание якоря, поэтому находка всплыла лишь при закреплении поведения тестом.

**Рекомендация:** разрешать алиасы при обходе AST (реестр якорей в конвертере), отвергая алиас без предшествующего якоря и циклическую ссылку как ошибки разбора; альтернатива — громко отвергать алиасы вовсе, в одном ряду с merge-ключом.

**Решено:** (2026-09-27) вариантом с разрешением: `yamlToValue` заменён конвертером `yamlConverter` с реестром якорей документа и множеством «конвертируемых» (защита от циклов): `AnchorNode` конвертирует и регистрирует значение, `AliasNode` берёт из реестра — алиас разворачивается в значение якоря, включая секции целиком и переиспользование между записями. Ошибки разбора, файл отвергается как `*domain.UserError`: «неизвестный алиас «*x» — якорь «&x» не определён до использования» и «циклическая ссылка: алиас «*x» участвует в значении якоря «&x»» (цикл вида `a: &x [*x]`); теги по-прежнему разворачиваются в помеченный узел как есть. Тесты: обновлён пин «якорь и алиас» (разрешение в значение), «алиас отображения», «неизвестный алиас», «циклический алиас», сквозной `TestParseYamlText_AnchorReuseBetweenEntries` (общая секция `attributes` с производителями переиспользуется между записями). SKILL.md: якоря/алиасы описаны в разделе формата, новые сообщения — в разделе типичных ошибок. Итоговое покрытие пакета с учётом нового кода — 97.0%.

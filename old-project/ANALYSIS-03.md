- **Метод:** сплошное чтение исходников всех пакетов; сопоставление точек расширения, декларированных AGENTS.md (каталог параметров → валидатор/справка/поля jsonc/CHECK, reflect-источники имён полей, диалектная изоляция, семантика nil-секций), с предметными системами обозначений: ГОСТ 10862-64 (диоды — та же грамматика), ГОСТ 13453-68 и легаси-семейства (резисторы), К-система и легаси-семейства (конденсаторы). `go build`/`go vet`/`gofmt`/`go test` — база чистая (см. «Выполненные проверки»). Это анализ работ, а не код-ревью: находок-дефектов нет, выход — план работ и проектные решения.

## Резюме

Архитектура проекта готова к расширению примерно на две трети. Декларативная механика, составляющая главную ценность кодовой базы, — каталог параметров, из которого генерируются валидатор, раздел `help`, список полей jsonc и CHECK-ограничения (правило 1 AGENTS.md); reflect-источники имён полей атрибутов и ratings; переносимое реляционное ядро с одним DML-набором; семантика секций импорта «отсутствует/null — не менять, задана — заменить целиком» — всё это не привязано к транзисторам семантически и переиспользуется для всех новых классов с минимальными правками. Транспортный слой (importer, CLI, вывод) обобщается механически.

Главная асимметрия — в грамматиках обозначений. **Диоды** обозначаются той же системой ГОСТ 10862-64 (материал + подкласс + признак + номер + буквы + модификация/бескорпусное): расширяется алфавит подкласса (`Т`, `П` → `Д`, `С`, `В`, `А`, `И`, `Г`, `Л`, `Ц`), и парсер, структура записи, таблица обозначений, фильтры `list`, подсказка `find` по материалу и семантика раздельности `КД105`/`2Д105` работают почти без изменений. **Резисторы** (ГОСТ 13453-68: `С2-33Н`, `СП3-19А`; легаси `МЛТ-0.5`, `ВС-0.25`) и **конденсаторы** (К-система: `К10-17Б`, `К50-35`, `К73-17`; легаси `КМ-6`, `МБМ`, `ЭТО-2`) имеют принципиально другие грамматики — для них нужны собственные парсеры, структуры, таблицы обозначений и фильтры.

Основной объём работ — не код, а **предметная каталогизация**: для каждого класса — перечень подклассов/групп из первоисточников, каталог параметров с условиями измерения и границами, набор предельных данных (правило «перечень полей — часть контракта»). Для конденсаторов, по постановке, вместо секций «параметры + ratings» вводятся «характеристики» (та же каталожная механика) и новая секция массогабаритных данных (габариты с валидацией формы корпуса, масса уже есть в атрибутах). Отдельного решения требует ключевая схема БД: сателлитные таблицы (параметры, атрибуты, производители) при нескольких корнях классов либо дублируются на каждый класс, либо получают общий корень `components` — рекомендуется общий корень (раздел D1). Рекомендуемый порядок: сначала архитектурная волна (общий корень + классы каталогов), затем диоды (дёшево), затем резисторы и конденсаторы (по полной программе).

## 2. Справочная база по классам (предметная область)

> Перечни ниже — рабочие для каталогизации; точный состав подклассов/групп и примеры фиксируются по текстам ГОСТ 10862-64 (с изменениями), ГОСТ 13453-68 и справочникам конденсаторов на этапе реализации (риск R1). Легаси-системы — по решению D3.

### 2.1. Диоды (ГОСТ 10862-64, грамматика транзисторов)

Обозначение: `<материал><подкласс>[С]<признак 1–9><номер 01–999><буква(ы)>[<модификация>][-<бескорп.>]` — идентично транзисторам, включая сборки (`КДС111В`) и бескорпусное исполнение.

| Подкласс | Группа приборов | Примеры |
|---|---|---|
| `Д` | выпрямительные, универсальные, импульсные диоды | `КД105Б`, `КД212А`, `2Д204А`, `ГД507` |
| `С` | стабилитроны и стабисторы | `КС168А`, `КС139А`, `2С191А` |
| `В` | варикапы | `КВ109Б` |
| `А` | СВЧ-диоды (смесительные, детекторные, переключательные, параметрические, умножительные) | `2А607` |
| `И` | туннельные и обращённые диоды | `ГИ403` |
| `Г` | генераторные диоды (диоды Ганна и лавинно-пролётные) | `3А704` |
| `Л` | излучающие диоды (светодиоды) | `АЛ307Б`, `АЛ106` |
| `Ц` | выпрямительные столбы и блоки | `КЦ405А` |

Примечание: тиристоры/динисторы (`КУ101`) и оптопары — следующая орбита расширения той же грамматики, в текущий объём не входят.

Ориентировочный каталог параметров (коды — по правилу именования 2 AGENTS.md: физическая величина — `U`, `I`, `C`; индексы ГОСТ — строчными):

| Код | Название | Ед. | Границы | Условия |
|---|---|---|---|---|
| `Upr` | прямое постоянное напряжение | В | не более | `Ipr` |
| `Iobr` | обратный ток | мкА | не более | `Uobr` (+ `temp`) |
| `Cn` | ёмкость между выводами | пФ | не более | `Uobr` (+ `freq`) |
| `Cp` | коэффициент перекрытия по ёмкости (варикапы) | раз | не менее | `Uobr` |
| `trr` | время восстановления обратного сопротивления | нс | не более | `Ipr` |
| `Ust` | напряжение стабилизации (стабилитроны) | В | диапазон | `Ist` |
| `Rdiff` | дифференциальное сопротивление (стабилитроны) | Ом | не более | `Ist` |
| `TkUst` | ТКН — температурный коэффициент напряжения стабилизации | %/°C | не более | `Ist` |
| `Kpr` | потери преобразования (СВЧ) | дБ | не более | `freq` |
| `Iv` | сила света (светодиоды) | мкд | диапазон | `Ipr` |
| `Lambda` | длина волны излучения (светодиоды) | нм | диапазон | — |

Новые ключи условий: `Uobr`, `Ipr`, `Upr`, `Ist` (В и мА — типы существующих; имена по ГОСТ-индексам строчными).

Предельные данные диодов (`diode_ratings`): `UobrMax` (наибольшее постоянное обратное напряжение), `UobrImpMax` + `pulseDuration`, `IprMax` (постоянный/средневыпрямленный прямой ток), `IprImpMax` + `pulseDuration`, `Pmax` (мВт), `tempMin`/`tempMax`, `tempJunctionMax`, `Rth` — профиль повторяет транзисторный с заменой электродных полей; для стабилитронов диапазон тока стабилизации `IstMin`/`IstMax`.

Атрибуты — без изменений (структура/технология для диодов просто остаются NULL при отсутствии данных).

### 2.2. Резисторы

Системы обозначений:

1. **ГОСТ 13453-68 (новая):** `[С|СП|СН]<группа материала 1–6> - <номер разработки> <буква>` — `С2-33Н` (постоянный, группа 2), `СП3-19А` (переменный), `С5-16МВ` (проволочный). Группа цифрой кодирует материал/технологию (уточнить таблицу по ГОСТ: 1 — углеродистые, 2 — металлодиэлектрические, 3 — композиционные плёночные, 5 — проволочные, …).
2. **Легаси-семейства:** `МЛТ`, `ОМЛТ`, `МТ`, `МГТ`, `ВС`, `УЛИ`, `ПЭ`, `ПЭВ`, `СПО`, `СП`, `ВК` — буквенное семейство + мощность через дефис: `МЛТ-0.5`, `ПЭВ-10`, `ВС-0.25`.

Каталог параметров: `Rnom` (номинал сопротивления, Ом, диапазон как min..max ряда типа), `Dop` (допуск, %, не более), `TKS` (ТКС, 10⁻⁶ 1/°C, не более), `Ush` (уровень шумов, мкВ/В, не более), `Riz` (сопротивление изоляции, МОм, не менее). Предельные данные: `Pnom` (Вт), `Umax` (предельное рабочее напряжение, В), `UimpMax`, `tempMin`/`tempMax`; снижение мощности при нагреве — примечанием, не схемой. Для переменных — атрибут «функциональная характеристика» (закон изменения сопротивления А/Б/В).

### 2.3. Конденсаторы

Системы обозначений:

1. **К-система (новая):** `К<группа диэлектрика, две цифры> - <номер разработки> <буква>` — `К10-17Б` (керамика НВК), `К50-35` (алюминиевый электролитический), `К52-1`? (танталовый), `К73-17` (лавсановый), `К78-2` (полипропиленовый), `К42-19` (металлобумажный), `К31-11`? (слюдяной). Группы — по диэлектрической семье; таблицу групп свести из справочника (риск R1).
2. **Легаси-семейства:** `КМ-4/5/6` (керамика монолитная), `КТ-1/2/3/4`, `КЛС`, `КСО`, `СГМ` (слюда), `МБМ`, `МБГЧ`, `МБГО`, `БМ-2` (бумажные/металлобумажные), `ЭМ`, `ЭТО-1/2`, `КЭГ` (электролитические) и др.

По постановке задачи у конденсаторов три секции: **характеристики** (механика секции `parameters`), **массогабаритные данные** (новая секция), **атрибуты**.

Ориентировочный каталог характеристик: `Cnom` (номинальная ёмкость, пФ канонически — см. D4, диапазон min..max как диапазон номиналов типа), `Dop` (допуск, %), `TKE` (группа ТКЕ: `Н90`, `Н30`, `М47`, `П33`, `МП0`… — **текстовое категориальное значение**, см. D5), `Unom` (номинальное напряжение, В), `Tgd` (тангенс угла потерь, %, не более, при `temp`), `Riz` (сопротивление изоляции, МОм, не менее), `Iut` (ток утечки, мкА, не более, при `Unom`-условии и `temp` — для электролитических), `Esr` (Ом, не более, при `freq` = 0.1 МГц).

Массогабаритная секция (`dimensions`): `length`, `width`, `height` (мм, прямоугольный корпус), `diameter`, `leadLength` (мм, цилиндрический: диаметр × длина с выводами), `leadPitch` (мм, шаг выводов). Валидация: все значения положительны; форма корпуса согласована — либо набор «прямоугольный» (L×W×H), либо «цилиндрический» (D + длина), смешение — ошибка. Масса: `massMax` остаётся в общих атрибутах (уже есть), дублирования не вводить (D8).

Атрибуты: общие поля покрывают корпус/материал корпуса/ТУ/годы/производителей; добавляется `Polarized` (полярность, для электролитических; bool, NULL — «не задано») — новое поле в общем reflect-источнике подхватывается колонками и `chk_any_attribute` автоматически (правило 1).

## 3. Проектные решения (принять до старта работ)

### D1. Ключевая схема БД: общий корень `components` — **рекомендуется**

Проблема: `electrical_parameters`, таблица атрибутов и связь производителей ссылаются FK на корень `transistors`. При втором–четвёртом корнях переносимого FK на «разные таблицы» нет — либо дублировать сателлитные таблицы и DML на каждый класс (×3–4 кода в `storage`, что противоречит философии проекта), либо ввести общий корень.

Рекомендуемая схема (пересоздаётся импортом — правило 5, миграций не нужно):

```
components(Id PK AUTOINCREMENT, Class TEXT NOT NULL CHECK (…))
  ├── semiconductors(ComponentId PK/FK, Material, Subclass, Assembly, Feature,
  │                   DevNumber, Letters, Modification, ChipVariant, UNIQUE(…))
  │     ├── транзисторы: Subclass IN ('Т','П')
  │     └── диоды:       Subclass IN ('Д','С','В','А','И','Г','Л','Ц')
  ├── resistors(ComponentId PK/FK, System, Family, Group, DevNumber, Variant, Power?, UNIQUE(…))
  ├── capacitors(ComponentId PK/FK, System, Group, DevNumber, Variant, UNIQUE(…))
  ├── component_attributes(ComponentId PK/FK, …все текущие поля…, Polarized)
  ├── electrical_parameters(ComponentId FK, Parameter, ValueMin, ValueMax, ValueText,
  │                          …union колонок условий…, CHECK из конкатенации каталогов)
  ├── component_manufacturers(ComponentId FK, ManufacturerId FK)
  ├── transistor_ratings / diode_ratings / resistor_ratings (ComponentId PK/FK, поля классов)
  └── capacitor_dimensions(ComponentId PK/FK, Length, Width, Height, Diameter, LeadPitch, CHECK формы)
manufacturers — без изменений
```

Обоснование: один набор DML в `relational.go` (rowReader, upsert-паттерн, транзакции, чистка сирот — обобщить `deleteOrphanManufacturers` на UNION link-таблиц), уникальность обозначений остаётся в классовых таблицах (правило 6 не меняется: обозначение — точный ключ внутри класса), AUTOINCREMENT и запрет переиспользования id наследуются корнем. Альтернативы: (Б) классовые наборы таблиц — дороже кодом, отклонить; (В) одна широкая таблица обозначений — слабые CHECK и NULL-«болото», отклонить.

### D2. Доменная модель ГОСТ 10862-64: обобщение, не дублирование — **рекомендуется**

`Transistor` → `Semiconductor` (те же поля): класс вычисляется по подклассу (`Class()`), `ValidateSemiconductor` выбирает допустимый алфавит и текст ошибки для позиции 2 (`Т/П` — транзисторы; `Д/С/В/…` — диоды; сообщение — по образцу текущего, перечень в сообщении — часть контракта). Новые структуры `Resistor`, `Capacitor` + интерфейс `Device { Name() string; Class() Class }` для полиморфизма в CLI/importer. Альтернатива — параллельная структура `Diode` с теми же полями — дублирование, отклонить. Волна переименований (`TransistorDetails` → `DeviceDetails` и т.п.) механическая, закрепляется правкой пин-тестов.

### D3. Легаси-системы обозначений — реестр, явно

Как со старой системой «П...» у транзисторов (отвергается с внятной ошибкой): для резисторов/конденсаторов принять решение — (а) только новые системы, легаси отвергается сообщением со списком поддерживаемых; (б) легаси-семейство поддерживается как «строковый ключ без разбора» (запись хранится, фильтры по полям обозначения недоступны). Рекомендуется (а) для первого прохода + (б) отдельным этапом по мере надобности (справочники насыщены легаси-типами, но грамматики их размыты — риск R2).

### D4. Канонические единицы новых величин — расширение правила 3

Предложение (фиксируется в AGENTS.md/SKILL.md вместе с каталогами): сопротивление — **Ом** (кОм/МОм даташита переводить до записи); мощность резисторов — **Вт** (у транзисторов остаётся мВт — единица принадлежит параметру каталога, асимметрия задокументирована); ёмкость — **пФ** (нФ/мкФ переводить; для электролитов 4700 мкФ = 4.7×10⁹ пФ — добавить инженерное форматирование больших/малых величин в вывод, хранение единое); ТКС — 10⁻⁶ 1/°C; ТКН — %/°C; сила света — мкд; длина волны — нм; ESR — Ом; напряжение — В; токи — мА/мкА по образцу текущих.

### D5. Категориальные характеристики (ТКЕ, функциональная характеристика)

`ParameterInfo` расширяется признаком вида значения (числовое | текстовое) и списком допустимых текстовых вариантов; `ElectricalParameter` — полем `ValueText *string` (числовые границы у текстовых запрещены валидатором и CHECK `ValueText IN (...)` per код). Альтернатива — хранить ТКЕ в атрибутах — теряет условия и справку каталога, отклонить.

### D6. Имена: модуль/бинарник/БД/переменная окружения

`soviettransistors` (модуль, бинарник, пути импорта), `transistors.db`, `TRANSISTOR_DB`. Варианты: сохранить имена (дёшево, имя становится историческим) или переименовать в нейтральные (`sovietcomponents`, `components.db`, `COMPONENTS_DB`) с поддержкой старой переменной окружения для совместимости. Решение принять до этапа 0 — переименование модуля затрагивает все импорт-пути и документацию одним механическим коммитом; позже — дороже.

### D7. Формат импорта: корневые ключи по классам

Корень объекта: необязательные массивы `"transistors"`, `"diodes"`, `"resistors"`, `"capacitors"` (хотя бы один). Текущие файлы (`"transistors"` только) остаются валидными — обратная совместимость без изменений. Записи диодов — те же формы (`name`-строка или явные поля + секции `attributes`/`parameters`/`ratings`); резисторов/конденсаторов — свои наборы полей и секций (`dimensions` у конденсаторов). Проверка ключей секций — по классовому каталогу записи (списки полей генерируются из источников правилом 1, пин-тесты — по образцу `TestRatingFields_MatchDomain` и round-trip).

### D8. Секция массогабаритов vs атрибуты

Габариты — отдельная секция `dimensions` с собственными CHECK (см. 2.3); масса `massMax` остаётся в общих атрибутах (уже есть у транзисторов, дублирование понятия не вводится). Если позже понадобится масса внутри массогабаритной карточки — пересмотреть, пока не требуется.

## 7. Что сделано хорошо (активы, которые нельзя сломать расширением)

- **Каталожная генерация** (`domain/parameters.go` → валидатор/справка/поля jsonc/CHECK): новые классы ложатся в готовый механизм — это ядро плана.
- **Reflect-источники имён полей** (`attributes.go:47`, `ratings.go:38`): новые поля/секции подхватываются колонками и CHECK автоматически; пин-тесты ловят рассинхронизацию.
- **Переносимое ядро DML и диалектная изоляция** (`relational.go`, `Dialect`): общий корень D1 не выходит за рамки разрешённых конструкций.
- **Семантика секций импорта и атомарность записи** (`importer/reader.go`): переносится на новые классы без изменений.
- **Подсказка `find` по материалу и раздельность записей** (`FindMaterialEquivalents`, правило 6): для диодов работает как есть.
- **Ошибки как значения** (`*domain.UserError`, правило 9): все новые сообщения — в ту же конвенцию, дословные тексты — часть контракта и тестов.

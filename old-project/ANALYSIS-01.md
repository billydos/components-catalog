# ANALYSIS-01 — Code Review проекта SovietTransistorsDatabase (Go-реализация)

- **Дата:** 2026-09-26
- **База:** коммит `acb87db` (+ незакоммиченная правка выравнивания текста справки в `internal/cli/help.go`)
- **Объём:** ~5 400 строк Go (cmd, internal/domain, internal/storage, internal/importer, internal/cli) + DDL + тесты
- **Метод:** чтение всех исходников; `go build` / `go vet` / `gofmt` / `go test`; воспроизведение подозрительных сценариев на собранной утилите во временной директории; `go mod tidy` на копии проекта

## Резюме

Проект в хорошем санитарном состоянии: сборка и тесты чистые, декларативный каталог параметров исключает основной класс рассинхронизаций, транзакции и NULL-семантика реализованы аккуратно. Найденные проблемы концентрируются в трёх местах: **(1)** логика upsert «UPDATE→INSERT по RowsAffected», которая сломается на заявленной цели переноса MariaDB; **(2)** семантика пустой секции `ratings` (фантомная all-NULL строка и пустой заголовок в `info`); **(3)** недостаточная строгость jsonc-парсера (мусор после корня и дубликаты ключей молча принимаются). Отдельно отмечено отсутствие автотестов для `internal/storage` — самого сложного пакета.

## A. Находки высокого приоритета

### A1. Upsert «UPDATE→INSERT по RowsAffected» не переносим на MariaDB/MySQL

**Где:** `internal/storage/relational.go:607-631` (`setAttributes`), `internal/storage/relational.go:700-732` (`setRatings`); заявка переносимости — `internal/storage/sqlite.go:35-38`.

`setAttributes`/`setRatings` определяют существование строки по `UPDATE ... ; RowsAffected > 0`, иначе делают `INSERT`. В SQLite (и PostgreSQL) `RowsAffected` считает совпавшие строки даже при записи идентичных значений. В MySQL/MariaDB драйверы по умолчанию (без `CLIENT_FOUND_ROWS`) возвращают **0** для UPDATE, не изменившего данные. Тогда код решит, что строки нет, и перейдёт к INSERT → конфликт первичного ключа `TransistorId` → **повторный импорт того же файла завершится ошибкой** на существующей записи с идентичными атрибутами/ratings. Это прямо противоречит заявленным «идемпотентный импорт» и «остальной DML менять не нужно».

**Рекомендация:** не выводить существование строки из `RowsAffected`. Варианты: (а) явный `SELECT 1 FROM ... WHERE TransistorId = @id` перед записью; (б) диалектозависимый upsert (`INSERT ... ON DUPLICATE KEY UPDATE` / `ON CONFLICT DO UPDATE`) через поле `Dialect`. Как минимум — зафиксировать ограничение комментарием и тестом.

**Решено:** не исправлено

### A2. Пустая секция `"ratings": {}` оставляет фантомную строку и портит вывод `info`

**Где:** `internal/storage/relational.go:183-187` (ветка `details.Ratings != nil` всегда пишет строку), `internal/cli/commands.go:374-421`.

Воспроизведено на собранной утилите:

1. Импорт записи с `ratings` и `attributes` → в `maximum_ratings` строка с данными.
2. Импорт `"ratings": {}` → строка **не удаляется**, а перезапывается all-NULL (проверено напрямую в SQLite: `(1, None, None, None)`).
3. `info КТ315Б` печатает заголовок «Предельные эксплуатационные данные:», под которым ничего нет.

Для сравнения, пустая секция `"attributes": {}` корректно делает `DELETE` (`relational.go:165-171`, `clearAttributes`). Семантика «`{}` — очистить» (AGENTS.md, правило 4) для ratings выполняется лишь фактически (все поля NULL), но не физически, и ломает вывод. CHECK `chk_ratings` all-NULL строку пропускает.

**Рекомендация:** в `Save` симметрично атрибутам: если все поля `MaximumRatings` nil — `DELETE FROM maximum_ratings WHERE TransistorId = @id`. Дополнительно (к защите): не печатать заголовок секции в `cmdInfo`, если все поля nil.

**Решено:** не исправлено

### A3. Мусор после корневого объекта JSONC молча игнорируется

**Где:** `internal/importer/jsonc.go:50-58` (`parseJsoncToValue` / `decodeJsonValue`).

После декодирования корневого значения остаток потока не проверяется. Воспроизведено: файл `{ "transistors": ["КТ315Б"] } ЭТО МУСОР ПОСЛЕ КОРНЯ` импортируется с exit 0. Сценарий реален: склейка двух файлов, обрыв копии, частичная перезапись — всё принимается как корректный файл, потери данных не детектируются.

**Рекомендация:** после `decodeJsonValue(decoder)` для корня убедиться, что следующий `decoder.Token()` возвращает `io.EOF`, иначе — `UserError` «после корневого объекта есть лишние данные».

**Решено:** не исправлено

## B. Находки среднего приоритета

### B1. go.mod: прямая зависимость помечена как indirect

**Где:** `go.mod:15` — `modernc.org/sqlite v1.59.0 // indirect`, при этом пакет напрямую импортируется в `internal/storage/sqlite.go:6`.

Проверено на копии: `go mod tidy` переносит модуль в отдельную прямую секцию `require modernc.org/sqlite v1.59.0`. Текущая разметка дезинформирует о графе зависимостей (в SKILL.md при этом корректно указано «единственная внешняя зависимость»).

**Рекомендация:** выполнить `go mod tidy` и закоммитить.

**Решено:** не исправлено

### B2. Дубликаты ключей jsonc молча принимаются

**Где:** `internal/importer/jsonc.go:40-47` (`has` возвращает первое вхождение; список `members` хранит оба).

Воспроизведено: `{ "transistors": [{ "name": "КТ315Б", "name": "ГТ115А" }] }` — принято без предупреждения, применён первый ключ. Опечатка вида два `"min"` в параметре не будет замечена.

**Рекомендация:** при сборке объекта в `decodeJsonValue` регистрировать повтор имени как ошибку разбора.

**Решено:** не исправлено

### B3. Panic в пути данных публичного API

**Где:**
- `internal/storage/relational.go:1032-1038` — `materialKindOf` паникует на некорректном символе материала; вызывается из публичного `FindMaterialEquivalents`. Через CLI недостижимо (парсер валидирует), но метод — часть интерфейса `TransistorDatabase` для внешних потребителей. Нарушает AGENTS.md правило 9 («не использовать panic в пути данных»).
- `internal/domain/parameters.go:139-141` — `ParameterInfoOf` для неизвестного `Kind` молча возвращает нулевое значение; далее `internal/domain/parametervalidator.go:55` вызывает `info.Conditions.IsSatisfiedBy(p)` на nil-указателе → паника. Через importer/CLI недостижимо (неизвестные коды отсекаются), но `ValidateElectricalParameter` — экспортируемая функция.
- `internal/domain/conditions.go:59, 84, 99, 124, 149, 176` — panic-заглушки на неизвестный ключ условия (защита от ошибок программиста; допустимо, но в связке с вышеописанным образует «тихий ноль → паника глубже в стеке»).

**Рекомендация:** `ParameterInfoOf` → `(ParameterInfo, bool)`; `materialKindOf` → ошибка. Для conditions.go паники можно оставить, но осознанно (инвариант закрытого множества ключей).

**Решено:** не исправлено

### B4. `lastInsertId` теряет причину и маскирует класс ошибки

**Где:** `internal/storage/relational.go:502-508`.

Сбой инфраструктуры (драйвер/БД) превращается в `domain.NewUserError("не удалось получить id вставленной записи")` — CLI напечатает его как «Ошибка: » (диалоговую), а исходный `err` отброшен. Для сравнения: остальные ошибки БД в пакете пробрасываются как есть.

**Рекомендация:** вернуть исходную ошибку, обернув через `fmt.Errorf("...: %w", err)`.

**Решено:** не исправлено

### B5. Команды записи создают файл БД, даже когда применять нечего

**Где:** `internal/cli/commands.go:60-66` (`cmdAdd` — `openDatabase` вызывается после разбора, но независимо от `failures`), `commands.go:122-129` (`cmdImport` — аналогично).

Воспроизведено: `add "ПЛОХОЕ" --db t5.db` → все обозначения некорректны, но `t5.db` с полной схемой создан. Побочный эффект неожидан для пользователя и засоряет каталог.

**Рекомендация:** если `len(valid) == 0 && failures > 0` — выход до открытия БД (для import — если `len(parsed.Entries) == 0`).

**Решено:** не исправлено

### B6. Ошибки `os.Stat` маскируются под «файл не найден»

**Где:** `internal/cli/commands.go:93-96` (import), `commands.go:547-551` (`openExistingDatabase`).

`Stat` возвращает и `EACCES`, и `EISDIR` (путь — каталог); все случаи печатаются как «файл не найден» / «база данных не найдена». Для каталога `--db` сообщение подсказывает неверное действие («сначала выполните init»).

**Рекомендация:** различать `os.IsNotExist()` и прочие ошибки; для каталога — отдельное сообщение.

**Решено:** не исправлено

### B7. `--dry-run` молча игнорируется частью команд

**Где:** `internal/cli/cli.go:39-40` (флаг разбирается глобально), `cli.go:70-92` (передаётся только в add/import/delete).

`list --dry-run`, `info --dry-run` и т.п. просто игнорируют флаг. Пользователь может ошибочно считать, что «проверка» прошла. Либо отвергать флаг для команд, где он не определён, либо не упоминать.

**Решено:** не исправлено

### B8. Тестовое покрытие: storage и cli — без автотестов

**Где:** `go test ./...` → `internal/storage [no test files]`, `internal/cli [no test files]`.

`relational.go` (1038 строк) — самая сложная логика проекта: upsert-семантика секций, NULL-безопасное равенство, каскады, чистка сирот производителей. Всё это — ручное сценарное QA. Именно здесь живут A1 и A2, которые поймал бы простой тест «импортировать файл дважды и сравнить состояние».

**Рекомендация:** smoke-тесты `storage` на временной файловой SQLite-БД (temp dir + `NewSqliteStore`): save→save идемпотентность, очистка секций, каскадное удаление, точность фильтров. Это дёшево: драйвер pure Go, БД в t.TempDir().

**Решено:** не исправлено

## Что сделано хорошо

- **Декларативный каталог параметров** (`parameters.go` + `conditions.go`): валидатор, справка, список полей jsonc и CHECK-ограничения генерируются из одного источника — главный источник рассинхронизации устранён архитектурно.
- **rowReader** (`relational.go:831-878`): чтение по именам колонок с проверкой наличия в SELECT — опечатка падает громко, порядок колонок не влияет.
- Переносимый NULL-предикат `col = @p OR (col IS NULL AND @p IS NULL)` без сенти́нелов последователен во всём DML.
- `insertTransistorIfAbsent` — атомарная вставка «если нет» одним оператором, без find-then-insert.
- Транзакции с `defer tx.Rollback()` + `Commit` во всех многошаговых записях; `rows.Err()` проверяется везде, `rows.Close()` — через defer.
- Парсер обозначений: точные сообщения с номером позиции и полученным символом; юникодные дефисы нормализуются.
- Пин-тест `TestAttributeFieldNames_PinExpectedFields` держит reflect-список полей и колонки БД в синхроне.
- `go build`, `go vet`, `gofmt -l` — чисто; тесты domain/importer содержательные (таблицы вариантов условий, дословные тексты ошибок).

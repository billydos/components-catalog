## Детальный разбор

### CC-1. Эндпоинт разбора обозначения — низкая

Текущее состояние: сервисные методы `Designations.Parse` / `ParseForSystem` / `Suggest` уже существуют (`internal/service/parse.go`), их использует CLI `catalogctl parse`. REST-маршрута разбора нет.

Работа: маршрут в таблице `routes` (`internal/httpapi/api.go`), хендлер, JSON-модель (`wire.go`), `api/openapi.yaml`, тесты, `docs/plan/04-module-functionality.md` §2. Сервисный слой готов полностью.

Единственная дизайн-задача — «конфиденс». Парсер строгий (детерминированные грамматики, фиксированный порядок автодетекта — `internal/domain/designation.go`, `autodetect`), числовой уверенности нет и ввести её честно нельзя. Эквивалент по UX: возвращать список всех систем, принявших обозначение (кандидатов), — небольшое расширение `domain.ParseDesignation`. Fallback из запроса (suggest + ручной выбор) уже покрыт существующим `GET /api/v1/suggest`.

Оценка: ~1 день с тестами и openapi.

### CC-2. Change feed / хуки изменений — средняя–высокая

Текущее состояние: инкрементальных событий нет вовсе; есть только монотонный счётчик `data_revision` в `schema_meta` (`internal/storage/meta.go`), инкрементируемый в транзакциях записи (`internal/service/devices.go`, `BumpDataRevision` в Upsert/Delete). Сайт сегодня видит только факт «данные изменились» через `/stats`.

Работа:

- новая таблица событий (ревизия, операция created/updated/deleted, kind, designation, id) — изменение DDL, инкремент `SchemaVersion` (сейчас 8) с пересозданием базы импортом (D5; выверенное наполнение в `data/` делает это приемлемым);
- запись событий в тех же транзакциях записи, что и `BumpDataRevision` — все пути: `Create`/`Upsert`/`Delete` сервисного слоя, включая компенсационные удаления импортёра (`internal/importer/importer.go`, `recordIssue` — уже сегодня шумят в `data_revision`);
- `GET /api/v1/changes?since=<revision>&limit=`: storage-запрос, сервисный метод, хендлер, openapi;
- политика ретенции/очистки событий;
- правка планов `02-database.md` (новая таблица + версия схемы) и `04-module-functionality.md` — осознанное изменение, по правилам AGENTS.md отдельным коммитом со всеми связанными местами.

Замечание по варианту «callback-хук OnChange в Go API»: значительно дешевле (без DDL), но не закрывает заявленный в запросе сценарий записи в обход сайт-обёртки (`catalogctl` напрямую в ту же базу) — событие в процессе сайта не возникнет. Раз нужен именно этот случай, правильный дизайн — таблица событий в БД; колбэк можно дать дополнительно как удобство для встраивания.

Оценка: 3–5 дней + прогон QA-матрицы (linux/SQLite, linux/PostgreSQL, windows/SQLite).

### CC-5. Диапазоны значений параметров для фильтров — низкая

Переносимый агрегатный запрос `GROUP BY parameter_code` с `MIN/MAX` по `parameter_values × devices` (фильтр классом); индексы `idx_pv_code_*` уже покрывают доступ; частоты enum — `GROUP BY value_text`. Новый метод storage, сервисный метод, экспозиция в `/stats?kind=` (или `/catalog`), openapi, тесты.

Дизайн-решение одно: конвенция min/max при смешанных формах значений — брать ту же семантику, что у параметрических фильтров поиска (`paramCondSQL` в `internal/storage/search.go`: границы учитывают и `value_min/value_max`, и `value_exact`).

Оценка: ~1 день.

### CC-6. Импорт больших файлов стримингом — низкая–средняя

Текущее состояние: Go API уже стриминговый — `importer.Importer.Import(ctx, io.Reader, name, dryRun)` читает NDJSON построчно без загрузки файла целиком (`internal/importer/ndjson.go`), отчёт — аккумулятор Issues. Записи буферизуются до конца файла ради семантики «всё-или-ничего» на синтаксисе — при 10⁴–10⁵ записей это структуры, а не сырые байты, память приемлема. Прогресс-колбэк в Go API — небольшое расширение сигнатуры (option).

Отсутствует REST-путь импорта: маршрутов импорта в `/api/v1` нет. Основная работа — `POST /api/v1/import` (NDJSON-тело, стриминговое чтение без `http.MaxBytesReader` с лимитом одной записи `maxBodyBytes`; лимит целесообразно заменить на лимит строки сканера, уже 16 МиБ), синхронный ответ отчётом после EOF; прогресс по REST — только polling/SSE (отдельное удорожание, в запросе не обязателен). Семантика частичных отказов (Issues) готова.

Оценка: 2–3 дня REST + тесты; Fallback с партиями по 2000 записей после появления эндпоинта не нужен.

### CC-8. Фильтр по набору id в GET /components — низкая

Сценарий F12 — составной поиск «FTS сайта × параметрика модуля» без дублирования данных каталога на сайте: сайт отбирает по релевантности ≤ 200 id и передаёт модулю вместе с остальными фильтрами (07). Предложение — повторяемый параметр `id` (до 200 значений), семантика — пересечение с прочими фильтрами; сортировка — существующий `sort`, без него — порядок передачи id. 200 id ≈ 4–5 КиБ строки запроса — в пределах типовых лимитов; выдача укладывается в действующий потолок `limit` 200.

Семантика пересечения ложится на существующий конструктор WHERE: `buildSearchWhere` объединяет условия через AND (`internal/storage/search.go`) — добавляется `d.id IN (...)` именованными аргументами самого конструктора WHERE (схема имён — как у хелпера `inList`, `internal/storage/db.go`; мутация чужой map аргументов хелпером туда не подходит); 200 аргументов далеки от пределов драйверов, `maxInList`-чанкование не требуется. Total (`COUNT(*) OVER()`) и пагинация работают без изменений. Дырки в наборе (id без записи либо отсечённые прочими фильтрами) — просто отсутствие строки в выдаче, отдельной ошибки не нужно.

Работа: `IDs []int64` в `SearchQuery`/`SearchRequest` + валидация в `buildSearchRequest` (потолок 200, положительные int64, дубликат в наборе — 400 либо дедупликация), разбор повторяемого `id` в `parseSearchQuery`, `api/openapi.yaml`, `docs/plan/04-module-functionality.md` §1.1/§2, тесты на обеих СУБД. Без DDL и инкремента версии схемы.

Дизайн-задачи две:

- повторяемый параметр — исключение из действующей строгости разбора: `rejectDuplicateParams` (`internal/httpapi/query.go`) сегодня отвергает любой повтор (?q=a&q=b → 400), `id` станет первым намеренно повторяемым параметром контракта; альтернатива без исключения — одна строка со списком `id=1,2,3`, но повторяемую форму генерировать из FTS-выдачи проще;
- порядок «без sort — порядок передачи id» — новый режим сортировки: переносимый `ORDER BY CASE d.id WHEN @id0 THEN 0 … END` первым ключом в `orderJoinClause`, пока `sort` не задан; обязательный финальный ключ (kind, designation) не мешает — id уникальны.

Fallback заявки (FTS — отдельный режим поиска, фильтр только kind из fts_docs, без комбинации с par./attr.) от модуля не требует ничего: сайт ищет по своему индексу сам, карточки достаются готовым `GET /api/v1/components/{id}`.

Оценка: ~1 день.

## Сквозные замечания

- **Планы и контракты**: CC-2 — осознанное изменение зафиксированных решений; по AGENTS.md требует отдельного коммита с правкой всех связанных мест плана (`02-database.md`, `04-module-functionality.md`, `api/openapi.yaml`, `docs/fill-format.md`).
- **Тесты**: все новые ноги интеграционных тестов обязаны проходить на SQLite и PostgreSQL (`CATALOG_TEST_POSTGRES_DSN`, `go test ./... -p 1`) и попасть в сценарии `qa/runner`.

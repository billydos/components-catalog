## Детальный разбор

### CC-1. Эндпоинт разбора обозначения — низкая

Текущее состояние: сервисные методы `Designations.Parse` / `ParseForSystem` / `Suggest` уже существуют (`internal/service/parse.go`), их использует CLI `catalogctl parse`. REST-маршрута разбора нет.

Работа: маршрут в таблице `routes` (`internal/httpapi/api.go`), хендлер, JSON-модель (`wire.go`), `api/openapi.yaml`, тесты, `docs/plan/04-module-functionality.md` §2. Сервисный слой готов полностью.

Единственная дизайн-задача — «конфиденс». Парсер строгий (детерминированные грамматики, фиксированный порядок автодетекта — `internal/domain/designation.go`, `autodetect`), числовой уверенности нет и ввести её честно нельзя. Эквивалент по UX: возвращать список всех систем, принявших обозначение (кандидатов), — небольшое расширение `domain.ParseDesignation`. Fallback из запроса (suggest + ручной выбор) уже покрыт существующим `GET /api/v1/suggest`.

Оценка: ~1 день с тестами и openapi.

### CC-2. Change feed / хуки изменений — средняя–высокая

Текущее состояние: инкрементальных событий нет вовсе; есть только монотонный счётчик `data_revision` в `schema_meta` (`internal/storage/meta.go`), инкрементируемый в транзакциях записи (`internal/service/devices.go`, `BumpDataRevision` в Upsert/Delete). Сайт сегодня видит только факт «данные изменились» через `/stats`.

Работа:

- новая таблица событий (ревизия, операция created/updated/deleted, kind, designation, id) — изменение DDL, инкремент `SchemaVersion` (сейчас 8) с пересозданием базы импортом (D5; выверенное наполнение в `data/` делает это приемлемым);
- запись событий в тех же транзакциях записи, что и `BumpDataRevision` — все пути: `Create`/`Upsert`/`Delete` сервисного слоя, включая компенсационные удаления импортёра (`internal/importer/importer.go`, `recordIssue` — уже сегодня шумят в `data_revision`);
- `GET /api/v1/changes?since=<revision>&limit=`: storage-запрос, сервисный метод, хендлер, openapi;
- политика ретенции/очистки событий;
- правка планов `02-database.md` (новая таблица + версия схемы) и `04-module-functionality.md` — осознанное изменение, по правилам AGENTS.md отдельным коммитом со всеми связанными местами.

Замечание по варианту «callback-хук OnChange в Go API»: значительно дешевле (без DDL), но не закрывает заявленный в запросе сценарий записи в обход сайт-обёртки (`catalogctl` напрямую в ту же базу) — событие в процессе сайта не возникнет. Раз нужен именно этот случай, правильный дизайн — таблица событий в БД; колбэк можно дать дополнительно как удобство для встраивания.

Оценка: 3–5 дней + прогон QA-матрицы (linux/SQLite, linux/PostgreSQL, windows/SQLite).

### CC-3. Метаданные «основных параметров» класса — низкая–средняя

Текущее состояние: у параметров каталога нет признака «основной» — колонки priority/is_key в таблице `parameters` нет (`internal/storage/ddl.go`), поля в `ParameterDef` снимка (`internal/catalog/snapshot.go`) и в JSON `/catalog` (`internal/httpapi/wire.go`) тоже.

Вариант 0 (без правки модуля): дефолтные колонки таблицы/карточки выводить из уже существующего `sort_order` параметров (первые N по каждой группе). Порядок параметров стабилен и наполняется файлами каталога — формально запрос закрыт без кода; сайт лишь фиксирует правило отбора.

Вариант с явным признаком: колонка в `parameters` (+ `ParameterDef`, каталог-секция формата наполнения, сиды, JSON `/catalog`, `docs/fill-format.md`) — инкремент `SchemaVersion` и пересоздание базы импортом. Если CC-2 тоже поднимает версию схемы, оба изменения совместить в одном инкременте, чтобы не пересоздавать базу дважды.

Оценка: 1–2 дня (вариант с признаком); 0 — при выводе из `sort_order`.

### CC-4. Нативный полнотекстовый поиск (F12) — высокая

Самый тяжёлый запрос. Ограничения, с которыми он сталкивается:

- равноправие диалектов (D3) и правило «всё диалектозависимое — только в `Dialect`» при полностью расходящихся механизмах: FTS5 (виртуальная таблица, `MATCH`) в SQLite против `tsvector`/GIN (`@@`, `to_tsquery`) в PostgreSQL — расходятся и DDL, и синтаксис запросов, и токенизация/стемминг, и ранжирование;
- переносимый DML-слой (`internal/storage/search.go`) допускает только общие конструкции — полнотекстовое условие потребует диалектных методов;
- паритет результатов между диалектами принципиально трудно выровнять (русская морфология), а набор интеграционных тестов обязан проходить на обоих (CI-матрица);
- синхронизация теневого индекса — зависит от CC-2 (события изменений), либо триггеры (тоже диалектный DDL);
- предварительно проверить, что FTS5 собран в используемом драйвере `modernc.org/sqlite` (риск, проверяется отдельным спайком).

Отдельно зафиксировать объём индексируемых текстов: по D9 в каталожных таблицах текстовых колонок нет; реальные тексты — значения текстовых атрибутов (`description`), примечания аналогов (`note`), имена производителей; `value_text` — коды enum, для поиска бесполезны.

Fallback из запроса (сайт-таблица `fts_docs`, синхронизация событиями CC-2 или ночная пересборка) существенно дешевле и не нарушает решений модуля. Рекомендация: нативный FTS брать только если требования к качеству поиска (морфология, релевантность) не покрываются сайт-сторокой.

Оценка: 5–10 дней с диалектами, синхронизацией и тестами матрицы.

### CC-5. Диапазоны значений параметров для фильтров — низкая

Переносимый агрегатный запрос `GROUP BY parameter_code` с `MIN/MAX` по `parameter_values × devices` (фильтр классом); индексы `idx_pv_code_*` уже покрывают доступ; частоты enum — `GROUP BY value_text`. Новый метод storage, сервисный метод, экспозиция в `/stats?kind=` (или `/catalog`), openapi, тесты.

Дизайн-решение одно: конвенция min/max при смешанных формах значений — брать ту же семантику, что у параметрических фильтров поиска (`paramCondSQL` в `internal/storage/search.go`: границы учитывают и `value_min/value_max`, и `value_exact`).

Оценка: ~1 день.

### CC-6. Импорт больших файлов стримингом — низкая–средняя

Текущее состояние: Go API уже стриминговый — `importer.Importer.Import(ctx, io.Reader, name, dryRun)` читает NDJSON построчно без загрузки файла целиком (`internal/importer/ndjson.go`), отчёт — аккумулятор Issues. Записи буферизуются до конца файла ради семантики «всё-или-ничего» на синтаксисе — при 10⁴–10⁵ записей это структуры, а не сырые байты, память приемлема. Прогресс-колбэк в Go API — небольшое расширение сигнатуры (option).

Отсутствует REST-путь импорта: маршрутов импорта в `/api/v1` нет. Основная работа — `POST /api/v1/import` (NDJSON-тело, стриминговое чтение без `http.MaxBytesReader` с лимитом одной записи `maxBodyBytes`; лимит целесообразно заменить на лимит строки сканера, уже 16 МиБ), синхронный ответ отчётом после EOF; прогресс по REST — только polling/SSE (отдельное удорожание, в запросе не обязателен). Семантика частичных отказов (Issues) готова.

Оценка: 2–3 дня REST + тесты; Fallback с партиями по 2000 записей после появления эндпоинта не нужен.

### CC-7. Webhooks-friendly события (F11) — для модуля почти нулевая

Доставка вебхуков (подписки, ретраи, подписи) — зона сайта. От модуля требуется только поток событий CC-2 и согласованный формат события (kind/designation, тип изменения, revision — уже предложен в запросе). Fallback (поллинг `/stats`) работает сегодня без изменений.

Оценка: 0–0.5 дня модуля (зафиксировать формат события), остальное — сайт.

### CC-8. Расширяемость классов приборов — средняя, прежде всего дизайн

Утверждение запроса «состав классов data-driven (как состав параметров)» сегодня **не соответствует действительности**: реестр классов — Go-код (`internal/domain/kinds.go`: пять констант `Kind…`, `kindOrder`, `IsValid`), синхронизированный пин-тестами с сидами; применимость классификационных полей — тоже код (`internal/domain/designation.go`, `classificationFieldKinds`); отображаемые названия — бандлы `internal/i18n`. При этом сама модель данных классонезависима: EAV-значения не требуют правок схемы на новый класс, а параметры/атрибуты с пустым набором `Kinds` применимы ко «всем классам, включая добавленные в будущем» (D7).

Практический вывод: новые классы ТЗ (индуктивности, кварцы, предохранители, микросхемы) не имеют системы обозначений с разбором — это система `other`, парсер не нужен. Добавление такого класса кодом: реестр + строки i18n + сиды + тесты — ~1 день на класс, без изменения схемы. Полностью data-driven механизм (динамический реестр классов через секцию catalog) — широкое рефакторинг-изменение (domain-реестр, движок валидации, пин-тесты, полнота бандлов) с правкой планов; требует отдельного архитектурного решения и, вероятно, не окупается при частоте появления новых классов.

Ссылка запроса на эскалацию в дорожные карты обоих проектов (15, 16) уместна: нужно зафиксировать политику — «новый класс = новый релиз модуля» (дёшево, предсказуемо) против «классы из файлов каталога» (гибко, дорого).

Оценка: ~1 день на класс (код-путь) либо 5–8 дней на data-driven механизм + правка планов.

## Сквозные замечания

- **Версия схемы**: CC-2 (таблица событий) и CC-3 (колонка признака) — оба инкремент `SchemaVersion`; выполнять одним инкрементом (одно пересоздание баз импортом вместо двух).
- **Планы и контракты**: каждое из CC-2, CC-4 — осознанные изменения зафиксированных решений; по AGENTS.md требуют отдельного коммита с правкой всех связанных мест плана (`02-database.md`, `04-module-functionality.md`, `api/openapi.yaml`, `docs/fill-format.md`).
- **Тесты**: все новые ноги интеграционных тестов обязаны проходить на SQLite и PostgreSQL (`CATALOG_TEST_POSTGRES_DSN`, `go test ./... -p 1`) и попасть в сценарии `qa/runner`; для CC-4 это главный источник стоимости.
